    你说一句

  2. 2

    它读懂上下文

  3. 3

    它动手

应用架构

上游原样接入，密钥只留在服务端。

i豆 是一层薄薄的产品层：Codex 和飞书 CLI 原样接入、不分叉；飞书文档是事实来源；模型密钥和飞书应用密钥只在企业自己部署的控制面里。

  1. 读

    用你自己的身份

    Agent 用随附的飞书 CLI 读，经控制面代理，你的飞书令牌只在最后一跳加上，不进 CLI、Codex 和界面。

  2. 想

    密钥只在服务端

    每个任务一个 Codex app-server，模型请求走控制面网关；桌面上一把密钥都没有。

  3. 写

    按任务授权

    默认写入先弹确认卡；完全访问只在当前任务授权范围内自动执行。服务端许可仍只对应一个具体请求。

  4. 站

    表格变，网站跟着变

    桌面读表、交给网站服务；访客能不能看，每次实时问飞书。

  5. 跑

    到点自己跑

    定时任务在 gVisor 沙箱里运行，凭据由沙箱外的代理加上，结果存进你的云盘。

每人一份加密知识，回答前重新核验。

索引里有一篇文档，不代表你能读它。每次知识回答前，i豆 都以你当前的飞书身份重新核验候选来源；未通过核验的内容不会进入这次回答。

  1. 01

    你读过的飞书

    文档、知识库、电子表格、多维表格；也可以粘贴链接主动加入。

  2. 02

    来源证据页

    按章节无损切片，带版本、内容哈希、租户、读者和权限证据，加密存在本机。

  5. 05

    带出处的回答

    按词的稀有度挑段落，摘录只取刚重读的原文；抄错的链接会被更正。

为什么是 i豆

把力气花在对企业重要的地方。

站在 Codex 的肩膀上，能力持续进化

Agent 的内核是 OpenAI 持续迭代的 Codex。绝大多数团队自己写不出比它更好的 Agent，i豆 不重复造轮子，而是把精力放在飞书一体化和企业可控上。Codex 每一次升级，i豆 的编程和执行能力都随之提升。

模型在服务端统一管理

现在支持 MiniMax-M3 和 GLM-5.3（经服务端网关，密钥只在服务端），管理员按部门配置可用模型、每日额度和超额后的降级模型；某个模型出问题会自动切到下一个。模型能力与应用版本分开管理，便于企业按需替换。

能力跟随开源飞书 CLI，一起更新

i豆 随附并锁定 larksuite/cli：消息、文档、电子表格、多维表格、云盘、知识库、日程、任务等能力通过 provider 契约接入。

复用飞书 OAuth 身份

管理员完成企业应用配置后，员工使用飞书授权登录 i豆，不需要再维护另一套员工密码。

读取权限按当前身份复核

知识回答只引用这次查询中重新核验成功的候选来源；这不把历史缓存当成持续有效的访问证明。

个人知识副本不要求额外检索集群

当前个人本地副本在明确的 1000 篇 / 64 MiB 边界内运行；大规模企业集中索引仍在路线图中。

飞书 SaaS 今天就能用，私有化按契约接入

飞书 SaaS 已经随附；飞书接入是一份 provider 契约，私有化部署照同一份契约接入，契约测试已经就位（私有化 provider 开发中）。

一句话做应用，发布在自己的服务器上

网站、小游戏、数据看板，说需求就能做出来，本人确认后发布；网站由企业自己部署的服务端托管，不依赖第三方平台。

企业可控

默认先问你，授权了就自己做完。

  • 权限跟随当前会话：只读、标准、完全访问三个档位；标准权限下，发消息、写文档、发布网站等外部操作会明确确认；只有你主动授予完全访问后，才会在本会话范围内连续执行。
  • 你一授权，它就全自动做完：给任务开「完全访问」，发消息、改文档、存云盘、生成图片、建日程和任务、操作电脑，都不再逐次确认。
  • 定时任务到点自己交付：建任务时选好结果写进哪份文档、发到哪个群，之后每次跑完自动写过去；任务自己改不了去处。
  • 生成视频，不管怎样授权，每一次都单独问你。
  • 没授权的，你不点它就不做——取消或者超时，这一步都不会执行。
安全与隔离

从外到里八层，每一层都有测试钉住。

1

身份

飞书 OAuth + PKCE；会话最长 15 分钟，续期要设备密钥签名；管理员一键把人从所有设备签出。

2

密钥

模型密钥、飞书应用密钥只在控制面；你的飞书令牌在最后一跳才加上；定时任务的执行节点拿不到任何密钥。

3

人在回路

确认卡片只由人点；一次许可只对应一个请求（摘要绑定、30 秒、只用一次）；删除走红色卡片；生成视频每次都问。

4

数据权限

知识库每次回答都以你现在的身份重读；网站按人、群、部门授权，或跟随表格自己的权限。

5

编程沙箱

五档权限对应 Codex 沙箱；标准档没有网络；只放开本任务的 .git，仓库自带的 .codex 规则不执行。

6

网站隔离

访问凭据按「网站 + 访客」封装在地址里（AES-256-GCM + HMAC）；页面在无源沙箱里运行；发布、改版、刷新数据前先扫描。

7

定时任务

生产只认 gVisor：只读根、去掉全部权限、内部网络、资源上限；凭据在沙箱外的出口代理上加。

8

供应链

发布清单签名；随附的 Codex、飞书 CLI、Node 每次启动按摘要校验，从不去 PATH 上找；关掉 Electron 的三个调试与注入开关。

`.295` 的严格发布门禁通过 3,067 / 3,067；当前 55 个测试文件专门覆盖安全与隔离相关边界。审查发现的问题先固化成会失败的回归测试，再进入发布门禁。
