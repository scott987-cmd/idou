# Feishu login: server protocol and desktop flow

SaaS Feishu OAuth and desktop login/identity-confirmation/logout are implemented with synthetic upstream coverage. An opt-in [read-only CLI safety bridge](feishu-cli-bridge.md) now lets the bundled CLI reuse that login without receiving the Feishu token. Fresh tenant-user matching remains as the fallback for an independently authenticated CLI. Production/live authentication acceptance remains incomplete. No real Feishu application was authorized during verification.

## Server configuration

Supply these variables to the server process through its secret/configuration mechanism:

| Variable | Meaning |
| --- | --- |
| `IDOU_PUBLIC_URL` | Trusted public HTTPS origin, without a path. Local development may use literal loopback HTTP. |
| `IDOU_PORT` | Loopback listener port; default `3041`. For HTTP development, it must match the public URL port. |
| `FEISHU_PROVIDER` | Optional name of the Feishu deployment, from those this build ships. `saas-cli` (Feishu SaaS) is the only one and the default. Its OpenAPI and sign-in origins, identifier formats and capabilities come from the code, not from a setting. |
| `FEISHU_APP_ID` | The login application's identifier, in the deployment's own format (`cli_...` on SaaS). |
| `FEISHU_APP_SECRET` | Server-only app secret. Never place in desktop configuration, source, logs or chat. |
| `FEISHU_ALLOWED_TENANTS` | Explicit comma-separated tenant keys; wildcard access is rejected. |
| `FEISHU_SESSION_RENEWAL_ENABLED` | Optional `1` enables bounded online session renewal with device proof and a fresh server-side Feishu identity check. Omit to retain manual re-login. On its own it adds no OAuth scope and no offline/refresh permission. |
| `FEISHU_LONG_SESSION_DAYS` | Optional `1`-`30`, and only alongside `FEISHU_SESSION_RENEWAL_ENABLED=1`. This is the one setting that changes the paragraph above: the login additionally requests `offline_access`, a refresh credential is retained server-side, and a session may then outlive the Feishu access token up to this many days. `0` or omitted keeps the no-refresh behaviour. `offline_access` is not a console permission and is not registered there. |
| `FEISHU_SOURCE_ACCESS_ENABLED` | Optional `1` enables server-only, current-user Docx permission checks and explicitly requests the minimal permission-check OAuth scope. Omit for identity-only login. See [source access](feishu-source-access.md). |
| `FEISHU_CLI_IDENTITY_CHECKS_ENABLED` | Optional `1`, requiring source access above, enables fresh account comparison for native CLI operations. Default off; both applications must have appropriate user-ID permissions and the CLI must already be logged in. It adds `contact:user.employee_id:readonly` **only when the CLI bridge is off**: the sole caller of the account-match endpoint is built for the unbridged desktop, so with the bridge on the scope would be consented to and never spendable. See [account matching](feishu-account-matching.md). |
| `FEISHU_CLI_BRIDGE_ENABLED` | Optional `1`, requiring source access and an explicit `FEISHU_CLI_SCOPES` list, enables bundled-CLI transit over the server-held OAuth grant. Reads are the default; writes require `FEISHU_CLI_WRITE_ACTIONS` as well. |
| `FEISHU_CLI_WRITE_ACTIONS` | Optional comma-separated subset of the reviewed write actions, requiring the bridge. Empty means read-only. Each action is separately gated and binds one exact request. See [the bridge](feishu-cli-bridge.md). |
| `FEISHU_WIKI_ORIGINAL_ORIGINS` | Optional JSON object mapping an allowed tenant key to its Wiki origin, requiring source access. Presence adds the Wiki document read scope to the login. |
| `FEISHU_WIKI_BUNDLE_READS_ENABLED` | Optional `1`, requiring the origins above. Adds the Wiki bundle scopes to the login. |
| `FEISHU_CLI_SCOPES` | Explicit comma-separated OAuth scopes for the bridge. There are no implicit defaults; validate the exact scopes for enabled readers and the customer edition. |
| `MINIMAX_API_KEY` or `MINIMAX_CONFIG_FILE` | Existing server-only domestic MiniMax configuration. Required for chat on the default route, and for image/video generation on either route. |
| `IDOU_MODEL_PROVIDER` | Optional chat model provider. Unset or `minimax` keeps `MiniMax-M3`; `litellm` enforces `GLM-5.3` through a LiteLLM proxy on the control plane's own machine. The desktop learns the model from `/healthz`; nothing is configured client-side. See [chat model provider](control-plane.md#chat-model-provider). |
| `IDOU_LITELLM_BASE_URL` | With `litellm`: the proxy's literal loopback origin, `http://127.0.0.1:<port>` or `http://[::1]:<port>`; default `http://127.0.0.1:4000`. Host names, HTTPS, paths, queries and user info are refused. |
| `IDOU_LITELLM_MODEL` | With `litellm`: the proxy's model group serving `GLM-5.3`; default `volc-coding`. Never shown to clients. |
| `IDOU_LITELLM_KEY_FILE` or `IDOU_LITELLM_API_KEY` | With `litellm`: the server-only proxy key. The file (absolute, no symlink, at most 64 KB) holds the key alone or `KEY=VALUE` lines with `LITELLM_MASTER_KEY` or `IDOU_LITELLM_API_KEY`, so the proxy's own `.env` can be pointed at. The inline value wins. Like every model key it never reaches the desktop, the CLI or a log. |

Run `node bin/server.js --feishu` after configuring the environment. The server listens only on `127.0.0.1`; remote access requires a separately configured TLS reverse proxy. Register the exact `${IDOU_PUBLIC_URL}/auth/feishu/callback` redirect in the Feishu application console. No development token or client connection file is issued by the server in this mode. The existing `server:dev` path remains a separate, explicitly development-only bootstrap.

## Desktop use

Start the desktop with `IDOU_SERVER_URL=https://your-configured-origin npm run desktop`, without a development `IDOU_SESSION_FILE`. Open the account/settings entry at the bottom of the sidebar, choose **使用飞书登录** and authorize in the browser that opens. That browser is then sent back to this computer (item 3 below), shows 「飞书授权完成，请返回应用确认账号。」, and the app shows the account to confirm by itself; **立即检查结果** is there for a check by hand. Verify the displayed tenant, user and Feishu App ID before choosing **确认账号并进入**. The authorization link the settings page offers to copy finishes only in a browser on this same computer. The trusted server origin comes from main-process configuration, not a renderer-supplied redirect. No app secret or model key is entered in the desktop.

Until identity confirmation, the credential stays pending in the main process and cannot activate the model connection. Confirmation rechecks `/auth/session`. Task records, managed workspaces and Codex runtime homes are partitioned by a hash of `[server origin, App ID, tenant, user]`; names and device IDs do not change the namespace. Account switching is rejected while tasks or scoped IPC operations are active. Logout hides the account's records without deleting them; confirming the same identity restores them. The renderer reloads only its exact application entry to discard old drafts and views. Old task IDs and workspace handles are rejected in the new scope.

The native process passes its short-lived Agent bearer token to the existing Codex auth helper through a process-owned temporary lease (0700 directory, 0600 file on macOS/POSIX). Neither token nor lease path crosses renderer IPC. The lease contains no provider/application credentials. Expiry, normal logout and normal process exit attempt lease removal; logout/exit also attempt server revocation. Partial cleanup is reported for explicit logout/account switching, and revoked or expired tokens are rejected by the server. A crash may leave an expired lease for OS temporary-file cleanup; this is **not encrypted persistent credential storage**, a refresh session, or protection against another process running as the same OS user. Windows ACL hardening and packaged cross-platform acceptance remain open. Restart requires login again.

Account namespaces provide application-level record routing, not encryption of task history or an OS-level boundary against local coding tools. Existing user-selected coding directories remain user-selected and are not copied or claimed to be isolated by login. The connection badge reflects the locally held token's expiry, not a continuous server-health/revocation probe; model requests are still authorized on the server.

### Recovering an unsuccessful login

An expired authorization flow, denied consent, missing server flow (including restart), or invalid redemption response returns the native client and settings UI to **使用飞书登录** / **重新登录 / 切换账号**. The user explicitly starts a fresh OAuth flow; there is no automatic browser launch, token reissue or task replay. HTTP 408/429/5xx and transport failures preserve the flow for a later manual check. If a successful redemption response was lost, the next check is rejected by the server's single-use flow and returns to fresh login; the unknown token is not reissued and expires server-side within its original lifetime.

An expired, revoked or identity-mismatched pending confirmation is discarded and its known token is best-effort revoked. Expiry is checked again after identity verification and lease creation before requesting activation. Failure to confirm a candidate does not retire the already active account or its task namespace. Temporary verification errors and a running-task/account-operation refusal leave the candidate available for manual retry while valid. Renderer actions refresh the native state after rejected login IPC, so stale confirmation/poll controls are not left on screen. Local lease cleanup and server revocation still have the previously documented failure boundaries.

That recovery flow is separate from the optional online renewal below. Each parent remains at most 15 minutes; independent CLI login, short-lived child leases, restart login and source-access checks remain. Actual live authorization, CLI Keychain repair and offline/long-lived enterprise session design remain open.

### Optional bounded online renewal

Default off. With `FEISHU_SESSION_RENEWAL_ENABLED=1`, the SaaS OAuth adapter retains the original access token only in server memory and binds it to the confirmed device public key and session. At most 100 pending/bound authority entries and four concurrent renewal verifications are accepted. Pending entries expire within five minutes; bound entries expire with their parent and zero their token buffers on removal. JavaScript/HTTP response strings are not secure-memory storage. With `FEISHU_LONG_SESSION_DAYS` unset or `0`, no refresh token is retained or used and no offline permission is requested; setting it to 1-30 days deliberately reverses both, which is the whole point of that setting. Either way, neither Feishu nor model/app secrets enter the desktop.

The desktop schedules one automatic attempt two minutes before expiry. `/auth/session/renew-begin` accepts only a current parent in that window and returns a single 60-second challenge bound to its session ID. `/auth/session/renew` requires a domain-separated Ed25519 signature covering server origin, session ID, challenge ID and nonce. Redemption is consumed before the fresh `user_info` request. The response must identify the same application/tenant/user; revocation and expiry are checked again after the asynchronous request. The new parent lasts at most 15 minutes, bounded by the original upstream token lifetime and an absolute four-hour horizon from initial redemption. The horizon never slides. Long upstream lifetimes do not enable indefinite login.

Old parents keep only their original expiry, giving the unchanged 60-second Codex auth-helper refresh interval a two-minute transition window. Existing child grants do not gain time or scope. Explicit logout of a live family parent revokes both generations and their children; natural expiry of a predecessor does not remove the successor. Optional source-access authority is copied server-side to the new parent within the original upstream expiry; each actual document/Wiki access still checks current identity and resource permission. Rotation does not grant source/CLI permission when it was absent.

The native lease is replaced atomically at the same private path. No workspace activation, task recreation or renderer reload is needed for successful renewal. The client checks device/account identity, expiry and the fixed horizon before adoption. An active login/switch operation pauses automatic renewal; complete that login instead. Expiry, logout, shutdown and late responses cannot reinstall a closed lease. A network failure, invalid response, failed live identity check or file replacement failure stops renewal, marks the connection unavailable and attempts local cleanup/family revocation. Unknown deliveries are not retried. If cleanup/revocation cannot be confirmed, an unknown bearer remains bounded by its original maximum 15-minute lifetime. Resume requires explicit login.

This is **not** renewal of media/MCP/runtime grants or pending write confirmations. The desktop serializes login renewal after current Wiki cloud and local work, then [revalidates running Wiki schedules and any already-enabled synthesis consent at one checkpoint](wiki-desktop-publication.md#online-session-checkpoint). Publication/reception grants are not extended. An unexpired local synthesis opt-in may adopt only a strictly newer same-account/same-gateway binding; its six-call startup budget is preserved. Explicit disable, expiry, identity/gateway mismatch or failed renewal leaves synthesis off, and paused/unknown/reserved work is not replayed. Other stale-session checks can still pause an operation. Long model streams and all-day Wiki work are not certified uninterrupted. Restart still requires login and manual synthesis opt-in; server state is volatile, with no distributed renewal registry, hardware attestation or production availability claim. The standalone `FeishuLoginClient` needs a stable supplied device-key factory for renewal; its default per-flow ephemeral key does not provide that continuity.

## Protocol and security boundaries

1. The native client obtains an Ed25519 signing key, opens a listener for this one sign-in on `127.0.0.1` at a port the system picks ([`login-return.js`](../src/application/login-return.js)), and posts its public key and that port (`returnPort`, 1024–65535) to `/auth/feishu/begin`. The desktop uses its [encrypted per-server device identity](device-identity.md); standalone clients without a supplied key factory retain the ephemeral-key default. The server creates a five-minute flow, nonce, OAuth state and PKCE verifier. A begin without a port is refused with `client_update_required`: it comes from a desktop older than 0.1.0-20260927.248, and signing in without a way back is exactly what the attack below needs.
2. The client opens the returned, same-origin `/auth/feishu/launch` URL in a trusted system browser. That endpoint sets an HttpOnly, SameSite=Lax callback cookie and redirects to Feishu with an S256 PKCE challenge.
3. The server callback checks one-time state and the initiating browser cookie, exchanges the authorization code server-side, reads the user's identity, and enforces the tenant allowlist. By default, Feishu access tokens are used transiently and not returned or persisted; no refresh token is requested. No document, chat, phone, email or offline-access scope is requested for this identity-only flow. With the explicit source-access opt-in, only the permission-check scope is added and the server retains the access token in memory, bound to the redeemed parent session, for at most its lifetime. It is still never returned or persisted. [Retention and revocation details](feishu-source-access.md). An authorized login gets no page: the callback redirects that browser to `http://127.0.0.1:<returnPort>/mydoubao/login-complete?flow=…&secret=…` with a one-time secret, which the server keeps only as a digest. The device's listener answers only that path, its own flow and its own `Host`, keeps the first secret it is given and tells the desktop, which finishes the sign-in at once. A denied or failed login, a probe (item 6) and a grant (item 7) still get their JSON page.
4. `/auth/feishu/complete` requires a signature over the server origin, flow ID, nonce and action, and -- once the flow is authorized -- the secret the device's listener received. Without it the answer stays `pending`, whatever the browser did; a wrong one ends the flow (`login_completion_mismatch`), since there is exactly one and nothing legitimate sends another. An authorized flow can issue one model-scoped Agent bearer token with a maximum 15-minute lifetime. Cancellation has a separate signed action. Expired, canceled, replayed and late exchange results cannot mint a replacement session.
5. `/auth/session` reads the current Agent identity and optional renewal metadata. `/auth/logout` revokes that Agent session family, not the user's global Feishu or CLI login.

6. `/auth/feishu/web-identity/begin` and `/auth/feishu/web-identity/status` answer one question: is the Feishu account the desktop's **embedded web pages** are signed in as the same person as this session? Nothing those pages say about themselves is evidence of that, so the desktop opens the returned launch URL inside the pages' own browser partition, Feishu's authorize page answers for whoever is signed in there, and this server redeems the code and compares tenant and `open_id` (same application, so the same `open_id` space). The status route returns only `verified`, `conflict`, `declined`, `probe_failed` or `pending`, once, to the session family that began it. The other account's identifiers are never returned or kept; no session, grant or credential results from a probe, and `/auth/feishu/complete` refuses a probe flow. A probe asks for the login's permissions **minus `offline_access`**, so it mints no refresh token: whether Feishu retires older refresh tokens when it issues a new one is undocumented, and unattended schedules depend on the one the server holds. Only a root session may begin one (not a turn token the coding agent can read), ten per person per ten minutes; a flow lives three minutes.

7. The unattended schedules credential comes from a **dedicated authorization** of the same shape: the schedule service begins a flow of kind `grant` for the requesting root session (`beginGrant`), the desktop opens its launch URL (in the pages' partition first, then the system browser), and the callback redeems the code with the login's own permissions — `offline_access` included — and hands the new refresh token to the schedule service's hook, only if Feishu says the authorization belongs to the session's person. It is a separate token chain on purpose: a refresh token is single-use, and the first version, which copied the live session's token, let whichever side refreshed first spend the other's copy. `/auth/feishu/complete` refuses a grant flow as it does a probe.

**Why a sign-in comes back to its own device (2026-09-27).** Until then the launch link worked in anyone's browser and the session went to the device that began the flow. Anyone could begin a sign-in on their own machine and send the link; the recipient, signed in to Feishu in their browser, clicked 授权, and the sender's device received a session holding the recipient's account. The device-key proof only proved the sender's device was asking. Now the secret that completes the sign-in goes to the loopback address of the machine whose browser authorized it -- the recipient's own -- and the sender has nothing to complete with. This is the loopback redirect of RFC 8252 §7.3, carrying the completion rather than the authorization code, which stays redeemed server-side. The cost is that a link opened on another device (a phone, another computer) cannot finish. It does not protect against software already running as the person on the same machine. `test/feishu-login.test.js` («a sign-in link opened in someone else's browser gives whoever sent it nothing») fails with the check removed, and `scripts/smoke-login-desktop.js` shows the real application staying signed out while an authorization that never came back to it is pending.

The device-key proof protects **login redemption and optional online renewal**. It is not per-request proof of possession or hardware attestation. The issued token remains a bearer credential. Flows and sessions are in memory and are invalidated by restart. A lost successful redemption response may require a new login; the server does not mint a second token on retry.

Auth routes reject browser Origin headers on native requests, bound JSON bodies/responses, suppress provider error details and set no-store/referrer/CSP protections. These controls do not replace a production security review, distributed abuse controls or reverse-proxy configuration. Proxy/access logs must redact callback queries, cookies, authorization headers, request bodies and the callback's `Location` response header, which carries the completion secret. Never enable payload logging for model traffic.

## CLI bridge, fallback identity matching and remaining work

The bundled `lark-cli` 1.0.78 exposes Device Flow through `auth login` and no import-token interface. It also provides an official compile-time `authsidecar` protocol. i豆 now packages that exact reviewed variant and can advertise `cliBridge: true` after one application OAuth consent when the server explicitly enables it. The CLI uses sentinel credentials and a loopback HMAC proxy; the real user token stays server-side. The implementation does not extract browser cookies, reset a CLI profile or downgrade Keychain protection. See [protocol and limits](feishu-cli-bridge.md).

`open_id` is application-specific. Optional native account matching compares freshly resolved `tenant_key` + `user_id`, not raw cross-application `open_id`, names, email, phone or employee number. Because `user_id` can be changed administratively, it is never a persisted login key or durable association. The server verifies its own current OAuth user and compares a candidate from the native reader; it does not authenticate arbitrary client claims as the CLI. See [protocol, tests and point-in-time limits](feishu-account-matching.md). The private CLI remains replaceable through the provider boundary, but its authentication contract is not yet supplied or verified.

`src/application/feishu-login-client.js` implements begin, signed polling, cancellation and optional online renewal. `desktop-auth.js` wires it into Electron with explicit identity confirmation, short-lived activation and same-path rotation. Persistent login across restarts, offline renewal and a public CLI login command remain open.

Without explicit server enablement, Feishu-login mode continues rejecting document/Wiki/chat business entry points. With `cliBridge: true`, each account scope owns an isolated native sidecar and the bundled CLI can execute only server-permitted read requests as that same OAuth identity. Otherwise `cliIdentityChecks: true` retains the point-in-time separately logged-in fallback. Existing document/resource/version/permission checks remain. Coding/local-file work can use the Agent gateway token; full enterprise command policy is still required before bridge writes are enabled. Instructions are **not an OS shell sandbox**. The separate development mode retains its CLI workflow. Live acceptance remains blocked by the developer environment's previously observed uninitialized Keychain, which was not retried or modified.

These tests do not establish private-deployment OAuth or uninterrupted real-model streaming.

The 2026-09-09 recovery increment adds seven automated tests across the actual native login client/desktop controller and loopback HTTP routes, with synthetic Feishu transport. A pre-fix reproducer failed because an expired flow retained `stage=waiting`. Additional coverage exercises transient errors without automatic retries, a lost redemption response without reissuance, malformed redemption revocation, pending confirmation expiry/revocation with the old account preserved, expiry across asynchronous checks, and cancelled poll single-flight recovery. They do not demonstrate live OAuth, private Feishu compatibility or production security certification.
