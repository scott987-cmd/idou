# Feishu message reading — development implementation

## User path

**飞书消息 → 读取会话 → select single/group chat → read messages → 在工作任务中打开文档**.

The standalone text-labelled sidebar entry now contains an actual reader, not a placeholder. Opening the section does not fetch private history until the user selects **读取会话**. Conversations sort by activity; additional pages are explicit. Message pages use newest-first ordering, with **更早一页** and **刷新消息**. Expanded thread replies are available under a disclosure; partial/error flags remain visible. Text/post messages now support reviewed plain-text replies as described below. This is not the complete Feishu client: unsolicited new messages, rich replies, events, search, unread synchronization, card actions and binary attachments remain unfinished.

Reading a message does not itself start Codex/MiniMax, persist chat history, transmit chat text to the control plane or create a Wiki page. **自动整理此会话文档** separately confirms a background scope that discovers document links without further clicks; see [automatic discovery](message-discovery.md). Clicking a discovered supported docx/wiki link manually still re-reads the source message first. Recalled, inaccessible, missing, replaced or link-removed messages cannot supply the old link. The application then opens a new work task and performs the normal fresh document read. Its source evidence may automatically enter encrypted local Wiki storage; model synthesis retains its existing opt-in policy. If the document read fails, the task displays an error with no cached body. An empty newly created task may remain; no model turn has started.

## Ownership and authorization

- `src/providers/feishu/chat-reader.js` owns SaaS argv/envelope parsing behind `feishu.chatReader`. The application service and renderer contain no SaaS/private URL or command branches. The executable/profile/digest are still owned by the existing provider. No pin changed.
- Each CLI read checks verified user identity before and after; subsequent operations bind principal and nonempty tenant to the current view. Under the login bridge a check made moments earlier under the same application session answers for both, for at most 30 seconds; a changed session is checked again, and a reply's own dispatch checks are always fresh (see [the bridge](feishu-cli-bridge.md#identity-checks)). No bot fallback, implicit scope grant, credential extraction or browser-cookie import. Production enterprise business IPC opens only for the explicit read bridge or fallback identity match; bridge writes go through the confirmed one-shot grants described there.
- `src/application/chat-reader.js` owns ephemeral conversation, pagination and document-link capabilities. Renderer-provided raw IDs/cursors cannot replace these. Different conversations/pages cannot exchange cursors; new message pages retire old links. A new read supersedes older asynchronous operations, and late completion cannot restore old state.
- Navigation, renderer crash/reload, account switch, close and a native five-minute timer dispose the session. The UI also clears expired content. Each action rechecks expiry; expiration is not extended by pagination. Previously displayed snapshots are not continuously reauthorized: revocation between reads is observed on the next operation or expiry, not instant push invalidation.
- A message read is not proof of document permission. Message revalidation and document reauthorization are separate, non-atomic reads. Documents can still change between them; no transaction or lock is claimed.
- Source text, resource placeholders and card projections are inert `textContent`, not HTML, Markdown rendering, downloads or tool instructions. Only separately validated HTTPS document references receive an action button. Upstream raw failures are not exposed. Sender display names are accompanied by supplied IDs and never guessed through a contact fallback.

## Bounded transport

Version-aligned embedded IM/shared skills and command help define the current contract:

- `im +chat-list --types p2p,group --sort active_time --page-size 30 --as user --format json`;
- `im +chat-messages-list --chat-id … --order desc --page-size 30 --no-reactions --as user --format json`;
- `im +messages-mget --message-ids … --no-reactions --as user --format json` for a selected source link.

Reading issues no `--download-resources`, write or auth mutation. Calls have a 30-second timeout and 2 MiB output ceiling. Upstream thread auto-expansion still occurs even with `--no-reactions`; it is not a guarantee of one HTTP request per CLI invocation. The reader bounds one response to 50 host messages plus at most 500 replies, 64 KiB per projected message, at most 20 supported document URLs per message and a 500-conversation browsing session. Oversized/incompatible responses fail closed rather than appearing complete. Unknown conversation attributes remain labelled unknown; external chats are labelled, not silently classified internal. Actual private-edition envelopes/capabilities remain to be supplied and tested.

## Reviewed plain-text replies

**消息 → 回复 → edit up to 2000 characters → optionally 在话题内回复 → 核对并发送回复 → native confirmation**. Both host messages and expanded text/post replies can be selected. Recalled messages, cards and media have no reply capability in this increment. The composer uses inert DOM text and preserves literal newlines; `<`/mention tags, control/bidi characters are rejected. No Markdown/media resolution, automatic @, bot identity or model generation occurs.

`ChatReader` holds an opaque reply handle tied to the exact page object, original message and CLI principal/tenant. New pages, same-chat refresh, expiry or navigation invalidate it. `ChatReply` serializes sends, re-fetches the selected message before confirmation, then the provider re-fetches after confirmation and rechecks identity after the durable reservation. Changes to content, sender, type, deletion, identity or a supplied mismatched chat ID prevent dispatch. The native dialog shows conversation ID, snapshot name/external status, source ID/author/excerpt, full reply text, user identity and thread/main-chat destination. Cancel is the default. A group reply is visible to the conversation's authorized audience, not only the original sender. Chat names/membership may change after reading; no atomic lock or current roster confirmation is claimed.

The provider calls the version-pinned CLI's `im +messages-reply` once with native-owned target, exact `--text`, explicit user identity and a UUID idempotency key; only a matching chat ID and valid new message ID count as acknowledged. Required user reply scopes are `im:message.send_as_user` and `im:message`; missing permissions never trigger automatic scope grants. Reply transport is bounded to 30 seconds and 256 KiB output. Acknowledgment is not proof that anyone has read the message.

Before dispatch, `chat/reply-receipts.enc` is atomically replaced using private temporary files, file sync and directory sync. It is protected by the same OS-backed cipher policy as local Wiki but is a separate account-local journal. It stores only fingerprint, UUID, time, state and optional receipt—not source or draft bodies. The fingerprint includes tenant/principal/chat/message/exact reply/thread mode, deliberately not source revision. Duplicate acknowledged or uncertain attempts remain blocked across restart and source edits. Lost or malformed receipts, including post-send local save failure, remain conservative `unknown`/`dispatching`; no automatic resend. Pending reservations can be conservatively retained even when a later preflight prevents the write.

Limits: 5000 entries / 2 MiB; corruption, unavailable encryption or a full journal stop sending without overwriting/evicting prior evidence. No automatic cleanup, operator reconciliation, cross-device deduplication or globally exactly-once guarantee is implemented. The upstream idempotency window is one hour; local tombstones do not expire automatically. OS encryption, filesystem power-loss guarantees and real SaaS reply behavior still need packaged/live acceptance.

`test/chat-reply.test.js` verifies consent/cancellation, exact arguments, native-handle tampering, source/identity/navigation/expiry races, durable intent ordering, encryption, missing/corrupt/full storage, lost/mismatched receipts and restart deduplication. `scripts/smoke-chat-reply-desktop.js` runs actual Electron/main/preload/renderer with synthetic Feishu/cipher and intercepted native-dialog answers: cancel, changed draft, thread reply, narrow composer, uncertain receipt, restart, navigation race and zero live writes. The login smoke separately rejects the reply IPC for an unlinked enterprise identity.

## Verification and remaining scope

`node --test test/chat-reader.test.js` covers the pinned provider-runner path, user/tenant checks, inert and recalled text, source re-fetch, malformed data, bounded paging, forged/cross-view handles, expiry and late responses. `node scripts/smoke-chat-desktop.js` uses actual Electron/native IPC and task/Wiki files with synthetic CLI and encryption responses; it tests desktop paging, thread rendering, script non-execution, navigation races, permission failure, source-to-task navigation, source-only encrypted Wiki and visible document errors. It makes no live Feishu or model requests. The existing login smoke also rejects all new business IPC for an unlinked enterprise identity.

An isolated in-memory mutation replacing source-message re-fetch with a cached URL made the recalled-source rejection assertion fail. No production file or real resource was mutated. Screenshots: `evidence/desktop-chat-reader-fixture.png`, `evidence/desktop-chat-reader-narrow-fixture.png`, `evidence/desktop-chat-document-task-fixture.png` (synthetic content only).

Live SaaS acceptance remains pending; the known developer-profile Keychain failure has not been retried/reset. Application login now has a server-held, read-only CLI bridge with synthetic actual-binary coverage, but browser Feishu embedding, bridge write policy, rich replies, enterprise-managed/event-driven ingestion, distributed Wiki/Drive publication, ACL propagation and private-CLI replacement remain part of the full product goal. The bounded background discovery worker and reviewed plain-text replies do not prove those requirements complete.
