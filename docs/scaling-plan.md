# 服务端扩容：从单进程到多副本与执行池

2026-09-26 起。目标是让我们自己的服务端能支撑十万人部署、管理和使用。飞书侧的限制（接口配额、令牌刷新）按用户要求不在这里考虑。本文是设计，也是进度记录。

## 现状（第 1 步之后）

- 控制面是**一台 4 核机器上的一个 Node 进程**。压测显示，单进程大约能同时撑 2000 路流式回答，到 4000 路就把一个核跑满（`scripts/load-test-control-plane.js`）。这就是现在的天花板。
- 三十多个模块把跨请求的状态只放在进程内存里：会话令牌、飞书刷新令牌和访问令牌、登录流程、一次性写入授权、MCP 租约、各种缓存。数据放在同一块盘上的 6 个 SQLite 库和若干 JSON 文件里。
- 所以现在既**不能开第二个进程**（另一个进程不认识这些会话），**重启也会让所有人掉线**（会话随进程消失，桌面要重新登录）。

**第 1 步的补漏（9-26 下午）**：代码里还有一批写死的整机数字，是试点时按「一个人用」定的：同时登录 100 个会话（第 101 个同时在线的人登录会失败）、同时读飞书 4 个、同时续期 4 个、每分钟新登录 30 次、写入确认每分钟 60 个、MCP 连接 32 个、同时生成媒体 4 个、知识库密钥授权 100 个。现在旧数字是每个人的份额，整机上限进了部署配置（`IDOU_SIGNED_IN_MAX` 等，见 `docs/server-deployment.md` 的容量表），默认按十万人定。这几个模块里每次调用都遍历全部授权的清理，也改成了按到期排队（`src/control-plane/limits.js`）。回归测试 `test/scale-limits.test.js`：150 个人同时登录全部成功，6 个人同时读飞书、10 个人同时续期互不挤掉，每分钟 100 次新登录不被拦；同时一个人的份额仍有上限。把默认值改回试点的数字，这些测试都会失败。

## 目标架构

```
             nginx（443）
   ┌───────────┼───────────┐
 api@a       api@b       api@c        ← 控制面副本：每个都能接任何人的请求
   └───────────┼───────────┘
          PostgreSQL                   ← 共享：持久数据 + 加密的短期状态 + 通知 + 选主
   ┌───────────┴───────────┐
 worker@1               worker@2       ← 执行池：领取定时任务，在本机 gVisor 沙箱里运行
```

**只新增 PostgreSQL 一样东西**，它同时承担三件事：

1. **持久数据**：替代 6 个 SQLite 库（定时任务与运行记录、用量、云盘额度、应用目录、知识库协调、知识库密钥），以及散落的 JSON 文件（网站登记、模型偏好、技能登记）。
2. **共享的短期状态**：会话、续期凭据、飞书访问令牌、登录流程、一次性授权、租约，都存进同一张表。
   - 值用 AES-256-GCM 加密；密钥是副本共用的一个文件，不进数据库，所以数据库备份里没有明文令牌。
   - 附加数据绑定到「命名空间 + 键」，一条密文不能被搬到别的位置用。
   - 键是令牌的 SHA-256 摘要，和现在内存里的做法一样，库里不存令牌本身。
3. **副本之间的协调**：
   - `LISTEN/NOTIFY` 做失效通知：吊销、网站更新、配置变化；
   - advisory lock 做选主：同一时刻只有一个副本当「协调者」，负责定时调度、清理任务和通知。

**每个副本仍在内存里缓存**，请求路径上的读是本地的、同步的，这一点不变。写入同步到数据库；缓存里没有的，就在请求入口处从数据库加载。因此：

- 任何副本都能接任何人的请求，nginx 可以随便分发；
- 滚动重启时，一个副本停下，它的用户由其他副本接着服务，**不掉线**；
- 吊销、单次消费这类必须全局一致的操作，都在数据库里原子完成（`DELETE … RETURNING`、带版本号的更新），不依赖哪个副本的内存。

**同一个人固定落在同一个副本上。** 有一类状态绑在连接或进程上，搬不进数据库。这一类在平时由路由保证。盘点见下表：

| 绑在进程上的状态 | 为什么搬不走 | 副本换了会怎样 |
| --- | --- | --- |
| MCP 会话（`mcp-broker.js`） | 持有和上游 MCP 服务的实时连接 | 返回「会话不存在」，客户端重新建立 |
| 媒体生成任务（`media-service.js`） | 在本进程里轮询供应商；每个进程有自己的编号，别的进程回 409 | 进行中的任务要重新发起 |
| 知识库密钥授权（`wiki-key-service.js`） | 明文密钥只在内存里，等客户端回来绑定 | 客户端按租约重新申请（已有幂等键） |
| 文档网站推送（`site-server.js`） | SSE 连接挂在进程上 | 浏览器的 EventSource 自动重连 |
| 用量、并发的计数 | 按进程计 | 整机上限变成「每个副本的上限」，按副本数分摊 |

- **做法**：令牌前面加一段由「租户 + 用户」算出的短路由码（SHA-256 的前几个字符，不含身份信息），同一个人所有令牌前缀相同；nginx 取这段前缀做一致性哈希。
- **平时**：一个人的请求都落在同一个副本上，上表的状态都在本副本里。
- **副本增减或重启**：只有那个副本上的人被重新分配。因为会话是共享的，他们不用重新登录，只有上表那些东西需要客户端重新建立。
- 没有令牌的请求（健康检查、开始登录）随便分；登录回调带着状态码，登录流程也在共享状态里，落在哪个副本都能完成。

**执行池（第 3 步）**：定时任务到点后进入 PostgreSQL 里的队列（`FOR UPDATE SKIP LOCKED` 领取）。worker 进程在自己所在的机器上起沙箱，并在本机提供沙箱的出口代理。控制面副本不再自己执行任务。先和控制面放在同一台机器上跑（用户 9-26 的选择）；以后加机器，只是在新机器上多起几个 worker。

## 不变的东西

- 所有安全约束照旧：
  - 租户身份和权限证据记在每条记录上，查询按调用者当前的授权过滤；
  - 模型和飞书的密钥只在服务端；确认卡片只能由人来点；
  - 沙箱仍是 gVisor 加内部网络加宿主防火墙。
- 桌面端的接口不变。
- 不设 `IDOU_DATABASE_URL` 时，一切照旧：单进程、内存状态、SQLite。开发态和测试默认也还是这样；多副本是显式开启的部署方式。

## 分阶段

盘点（9-26，三份，覆盖认证、授权与租约、持久数据与单进程职责）之后的顺序：**先把最重的负载摊开，再逐步把其余部分搬过去**。

- 最重的负载是流式模型请求（`/v1/responses`），它只需要认得会话。
- 其余路由量小，状态又多：登录、续期、定时任务、文档网站、管理台、云盘额度、应用目录、知识库、技能登记、模型偏好。这些暂时全部留在一个「协调副本」上，模块一行不改。

## 2.2 的做法（9-26）

代码在 `src/control-plane/sessions.js`（会话登记）和 `src/control-plane/database.js`（接数据库）。设了 `IDOU_DATABASE_URL` 和 `IDOU_STATE_KEY_FILE` 才启用，不设和以前完全一样。

- **写库**：每签发一个令牌就写一条加密记录，键是令牌的摘要。同一个令牌的写入排队进行，所以吊销一定落在签发之后，晚到的签发写不回已吊销的会话。
- **交出令牌前等写库**：登录、恢复登录、续期返回令牌前，先等它第一次写库完成，因为桌面端的下一个请求可能落到别的副本。写不进（数据库不在）时不拒绝：续期那一刻飞书的刷新令牌已经换过，拒绝等于让人重新登录。令牌先在本副本可用，后台一直重试到会话到期。
- **读库**：请求入口带着本副本没有的令牌时，从库里读出它和它所挂的根令牌。库里没有的令牌记住 1 秒，客户端反复重试同一个失效令牌不会每次都查库。
- **吊销**：一个登录的所有轮换和子令牌用一条语句删除，并通知所有副本；从没持有过这个登录的副本也能吊销它。退出登录在吊销写进库之后才回复。
- **通知断开**：监听连接断开后不断重连（间隔逐步加长，最长 30 秒）。重连成功后，每个副本把手上的令牌拿到库里批量核对一遍，丢掉已经不在的。断开期间照常服务，因为会话最长 15 分钟，而数据库一重启就拒绝所有人的代价更大。
- **暂时只给模型网关用**：从库里读来的会话只被模型网关（`/v1/responses`）接受。续期、飞书访问、各种租约还按会话把状态存在签发它的进程里（2.4 才写库），所以这些服务仍把它当未知会话，回 401，桌面端照旧立即用本机凭据自动重连，和今天重启后的行为一样。唯一的变化是模型请求在重启期间不断。
- **路由码**：令牌的前 6 个字节（前 8 个字符）是用密钥对「租户 + 用户」算的 HMAC，同一个人的所有令牌前缀相同，其余 26 个字节随机。路由密钥由封存密钥派生，运维只需保管一个密钥文件。
- **顺带修的**：过期清理原来每签发一次就扫一遍全部会话，十万人在线时这一项就要大半个核，现在按到期时间排队，只看已到期的。共享状态层的监听连接原来只重连一次，数据库停超过 1 秒就再也收不到通知，已修。

测试：`test/session-sharing.test.js`（两三个副本共用一个 PostgreSQL 的吊销、轮换、断线核对、读写竞争）、`test/database.test.js`（配置校验，以及起两个真实服务端进程共用一个库）、`test/state-store.test.js`（新增批量核对和数据库重启后重连）、`test/feishu-login.test.js`（登录等写库、退出等吊销）。其中 14 处关键修复逐一撤回验证过，每一处都会让测试失败。

## 2.3 的做法（9-26）

- **角色**：`bin/server.js --feishu --role api`。只起模型网关和指标，别的一概不起：不签发令牌、不跑定时任务、不开文档网站。没配数据库就拒绝启动（副本认不得别人签发的令牌就不算副本）。其他路径一律 404。
- **模型相关的部件两种角色共用**：模型列表和顺序、模型健康状态、可见性策略（按群的规则照样读飞书群成员）、用量记账。用量记在同一个 SQLite 文件里，WAL 模式允许几个进程同时写。
- **停机排空**：API 副本收到 SIGTERM 先停止接新连接（nginx 立即把新请求转给另一个副本），正在流式回答的请求最多再等 45 秒说完；还没说完的就断开，由 Codex 自己重试。停机不吊销任何会话。
- **nginx**（`deploy/server/nginx-idou.conf`）：从 `Authorization` 头取令牌前 8 个字符做一致性哈希。一个副本连不上（停机、重启中），请求转给下一个；那个副本从库里读出会话照常服务。
- **容量**：每个 API 副本各自按 `IDOU_MODEL_MAX_CONCURRENT` 限流（默认 8）。两个副本合计 16，是原来单进程的两倍。模型账号的并发配额如果更低，高峰时上游会回 429，这时按配额把每个副本的上限调低。每人上限不变：一个人固定落在一个副本上。
- **systemd**：`deploy/server/idou-api@.service`，实例 N 在共用配置之后再读 `/etc/idou/api-N.env`（端口和指标端口）。

测试：`test/api-replica.test.js` 起真实的协调副本和 API 副本共用一个 PostgreSQL，检查：协调副本签发的令牌在 API 副本上能用；其他路径 404；API 副本停机时在途回答完整返回、不再接新连接，停机后协调副本的令牌照样有效。「在途回答立即被切断」「停机时还接新连接」两种写法撤回验证过，测试都会失败。`test/deploy-server.test.js` 核对 nginx 取的路由码和会话登记放进令牌的一致，nginx 的上游端口和 systemd 实例的端口一致。

## 2.4 的做法（9-26）

- **存什么**：每个登录会话的飞书访问授权（`source-grant`）和续期凭据（`renewal-grant`，含刷新令牌和设备公钥），按会话编号加密存进共享库，到期时间跟会话一致。签发、续期换代、刷新访问令牌时写库；续期一开始就把旧凭据标成「已用」并写库；吊销、到期时删库。**关机不删**：协调副本停下时只清自己的内存，库里的授权留给重启后的自己（或别的副本）。代码在 `src/control-plane/shared-records.js`，两个模块各自的 `load()`。
- **怎么读回**：会话登记从库里读会话时，调用这两个模块登记的读取函数，把这个会话的授权一起读回。两份都读到了，这个会话就对所有服务开放；有一份没读到（2.4 上线前签发的会话、写库失败），就维持 2.2 的规则：只给模型网关用，其余服务回 401，桌面端用本机凭据自动重连。
- **交出令牌前**：登录、恢复登录、续期返回令牌前，除了等会话写进库，也等两份授权写进库。
- **效果**：协调副本重启后，桌面端的会话连同飞书访问和续期一起从库里恢复，不再需要重连。上线 2.4 的那一次重启例外：之前签发的会话库里没有授权，会重连一次。
- **仍然只在进程里的**（重启后由客户端重新建立，不影响登录状态）：进行中的登录流程、续期挑战（重启落在要挑战和回答之间的一分钟里，会退回重连）、写入确认、MCP 连接、媒体生成任务、知识库密钥授权、定时任务的「本次登录内授权」（无人值守授权另有持久化）。

测试：`test/grant-sharing.test.js` 用两三个「协调副本进程」共用一个 PostgreSQL：A 登录后关机，B 读回会话和两份授权，飞书访问照常，还能在 B 上完成一次续期；续期得到的新会话和授权又能被 C 读回，旧凭据在 C 上也是「已用」。吊销会把会话和两份授权都从库里删掉；库里没有授权的老会话只给模型网关用。关机删库、读会话不读授权、「已用」不写库、吊销不删库、缺授权也放行，这 6 种写法撤回验证过，测试都会失败。

## 第 3 步的做法（9-26）

- **从哪里切**：定时任务这条链是「到点 → 认领 → 确认身份 → 执行 → 归档 → 记录 → 通知」，真正起容器的只有「执行」里的 `sandbox.execute(job)` 一处。执行池就在这一处把「本机 Docker」换成「放进队列、等 worker 做完」。准备运行目录、出口令牌、读上一次的报告、选模型、解读结果、归档、通知，全部照旧留在协调副本。worker 不持有任何飞书授权，也不碰定时任务库。
- **队列**（`src/control-plane/run-queue.js`，表 `idou_run_queue`；表名前缀新库是 `idou_`，改名前建的库整库沿用 `mydoubao_`，见 `src/control-plane/database-names.js`）：
  - 任务内容（沙箱任务，含本次运行的出口令牌）和结果都用副本共用的密钥加密，绑定到运行编号。
  - 同一个定时任务同一时刻只能有一条「排队中 / 运行中」，由唯一索引保证，任何进程来都一样。
  - worker 用 `FOR UPDATE SKIP LOCKED` 领取，不会被别人正在领的那条卡住。
  - worker 领到后按租约持有，每 3 秒续一次。进程死了租约就过期，这次运行判为「执行节点中断」，**不再重跑**：它可能已经往飞书里写过东西，写两次比说「中断了」更糟。
  - 取消是一个标记，worker 续租时看到就停掉容器。协调副本重启时，会取消自己留下的全部任务：它们的出口令牌随旧进程没了。
  - 30 秒内没有 worker 接手，就放弃这次运行，并如实说明「没有执行节点接手」。这个时限对应出口令牌比运行时限多留的 30 秒。
- **worker**（`bin/server.js --role worker`，`src/control-plane/run-worker.js`）：
  - 只接受自己配置的镜像和出口网关，其余一律拒绝；每个任务按协调副本那边的规则重新校验一遍。
  - 在自己的目录里还原运行目录（任务说明、出口 CA 证书这两个小文件随任务一起来，不依赖共享磁盘），用和协调副本完全相同的配置起 Docker 沙箱。
  - 先清理运行目录，再回报结果。
  - 启动时检查沙箱是否可用，不可用就拒绝启动，不去领自己跑不了的任务；然后清理上次留下的容器和目录。
  - 停机时不再领新任务，已在跑的最多再等 45 秒，之后停掉。
- **开关**：`IDOU_SCHEDULE_EXECUTION=pool`，默认 `local`，也就是和以前一样由协调副本自己起沙箱。`IDOU_SCHEDULE_MAX_CONCURRENT` 在协调副本上表示所有 worker 合起来同时跑几个，在 worker 上表示它自己同时跑几个。
- **别的机器上的 worker**（`.237`，`src/control-plane/egress-relay.js`）：那台机器上的容器照样去找本机沙箱网络网关上的出口（`IDOU_SANDBOX_GATEWAY` 加出口端口）。worker 在那个地址上监听，把 TCP 字节原样转给协调副本（`IDOU_EGRESS_UPSTREAM`）。TLS 从容器一直到协调副本的出口代理，证书是协调副本那张，转发不持有任何密钥，看不到内容。协调副本另开一个内网监听（`IDOU_EGRESS_REMOTE_LISTEN`），背后是同一个出口代理，只放行 `IDOU_EGRESS_REMOTE_PEERS` 里列出的 IP，别的连接在 TLS 握手前就断开；不能监听 `0.0.0.0`。协调副本不在时，转发让那一个请求失败，自己继续服务。**还没有真的加第二台机器**：那台机器要有自己的 internal 沙箱网络和防火墙（照 `docs/server-deployment.md` 的做法），火山引擎安全组也要放行协调副本的那个端口。

测试：
- `test/run-queue.test.js`：密文存放；同一任务同时只能一条；并发领取每条恰好一次；不会被别人正在领的那条卡住；租约过期判中断、不重跑；取消；协调副本只取消自己的。
- `test/run-pool.test.js`：协调副本和 worker 之间走完一整圈。worker 只认自己的镜像和网关、守自己的并发、取消会停容器、没人接手会如实报错、worker 死掉判中断。
- `test/scheduled-pool.test.js`：用真的调度器、执行器和出口代理走一遍队列。
- `test/worker-role.test.js`：用真实进程和假 docker 验证 worker 的启动、领任务、回报、干净退出；以及 pool 模式下协调副本不需要本机 Docker。
- 去掉唯一索引、去掉 SKIP LOCKED、不查镜像、不回收死掉的 worker、听不到取消，这 5 种写法撤回验证过，测试都会失败。
- `test/egress-relay.test.js`：转发原样送达 TLS、证书是协调副本的；协调副本不在时那一个请求失败、回来后照常；只放行列出的 IP；定时任务开的内网监听背后就是出口代理本身；配置写错按名字报错。worker 进程带转发启动和退出（`test/worker-role.test.js`）。

## 2.5 的做法（9-27，进行中）

开关是 `IDOU_DATA_STORE=postgres`（需要 2.1 的共享数据库），不设就是本机文件，和以前一样。切换前停掉协调副本，用 `node bin/migrate-data.js --to postgres` 把本机数据搬进去；回退用 `--to files` 搬回来。

- **用量账本**（`.234`，`src/control-plane/model-usage.js`，表 `idou_model_usage`）：API 副本和协调副本都往一张表里记。每个进程把计数先攒在内存里，每秒合成一条语句写出去；写的顺序按键排好，两个副本同时写不会互相死锁；数据库拒绝的那一批并进下一批，不丢。
- **模型偏好**（`.239`，命名空间 `model-preference`）：一人一行，改一个人只写一行。原来的文件是每次整个重写，十万人时每点一次就是 10 MB。读仍然走内存，启动时分页读全。
- **技能登记**（`.239`）：整个货架是一条记录，按版本号比较后写入。另一个协调副本已经改过的，这边的旧副本写不进去（409），不会覆盖。
- **文档网站**（`.239`）：站点记录在命名空间 `site`，文件和快照数据在 `idou_site_files`、`idou_site_data` 两张表里，都用共享密钥加密；每个站点保留最近 3 个版本，更早的清掉。文件读过的在内存里缓存（最多 64 MB）。
- **站点登录密钥**（`.239`）：所有协调副本共用一把。第一个在数据库模式下启动的协调副本带上自己磁盘上原有的那把，所以切换时已登录的访问者不会掉线。
- **无人值守凭据**（`.239`）：封存密钥和设备密钥在库里只创建一次，所有协调副本共用；两个同时启动也只会有一对。记录按版本号比较后修改，两处同时改不会丢掉任何一处。搬迁时密钥和记录一起走：用 A 密钥封存的记录搬到 B 那边就再也打不开了，所以目标那边已有用另一把密钥封存的记录时，工具会拒绝搬迁。
- **定时任务库**（`.240`，`src/control-plane/schedule-store-postgres.js`，表 `idou_schedules`、`idou_schedule_runs`）：
  - 方法和 SQLite 版同名，规则（什么时候到期、认领做什么、校验什么）也还是 `schedule-store.js` 那一份，只换了存放的地方。
  - 任务名称、提示词、资源授权、运行正文用共享密钥加密。时间、状态、编号是明文，因为查询要按它们筛选。任务被删时，它的名称原样复制到它的运行记录上，不用解开。
  - SQLite 版在一个事务里做的事，这里也是一个事务，任务那一行 `FOR UPDATE`。所以同一次到点只会被认领一次，不管哪个协调副本来认领。新建任务时按租户加锁计数，所以同时来很多请求也不会超过上限。这两处撤回验证过：去掉锁，50 个的上限建出了 53 个；去掉 `FOR UPDATE`，同一次到点被认领了两次。
  - 启动时把每一份要调度的资源授权核对一遍，和 SQLite 版一样：核不过的暂停掉，免得一行永远启动不了的到期任务让调度器再也不设定时器。解不开的（密钥不对）拒绝启动，什么都不丢。
  - 调用方全部改成等待异步结果：调度器、服务接口、定时任务装配、出口代理。
    - 调度器读不到库（数据库重启）时，按 1、2、4……秒退避重试，最长 1 分钟一次，不会停摆。
    - 一次运行的结果写不进去时重试 3 次；仍写不进去，就留着让下次启动记为「中断」。
    - 顺带修了一个早就有的竞争：到点的运行在认领、确认身份期间没有占住位置，这时点「立即运行」会和它并排跑两份。现在占位从第一次等待之前开始，和「立即运行」一样。
    - 出口代理在流式回答期间最多每秒复查一次任务（以前是每一段都查一次库）；任务被删或暂停，最迟一秒内切断。读不到库时拒绝这次调用，报「暂时不可用」，不放行。
  - 测试：原来的 39 条行为测试现在同时跑在 SQLite 和 PostgreSQL 上（`test/schedule-store.test.js`）。另有：并发新建守住上限、库里没有明文、换错密钥拒绝启动、全部字段从文件搬到库再搬回来原样不变。调度器新增：库暂时不可用、结果晚一点写进去、在共享库上走完一整圈、认领期间「立即运行」被拒。出口新增：流式中途删除任务、读不到库。
- **云盘额度账本**（`.241`，`src/control-plane/drive-budget.js` 的 `PostgresDriveBudget`，表 `idou_drive_reservations`）：
  - 额度策略照旧来自运维的配置文件；配置文件里的 `databaseFile` 是本机账本，迁移工具从那里搬。
  - 请求要带什么、找到的记录允许什么，两种账本共用同一组函数，不会各算各的。
  - 预留一次锁住整个账本，和 SQLite 的 `BEGIN IMMEDIATE` 一样。撤回验证过：不加锁时，8 个协调副本同时各要 20 字节，预算 100 却全给了。
  - 账本里只有摘要、大小和云盘文件标识，没有要保密的内容，所以不加密，和文件版一样。
- **还没进共享库的三项**：应用目录（`IDOU_APPS_CONFIG_FILE`）、知识库协调（`IDOU_WIKI_CONFIG_FILE`）、知识库密钥（`IDOU_WIKI_KEY_CONFIG_FILE`）各有自己的本机 SQLite 账本。知识库协调还在自己的事务里同步读写云盘额度账本。服务器上三项都没开（9-27 核对过）。`IDOU_DATA_STORE=postgres` 时开着其中任何一项，服务端会点名拒绝启动，免得协调副本换了机器以后悄悄变成两份。
- **真进程测试**（`test/durable-coordinator.test.js`）：两个真实的协调副本先后连同一个库，第二个用另一台机器的 HOME。第一个建的定时任务，第二个能列出来；两台机器的磁盘上都没有任务库文件和额度账本文件。撤回验证过：不把任务库接到共享库，第二个就看不到。三项还不能共用的配置各自点名拒绝启动。
- **迁移工具**（`bin/migrate-data.js`）：
  - 只读来源，不改来源；搬完两边各读一遍，少一条就报错停下。
  - 可以重复跑，结果和跑一次一样。
  - 来源里没有数据，就不拿空集覆盖目标。
  - 本机根本没有的那份数据，搬向数据库时跳过，不在本机新建一个空的。
- **只有一个协调副本在写**：这几份数据只由协调副本读写，读在内存里。所以 2.6 的热备必须拿到锁以后才打开它们，不能提前读好了等着。

测试：`test/durable-stores.test.js`（一个协调副本写的，下一个读得到；库里没有明文；与文件版来回搬）、`test/model-usage-shared.test.js`（同一组用例跑 SQLite 和 PostgreSQL 两种实现）、`test/migrate-data.test.js`（用真实进程搬迁、重复跑、空来源、密钥冲突）。

## 2.6 的做法（9-27）

代码在 `src/control-plane/coordinator-lease.js`。只在 `IDOU_DATA_STORE=postgres` 时启用：那时第二个协调副本才是同一份数据的备用。数据还在本机文件里时，两个协调副本各管各的数据，和以前一样。

- **租约，不是锁**：共享库里一行 `idou_coordinator`，持有者每三分之一租约续一次，默认租约 30 秒（`IDOU_COORDINATOR_LEASE_SECONDS`，6 到 300）。
  - 不用 PostgreSQL 的 advisory lock，因为锁跟着连接走：一台机器突然没了，数据库要等 TCP keepalive 放弃才知道，默认两个小时。
  - 所有比较的时间都用数据库的时钟，两台机器的时钟从不相比。
- **不会两个同时工作**：
  - 备用的只在租约被交还、或按数据库时钟已经过期后才能接手。
  - 持有者续不上时，在租约到期前自己退出。它按本机单调时钟、从上次发出续期请求时算起，由一个独立于续期请求的看门狗检查，所以一次卡住不返回的续期也拖不过去。
  - 撤回验证过：去掉看门狗，数据库不响应时持有者一直不退出。
  - 续期时发现租约被别人拿走，立即退出。进程退出后 systemd 会重启它，它就成了备用。
- **备用**：启动到打开共享库为止，拿不到租约就待命。它不打开任何持久数据，不监听任何端口（网关、文档网站、出口代理、指标都不监听），每 2 秒看一次；收到 SIGTERM 直接退出。接手后照正常启动：从库里读数据，把上一个协调副本留下的运行标为中断，取消它放进执行池的任务。执行池里的任务归属改成固定的「coordinator」，不再按目录算，所以换了机器也认得。
- **交还**：正常停止时，先关掉所有监听和定时任务，最后交还租约，备用在下一次查看时（2 秒内）接手。启动到一半失败（比如配置文件不存在）也会交还，下一次启动不用等自己的旧租约过期。
- **迁移工具**：有协调副本持有租约时拒绝运行，并说出是哪一个。
- **两台机器怎么摆**：协调副本只监听本机回环，由本机 nginx 转发。第二台机器上放同样的一套（nginx + 协调副本备用 + API 副本），前面用火山引擎负载均衡按 `/healthz` 做健康检查。备用不监听端口，那台机器的 nginx 就回 502，负载均衡不会把请求发过去；接手后健康检查转绿，原来那台的 nginx 变 502。不需要把协调副本暴露到内网。还没做：第二台机器、负载均衡、以及那台机器上的沙箱网络和防火墙（见第 3 步「别的机器上的 worker」）。

测试：
- `test/coordinator-lease.test.js`（租约 1.5 秒，真实 PostgreSQL）：
  - 持有和交还；
  - 冻住的持有者，租约过期后被接手，它自己一运行就退出；
  - 被拿走后下一次续期就发现；
  - 数据库拒绝或不响应时，持有者都在租约过期前退出，而且接手严格发生在退出之后；
  - 待命可以被停止。
- `test/durable-coordinator.test.js`（真进程）：

  - 第一个停下后，第二个接手并列出第一个建的任务；
  - 租约被拿走的协调副本立即退出；
  - 启动失败的协调副本交还租约，下一个马上拿到。
