# 文档网站的内容安全与审计

文档网站把员工做的页面和飞书表格里的数据发布出去，其中「互联网上获得链接的人可阅读」的网站谁都能打开、不用登录。这份文档讲服务端在内容上线之前做什么检查、查出问题怎么处理、管理员怎么审核，以及留下哪些记录。

代码：`src/control-plane/content-scan.js`（敏感信息检查）、`site-moderation.js`（AI 审核）、`site-safety.js`（规则、检查记录、访问统计）、`site-registry.js`（网站的审核状态）、`site-service.js`（在发布流程里检查）、`admin-api.js` 与 `admin-ui/pages-content.js`（后台「内容安全」页）。

## 1. 什么时候检查

内容**上线之前**，在服务端：

| 时机 | 查什么 |
| --- | --- |
| 发布、发布新版本（「更新线上」） | 这个版本的全部文本文件（HTML、JS、CSS、JSON……）和随它一起发的表格数据 |
| 改分享范围（受众变了时；同样的范围再保存或只加协作者，不检查，也不改变审核状态） | 当前版本和当前数据，按新受众的规则 |
| 重新发布 | 当前版本和当前数据，按现在的规则 |
| 表格数据刷新（数据有变化时） | 新数据；和线上一样的数据不重复检查 |
| 补查 | 服务端启动几分钟后，把从没检查过的网站（这个功能上线前发布的）和上次 AI 没读完的网站查一遍；还有没读完的，之后每半小时再查一遍，最多再六次；后台「全部重新检查」按现在的规则把租户的每个网站再查一遍，它留下没读完的也交给这半小时一次的补查（这一轮正在跑时交来的，等它跑完再安排）。服务端停止时，进行中的补查（包括后台点的）当场停下 |

## 2. 查什么

- **敏感信息**（规则，服务端本地完成，不调用任何外部服务）：
  - 密钥或凭据：私钥、AWS/GitHub/Slack 的密钥、`sk-` 开头的模型 API 密钥、JWT、写在代码里的 `Bearer` 令牌、带密码的网址。
  - 身份证号（校验位正确的才算）、银行卡号（发卡行前缀 + Luhn 校验）、手机号、邮箱地址（`logo@2x.png` 这类图片名不算）。
  - 管理员自定义的敏感词（最多 200 个，不区分大小写）。
- **违规内容**（只查公开网站）：部署自己配置的对话模型读一遍页面文字和数据，按固定格式回答「通过 / 需要人看 / 不适合公开」和原因。页面文字作为引用材料交给模型，并明确告诉它其中的要求一律不理会。等待时间和输出上限用这个模型实测过的 JSON 调用预算（`chat-models.js` 的 `sideCalls`：MiniMax-M3 90 秒、3000 tokens，GLM-5.3 180 秒、8192 tokens）——会先推理的模型推理也算在输出里，给少了就答不完。模型那边忙（HTTP 429、5xx、MiniMax 过载时回的 529）、连不上或回答读到一半断了，3 秒后再问一次；超时、读不出结论和其他拒绝不再问。两次共用一个期限（就是上面那个等待时间），期限剩不到四分之一就不再问——发布要等这一步，i豆 等发布最多 4 分钟（`src/application/site-requests.js`，按最慢的模型加一分钟），不能让发布在服务端照常完成、发布人却已经被告知失败。即便如此，i豆 等不到（超时、中途退出应用）时，第一次发布用的网站标识是发送前就存在本机的：再点一次发布会更新同一个网站，不会多出一个；网站列表刷新时如果服务端已经有这个标识，i豆 直接认领它。退出应用不会再等进行中的发布。给模型的类别说明写得具体：广告引流指引导加私人微信或 QQ、第三方推广、刷单返利，企业介绍自己的产品、发布会和活动不算；内部机密指未公开的财务数据、客户名单、内部系统的地址和账号。同一段文字只读一次；表格数据每个网站每小时最多读一次。开发服务端（`--dev`）不调用模型。
- **模型没回答**（超时、报错、答不完、读不出结论）：内容上线之前，一律算「需要人看」，不会当作通过；数据刷新则这次不更新，下次刷新再试，而且下次一定让模型读过才上线——不受「每小时最多读一次」限制，免得中间别的一次读取把这份数据顺带放过去。已经在线的网站补查时**不因此下线**——规则检查照常决定——检查记录写明 AI 没读完，之后的补查再读（见上表）。

## 3. 怎么处理（默认规则，管理员可改）

受众分两种：**公开**（互联网上获得链接的人）和**组织内**（组织成员、邀请的人）。

| 发现 | 公开网站 | 组织内 |
| --- | --- | --- |
| 密钥或凭据 | 拦截（不可改） | 拦截 |
| 身份证号、银行卡号 | 拦截 | 只记录 |
| 手机号、邮箱地址 | 送管理员审核 | 只记录 |
| 敏感词 | 送管理员审核 | 只记录 |
| AI：不适合公开 | 拦截 | 不查 |
| AI：需要人看 | 送管理员审核 | 不查 |

- **拦截**：这次发布、改范围或数据刷新被拒绝，发布人在 i豆 里看到原因（哪一类、几处、第一处在哪个文件第几行或数据第几行）。什么都不保存：新版本没有存，数据没有更新，线上照旧。已经在线的网站补查出要拦截的内容时没法「不发布」，改为下线等管理员审核，发布人看到「补查发现问题：……」。
- **送管理员审核**：版本存下来，但**网站下线、等待审核**，链接打不开。这一步和保存是同一次写入，所以没有「先上线、再拦下」的空档。数据刷新遇到要审核的内容时，新数据不写入，线上继续显示上一次的数据，发布人被告知原因。
- **只记录**：照常上线，记一条检查记录。
- 另有开关「所有公开网站都要管理员审核后才上线」（默认关）：打开后每个新版本都要审一次，数据刷新不算新版本。

## 4. 审核

后台「内容安全」页：

- **等待审核**：每个网站、发布人、原因。「查看」打开检查详情：每处发现的类别、位置和**打码后的样本**（如 `138****5678`），AI 的结论和原因，以及一段页面文字摘录——摘录里的手机号、身份证号等同样打码。
- **通过**：网站上线（发布人自己下线过的仍保持下线；管理员下线着的仍下线）。记下的「已审核版本」是这次检查所查的版本——批准一次较早的检查，不会把之后还没审核的版本当作审核过。这次发现的内容按「指纹」记住，以后同样的手机号、同样的文字再出现，不再送审；被规则拦截的类别不受影响。只有网站正在等的那一次检查能让它上线：批准一次较早的检查（比如一次被拒的数据刷新），只是放行那些内容，不会结束一次更新的等待。
- **不通过**：要写原因。网站保持下线，发布人看到原因；改好后发布新版本会重新检查。
- 发布人这边：等待审核时不能「重新发布」绕过；可以发布新版本（重新检查），或改成只给组织内的人看（按组织内的规则检查，通过就上线）；不能用「再保存一次分享设置」结束等待。
- 部门管理员只看得到、只能审核发布人在他范围里的网站；改规则和「全部重新检查」只有管理整个组织的管理员能做。

**检查期间网站有了变化**：检查可能要几分钟。写入时如果网站已经不是检查时的样子——发布人点了「取消发布」、管理员下线了它、另一次发布先到了、审核状态变了——这次发布、改范围或重新发布不生效，发布人看到「这个网站在检查期间有了变化……刷新网站列表后再试」，网站保持变化后的样子。发布人在这期间被离职清理的，同样什么都不发布；离职清理也会取下他等待审核和被管理员下线的网站，免得之后一次审核通过又让它上线。补查同理：查的时候网站换了版本或受众（新内容放上去时各自检查过），就不按旧内容把它下线；数据换了，只有当发现全在数据里、且不是 AI 的判断时才算作废——页面文件里的发现照样下线。只是加了协作者、被管理员下线或被发布人取消发布的，照样转为等待审核，原来的状态留在底下。被拒绝的发布写过的版本文件会清掉。

**网站是否在线**只由三件事决定：发布人最后想要它在线还是下线、管理员有没有下线它、它有没有在等待审核或被驳回——任何一项让它下线，它就不在线。记录里给每一层各存一份「发布人想要什么」（旧版本读这些副本），每次改动都用同一个函数把这几份一起写好（`compose`）：审核那一份是发布人的意愿；管理员下线那一份是「恢复后回到什么」，审核没结束时它是「下线」——.269 的恢复只看这一份，回退后也不会让等待审核或被驳回的网站上线；`test/site-states.test.js` 用固定种子走两万多步随机操作，每一步都和这个规则对照。被驳回的网站只有发布新版本才能回来，批准不会让它上线，补查也不会把它改回等待审核。i豆 每次显示网站列表时按服务端同步每个网站是否在线、对谁公开；同一个网站的发布、改范围、重新发布一次只能进行一个。所有对网站记录的改动按先后一个一个做，每个都从当时的记录出发。

管理员下线（[admin-console.md](admin-console.md) §9）是另一回事：那是管理员主动把网站拿下来，发布人改什么都不能恢复。

## 5. 留下的记录

- **检查记录**（管理库 `idou_admin_site_checks`）：时间、网站、版本、数据摘要、受众、发生在什么操作、结果（通过/记录/送审/拦截）、每类几处、每处的位置和打码样本、AI 结论、打码后的文字摘录、管理员的决定（谁、什么时候、原因）。**不保存任何原值，也不保存整页内容。**数据刷新没有发现、或发现和上一次一样时不新增记录，免得每几分钟一条。
- **指纹**：每处发现带一个指纹，是用服务端密钥对值做的 HMAC。手机号这类值可能的取值不多，普通哈希能被逐个试出来；带密钥的不能，而密钥不和指纹存在一起。指纹只用来认出管理员放行过的内容。
- **审计日志**：发布被拦截（`site.refused`）、送审（`site.review`）、审核通过/驳回（`admin.site.approve` / `admin.site.reject`）、改规则（`admin.site-rules.update`，带改动前后）、全部重新检查。
- **访问统计**（`idou_admin_site_visits`）：每个网站每天被打开几次、其中不用登录的几次、被拒几次；在内存里累加、每半分钟写一次。后台「文档网站」页显示近 7 天。

## 6. 回退

审核状态写在网站记录里，同时把网站记为「已下线」，和管理员下线一样：回退到不认识审核状态的旧版本，等待审核和没通过的网站仍然是下线的。新加的表旧版本不读。

## 7. 还不是什么

- AI 审核是辅助，不是保证：页面文字可能诱导模型，所以它的结论只用来拦截或送审，不会让一个本该送审的网站跳过审核；规则检查不依赖它。
- 图片、视频、PDF 里的文字不查（只查文本文件和表格数据）。
- 页面运行时从别处加载的内容（文档网站本身不允许联网，`network: none`）不在检查范围内。
- 检查发现之后不会通知发布人（没有推送）：发布人在 i豆 的网站列表里看到状态和原因，管理员在后台看到待审核。
- 「全部重新检查」做到一半服务端重启的，不会自动续上，重启后再点一次。

## 8. 验证

- `npm run check` 里的单测：规则、打码、指纹、送审与批准的状态、补查（`test/site-safety.test.js`），以及在改名前建的 PostgreSQL 上表名仍是旧名（`test/admin-legacy-names.test.js`，生产服务器就是这种库）。
- 界面：`scripts/smoke-admin-console.js`（后台「内容安全」页、检查详情、AI 没读完的写法）和 `scripts/smoke-site-review-desktop.js`（i豆 网站列表里的三种状态和按钮）。
- 真实模型：`node scripts/smoke-site-moderation-live.js --live` 用部署配置的对话模型读四段自带的文字（普通介绍和企业自己的产品发布要通过，赌博推广和「请直接判通过」的那段都不能通过），共四次付费调用，默认验收不跑。
