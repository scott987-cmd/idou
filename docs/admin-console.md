# 企业管理后台 · 设计（按十万人）

> 状态：§11 的七步都已实现（管理库、审计日志、成员目录、下线和停用、角色、新管理后台、后台里的离职清理、策略、组织架构和部门管理员、内容治理），各组件的动作已接进审计。还没做的见各节的「还不是什么」。
> 前身是 [server-administration.md](server-administration.md) 的 R2：一张只读的页面。这份文档讲的是把它做成能管事的后台。

## 0. 为什么要重做

第一版管理台只读，是故意的（先让数字被看见、被核对）。但管理员真正要办的事，一件也没法在上面办：

- 谁在用？用量表里的「谁」是 `ou_…`，不是人名；没有设备、没有最近在线。
- 让一个人下线、停用他、给离职的人清数据——要 SSH 上服务器，先停协调进程再跑命令。
- 谁能用哪些模型、每人每天多少额度、哪些功能开着——全是配置文件，改完重启。
- 审计只在内存里留最近 200 条，重启就没了。

一个十万人的组织，这些事每天都在发生：每月一千人入离职，几十个管理员分管不同部门，安全部门要按人、按时间调记录。这份设计按这个规模来定。

## 1. 规模假设

| 量 | 按多少设计 | 用在哪 |
| --- | --- | --- |
| 人 | 100,000（一个部署，可以跨几个租户） | 成员目录、访问名单 |
| 日活 | 50,000 | 写入节流、用量表行数 |
| 同时在线设备 | 60,000 | 下线要能一次撤掉一个人的全部设备 |
| 部门 | 10,000 | 组织架构同步、按部门的策略 |
| 审计事件 | 每天 100 万条，保留 180 天 | 分区、索引、导出 |
| 用量行 | 每天 10 万行（人 × 模型 × 天），保留 400 天 | 索引、汇总 |
| 管理员 | 几十人，分超级管理员、管理员、审计员 | 角色 |

由此来的几条硬要求：

1. **列表全部在服务端分页**，用游标（按排序键往后翻），不用 OFFSET——翻到第 2000 页和第 1 页一样快。
2. **每个查询都有索引撑着**，并且有查询计划测试守住（SQLite 从不 ANALYZE，跨表 OR 会退化成全表扫描，见 `test/` 里的查询计划测试）。
3. **每个请求上的检查是 O(1)**：停用名单、策略都常驻内存，变动由数据库通知推到每个进程，不是每个请求去查库。
4. **写入要节流、要成批**：在线状态最多 10 分钟写一次，审计成批落库。
5. **导出是流**：一个月的审计可能上千万行，边查边写给浏览器，不在内存里攒。

## 2. 架构

```
浏览器（管理员）
   │  https://<IDOU_ADMIN_URL>   飞书登录 → 管理台 cookie
   ▼
管理台监听（协调副本里，自己的端口和来源）
   ├─ /admin            页面外壳（静态 HTML/JS/CSS，无外部资源）
   ├─ /admin/api/…      JSON 接口：每个请求重新判定角色；写请求要 CSRF 令牌 + 同源
   └─ /_auth/…          飞书登录回调
        │
        ├─ 成员目录、访问名单、角色、策略、审计 ──► 管理库（有共享数据库时在 PostgreSQL，没有时是本机 SQLite）
        ├─ 会话（撤销）、用量账本、网站登记、定时任务……  ──► 已有的存储，由各自的服务改
        └─ 变动通知（LISTEN/NOTIFY）──► 每个模型副本、协调副本里的内存副本
```

- **管理库一份代码，两种数据库。** 写一套 SQL，经一个很薄的适配层（`admin-db.js`）在 SQLite 和 PostgreSQL 上都跑；只有建表、分区、通知是各写各的。表名按 `database-names.js` 的规矩写 `idou_admin_*`，旧库里自动叫 `mydoubao_admin_*`。
- **有共享数据库就放共享数据库。** 模型副本要知道谁被停用、谁能用哪个模型，所以只要配了 `IDOU_DATABASE_URL`，管理库就在那里——不管 `IDOU_DATA_STORE` 设没设。单进程、没有数据库的部署放 `<数据目录>/admin.sqlite`。
- **管理台不碰别人的数据库存储。** 撤会话走 `SessionRegistry`，下线网站走网站登记，删定时任务走定时任务的存储——和桌面端改它们走的是同一条路，所以缓存、通知、额度归还都不会漏。

## 3. 角色与权限

| 角色 | 从哪来 | 能做什么 |
| --- | --- | --- |
| 超级管理员 | `IDOU_ADMIN_USERS`（逃生口，改要重启）；或在后台被授予 | 全部，包括授予和收回角色、改策略 |
| 管理员 | `IDOU_ADMIN_CHAT` 群里的人；或在后台被授予 | 管成员（下线、停用、离职清理）、改策略、管内容 |
| 审计员 | 在后台被授予 | 只读全部页面，导出审计和用量；不能改任何东西 |
| 部门管理员、部门审计员 | 在后台授予管理员或审计员时选了部门（最多 20 个） | 同上，但只对这些部门和下级部门里的人：见下面「管理范围」 |

- **每个请求重新判定**，判定结果最多缓存 60 秒（群成员本来就缓存 60 秒）。在飞书里把人移出管理员群，一分钟内生效。
- **按租户隔离**：管理员只看得见自己租户的人、用量和审计。部署级的信息（服务状态、模型、版本）所有管理员都看得见。
- **不能把自己锁在外面**：不能停用自己、不能收回自己的超级管理员；配置文件里的超级管理员在后台里收不回。

### 管理范围（部门管理员）

一个十万人的组织，几十个管理员分管不同部门。授予管理员或审计员时可以选部门，他就只管这些部门和下级部门里的人；不选就是整个组织。超级管理员、配置文件里的超级管理员、管理员群里的人永远是整个组织（群里的人同时被授予了限定部门的角色，按群算，整个组织）。

- **一处判定**：后台接口的每一条路由都声明自己对限定范围的管理员怎么做——与人无关（`any`：部门树、搜部门、管理员名单）、按范围收窄或拒绝（`scoped`）、只有整个组织的管理员能做（`tenant`：用量、服务状态、组织同步、授予角色）。分发处统一检查，测试逐条路由各发一个请求，新加的路由没说明就会失败。
- **按范围收窄**：成员列表和搜索、概览、待清理、审计（他管的人做的和被做的，加上他自己做的）、文档网站（发布人在范围里的）；成员详情、下线、停用、恢复、离职清理、策略的「试一试」对范围外的人一律拒绝；批量操作把范围外的人挑出来、不处理、告诉他。
- **策略**：他看得见对所有人、对群的规则和对他的部门（及上级部门）、他的人的规则，只能改他的部门和他的人的规则。
- **范围按通讯录算**：一个人在不在范围里，看组织架构同步记下的他所在的部门（含上级）。通讯录里没有的人不在任何人的范围里；授予的部门后来在飞书里撤销了，那部分范围就是空的。没开通讯录权限时，限定了部门的管理员什么人都看不到——宁可看不到，不能看多了。
- 十万人合成数据实测（SQLite）：管一个三万三千人的中心的部门管理员，成员第一页 29 毫秒、搜索 33 毫秒、审计 20 毫秒、概览 96 毫秒、组织架构 33 毫秒。

## 4. 成员目录

**记下谁用过。** 一个人在桌面端登录、恢复登录、续期时，协调副本把他记进目录：租户、open_id、名字（登录时飞书返回的，不需要额外权限）、第一次和最近一次在线、桌面版本。

- 最近在线最多 10 分钟写一次，成批写；十万人同时在线时约每秒几十行。
- 名字以最近一次登录为准。改了名，下次登录就更新。
- 搜索：名字包含、open_id 精确。十万行的「包含」查询要扫一遍名字列，PostgreSQL 上约十几毫秒，可以接受；不引入额外扩展。
- 排序：最近在线、名字、第一次使用，都有索引。

**一个人的详情页**：基本信息、状态、在线设备数、近 30 天用量（按模型、按天）、定时任务个数和状态、发布的网站、无人值守授权、这个人最近的审计记录。**不显示任何对话、提示词、任务内容**——这些数据本来就不在管理台能拿到的地方。

## 5. 下线、停用、离职清理

| 动作 | 含义 | 怎么生效 |
| --- | --- | --- |
| 下线 | 这个人所有设备立刻退出，要重新扫码登录 | 撤掉他在共享库里的全部会话（通知传到每个副本）；记一个「下线时间」，在它之前签发的会话和恢复凭据一律不认 |
| 停用 | 这个人不能再用 i豆，直到恢复 | 下线 + 停用标记：登录、恢复登录、续期、无人值守授权、文档网站访问都拒绝 |
| 恢复 | 撤销停用 | 去掉标记，他自己重新登录 |
| 离职清理 | 清掉他在服务端的数据 | 先停用，再按 server-administration.md §6.5 的表删除；在后台里先列出要删什么，输入他的名字确认后才删 |

- **为什么要「下线时间」**：桌面端存着恢复凭据（里面是飞书刷新令牌），只撤会话的话，它下次启动会用凭据自己登回来。所以恢复凭据从这一版起带上签发时间，下线时间之前签发的一律拒绝；以前签发的没有这个时间，按最早算。
- **停用的检查在会话层统一做**：`SessionRegistry.verify` 认会话之前先问访问名单，所以模型网关、飞书代理、定时任务、媒体……每个入口都挡住了，不用一个个加。签发会话（登录、恢复、续期、无人值守）也在同一处拒绝。
- **桌面端怎么说**：服务端拒绝时带 `account_disabled`，新版桌面显示「你的 i豆 账号已被管理员停用，请联系管理员」；旧版桌面显示带这个代码的通用提示。
- **离职清理在后台里不用停协调进程**：命令行版要停，是因为它绕过了内存里的网站登记和模型偏好；后台里的清理走这些服务自己的删除方法，内存和存储一起改。

## 6. 审计日志

**记什么**：谁、什么时候、对什么、做了什么、结果如何。分几类：

| 类 | 例子 |
| --- | --- |
| 管理 | 停用、恢复、下线、离职清理、授予角色、改策略、下线网站（改动前后的值都记） |
| 登录 | 登录、恢复登录、退出、被拒（停用、租户不在名单） |
| 飞书 | Agent 写文档、发消息、删除、上传（动作和对象 id，不记内容） |
| 定时任务 | 新建、删除、运行结果、无人值守授权的授予和撤销 |
| 网站 | 发布、取消发布、免登录链接 |
| 媒体 | 生成图片、视频 |

**不记什么**：提示词、回答、消息正文、文档内容、工具参数。审计是给管理员追责用的，不是第二份对话记录。

**存储**：
- PostgreSQL 上按天分区（`PARTITION BY RANGE (at)`），保留期过了整块删分区，不留膨胀；SQLite 上一张表，分批删。保留期 `IDOU_AUDIT_RETENTION_DAYS`，默认 180。
- 索引：按时间、按操作人、按类别、按对象，都带租户前缀。
- 写：成批落库（每秒或每 500 条一次）；管理员自己的操作同步落库再返回。库暂时不可用时在内存里攒，满了丢最旧的并计数；每条事件同时还是 stderr 上的一行 JSON，运维的日志收集是第二份。
- **管理员删不掉审计**：后台没有这个接口。
- 查询：时间范围必选（默认最近 7 天），可以按人、类别、对象、结果筛；游标翻页。
- 导出：CSV（带 BOM，Excel 直接打开），一次最多 31 天，边查边写。

## 7. 策略（模型、额度、功能开关）

**一条策略**：对谁（所有人 / 某个部门及其下级 / 某个群 / 某个人）设什么：

- 模型：能用哪些、默认哪个；
- 额度：每天多少 token、超了换哪个模型、并发上限（R4 设计的软上限）；
- 功能：定时任务、无人值守、发布网站、免登录链接、图片、视频、连接器、Agent 写飞书（文档 / 消息 / 云盘 / 删除，分开开关）。

**谁说了算**：配置文件定上限，后台在上限内调。配置文件里没开的功能、没配的模型，后台开不了；后台能把它们对某些人关掉。回退到旧版本时，按配置文件生效。

**判定**：越具体越优先，个人 > 群 > 部门（近的部门优先于远的）> 所有人；同一层多条命中时，功能取「都允许才允许」，模型取交集，额度取最小。每个人的结果缓存在每个进程里，策略一变就整体作废重算。

**都在服务端执行**：模型和额度在模型网关；功能开关在各自的服务（定时任务服务、网站服务、媒体服务、飞书代理）。桌面端读自己的生效策略，把关掉的入口藏起来——但藏只是体验，挡是服务端挡的。

「完全访问」是桌面端的授权方式，服务端看不出一次写入是人点的卡片还是完全访问自动放行的。所以这个开关由桌面端执行，后台页面上如实这么写；服务端能做的硬限制是把对应的写入类别整个关掉。

### 已经是什么（第 5 步）

- `policy.js`：规则存在管理库（`idou_admin_policies`），对所有人 / 群 / 某个人（部门在第 6 步）；`IDOU_MODEL_POLICY_FILE` 的规则照旧生效，在后台显示为只读。改动几秒内所有进程生效（管理库的通知），每人的生效结果缓存一分钟、任何改动立刻作废。
- 执行点：模型网关（能用的模型、默认模型、每天额度——超了换到指定模型并在响应头 `x-idou-quota: downgraded` 说明，没指定就以 `quota_exhausted` 拒绝——以及每人同时进行的请求数）；飞书写入代理（文档 / 消息 / 云盘 / 删除，四类分开，拒绝也进审计）；定时任务（新建、立即运行、每次到点运行、无人值守授权）；网站发布和免登录链接；图片、视频生成。
- 额度按「人 + 天（UTC）」计：每个副本从用量账本读一次今天的数，之后自己累加，最多十分钟重读一次；一个人固定落在一个副本上，所以这个数就是他的。
- 桌面端每五分钟问一次 `/v1/policy`：「完全访问」被收回时，菜单里这一项变灰、不能再选、不能用它新建任务；已经是完全访问的任务，确认卡片立刻回来，下一轮按标准模式（有沙箱、先问）跑。
- 后台「策略」页：按层列出规则，新建 / 修改 / 删除（每次进审计，带改动前后）；「试一试」选一个人，逐项给出他实际得到什么、由哪条规则决定。

### 还不是什么

- 大群（超过 5000 人）读不全成员，按群的规则对后面的人不生效；十万人的组织应当按部门设规则（第 6 步）。
- 额度用完后的降级，桌面端还不会主动提示「今天额度用完了，现在用的是 X」：响应头里有，界面还没读。

## 8. 组织架构

按部门管理要读飞书通讯录，用应用自己的身份（不是任何管理员的）。应用要有：

| 权限 | 名字 | 用来 |
| --- | --- | --- |
| `contact:contact.base:readonly` | 获取通讯录基本信息 | 读部门树和人员 |
| `contact:user.base:readonly` | 获取用户基本信息 | 人员的在职状态 |
| `contact:user.department:readonly` | 获取用户组织架构信息 | 人在哪些部门 |
| `contact:department.base:readonly` | 获取部门基础信息 | 部门名字和上下级 |

还要把应用的「通讯录权限范围」设成全部成员（或要管理的那些部门），发布新版本。飞书开发者后台改版后它不再是单独一栏：在「开发配置 → 权限管理」的 API 权限列表里，通讯录权限那一行的「可访问的数据范围」列点「配置」（飞书文档 contact-v3「权限范围资源介绍」）；改完要创建版本、企业管理员审核通过才生效。没开通时飞书回 HTTP 400、错误码 99991672；后台的「组织架构」页照实显示缺哪几项、去哪里开，不假装有一个空的组织。权限开了但字段被飞书省掉（比如缺人员部门那一项，飞书不报错，只是不给 `department_ids`）时，也照实说缺哪一项。

同步先读应用的通讯录权限范围（`/contact/v3/scopes`）。范围是全部成员时飞书并不明说：它返回的是根部门下的一级部门和直属成员，不含根部门（飞书文档；2026-10-05 在一个只有 2 人、没有部门的组织上实测是「0 个部门、2 个人」），所以没看到根部门时再读一次根部门，读得到就是全部成员（部分范围时飞书拒绝，40004）。范围是全部成员，就从根部门往下读；只是部分部门，就逐个读这些部门和它们下面的部门，后台显示「通讯录权限范围：N 个部门、M 个人（不是全部成员）」并说明怎么扩大，范围外的人不核对、不会因此停用。范围不包含要读的部门时飞书回 **HTTP 403、错误码 40004**（no dept authority，2026-10-02 在服务器上实测：开了权限、范围只有一个人），后台显示「通讯录范围不够」和改法，不是一行看不懂的报错。

- **同步**（`org-sync.js`，协调进程里跑）：启动两分钟后一次，之后每天一次，后台可以「立即同步」。部门树一次分页读完（`departments/0/children?fetch_child=true`），十万人的组织约一万个部门；用过 i豆 的人每 50 个一批查部门和在职状态（`users/batch`），十万人约 2000 次调用，每秒最多 10 次，几分钟。一次只跑一个。
- **存在哪里**（`org-directory.js`）：部门按从根开始的路径存（`/od-a/od-b/`），「这个部门和下面所有部门」是一次前缀查询；人只存用过 i豆 的，只存在职状态和所在部门。
- **按部门筛成员**：成员页可以按部门（含下级）筛。十万人实测：一个中心（两万人）30 毫秒，含统计人数；一个小组 3 毫秒。
- **按部门设策略**：部门规则对这个部门和下面所有部门的人生效；一个人同时在几个部门时，最近的那一级说了算，同样近的几条规则取最谨慎的组合（功能都得允许、模型取交集、额度取最小）。层级是：某个人 > 群 > 部门（由近到远）> 所有人。
- **离职**：飞书显示离职（`status.is_resigned`）的人，同步时自动停用，审计里记操作人是「组织架构同步」。管理员之后在成员页把他恢复的，同步不再停用他——管理员说了算；他回来上班再离职，算新的一次离职。
- **待清理**：自动停用只是挡住登录，数据还在。离职的人进「待清理」，按离职先后排，清理完就离开这个列表、进「最近清理」。可以勾选一批一起清理：先汇总这一批要删多少定时任务、授权、网站，输入人数确认；一次最多 50 人（每人要动每个存数据的服务，一批在几秒内做完），一个人失败不影响其他人，失败的留在列表里可以重试，每个人一条审计。
- **不在通讯录权限范围里的人**不会被当成离职：飞书不回答，就记作「没有核对」，不停用。

## 9. 内容治理

- **文档网站**（「文档网站」页）：按名字、状态（在线、公开、管理员下线、发布人下线）、发布人筛。管理员可以**下线**一个网站，要写原因：链接立刻失效，正在看的页面断开，文件保留；发布人不能自己重新发布、改共享范围、发新版本或删除它，想这么做时看到的就是那个原因。**恢复**回到下线前的状态（发布人自己下线过的仍然下线）。下线时网站同时记为「已下线」，所以回退到不认识「管理员下线」的旧版本，它也仍然是下线的。
- **定时任务**（「定时任务」页）：全租户有多少任务、多少在运行、暂停、挂起；按人列出各有几个任务、下次什么时候跑、最近 24 小时完成和失败几次、有没有无人值守授权。**看不到任务的标题和提示词**：给后台的查询只取计数和状态。
  - **停止某人的定时任务**：在他自己的策略规则里把「定时任务」关掉——调度器每次运行前本来就问策略，他也不能新建；任务和记录不删。**允许**就是把这一项从他的规则里去掉。所以它在「策略」页可见、和其他规则一起生效，不是另一个开关。
  - **撤销某人的无人值守授权**：删掉他留给服务端的长期飞书凭据，正在用它跑的那次立刻停止。飞书那边给应用的授权不受影响，要由他自己在飞书「设置 - 应用授权」里撤销。
- **内容安全**（「内容安全」页）：文档网站每次发布、改分享范围、刷新数据之前，服务端检查敏感信息（密钥、身份证号、银行卡号、手机号、邮箱、敏感词），公开网站的文字再由 AI 读一遍；按规则拦截、送管理员审核或记录，管理员在这里审核、改规则。见 [site-content-safety.md](site-content-safety.md)。
- **企业技能**（「企业技能」页和每个技能的详情页，[enterprise-skill-governance.md](enterprise-skill-governance.md)）：上架前审核（默认开；看全部文件、与线上版本逐行的差别、所需工具意味着什么，再通过或写原因驳回）、谁能上架（服务器配置的之外，在后台加减）、每个技能保留最近 5 个上线过的版本并可回到其中一个、按部门限定谁能看见、近 30 天多少人用了多少次、对这个技能做过的每件事；可以**下架**（写原因，进审计）。技能包仍由上架人在桌面端提交，因为技能包在那里。
- 部门管理员：网站、定时任务按发布人、负责人是否在其范围里收窄，范围外的一律拒绝；企业技能是整个租户的，只有管理整个组织的管理员能看能改。

## 10. 安全

- 管理台有自己的来源和自己的 cookie（见 server-administration.md §4.2），cookie 8 小时过期。
- 写请求：只收 JSON；`Origin` 必须是管理台自己；带 CSRF 令牌（由 cookie 派生，页面从 `/admin/api/me` 拿）。
- 危险操作要确认：离职清理、收回角色输入对方名字，批量离职清理输入人数；下线网站必须写原因（发布人会看到）。每一次写都进审计，带操作人、来源地址、改动前后。
- 限定了部门的管理员，每条接口都在分发处按路由声明的范围检查（§3「管理范围」），不靠各页面自己记得。
- 每个管理员每秒最多 20 个请求。
- 页面只加载自己的脚本和样式（CSP `default-src 'self'`），不连任何外部地址；头像用名字首字，不从飞书 CDN 拉图。
- **管理台看不到对话内容**，靠的是它拿不到：用量表、审计表、目录表里都没有那些列，单测断言列名集合。

### 已经是什么（第 1–3 步）

- 代码：`admin-db.js`（一套 SQL 两种库）、`audit-log.js`、`audit-trail.js`（各组件的事件 → 审计行）、`people-directory.js`、`access-list.js`、`admin-roles.js`、`admin-server.js`、`admin-api.js`、`admin-ui/`（不依赖任何外部资源的页面）、`usage-reports.js`（过去的日子加总一次存进汇总表）。
- 停用和下线在会话层执行：`SessionRegistry.verify` 和签发都先问访问名单；恢复登录在花掉飞书刷新令牌之前就拒绝；无人值守运行在花令牌之前拒绝并暂停任务；网站访客同样拒绝。恢复凭据从这一版起带签发时间。
- 审计里有：管理员的每个动作（同步落库）、登录 / 恢复登录 / 退出和它们的拒绝、Agent 写飞书（写入、发消息、删除、上传，带对象 id）、定时任务的增删改和每次运行的结果、无人值守授权、网站发布和下线、图片视频生成。
- 十万人合成数据实测（`node scripts/smoke-admin-console.js --people 100000`，SQLite）：十万人、59 万行用量、30 万条审计，每个列表在缓存热了以后 34 毫秒以内（成员第一页约 3 毫秒、审计查询 0.2 毫秒）；第一次打开时冷读文件 0.2–0.4 秒，用量页第一次要把 30 天逐天加总约 0.9 秒，之后 26 毫秒。

### 还不是什么

- 离职清理（第 4 步）已在后台：先列出要删、要下线、要保留什么，输入对方名字确认；先停用、停下他正在跑的任务、结束他的所有会话，再通过内存里持有数据的那些服务删除（`person-data.js` 的 `offboardLive`），所以不用停协调进程。命令行版（`bin/forget-person.js`）照旧可用。
- 部门管理员看不到用量页：用量的汇总表在用量自己的库里，不能和部门做联查（SQLite 上是另一个文件）。
- 审计按范围收窄只看操作人和对象：对部门规则的改动，对象是部门不是人，部门管理员只看得见自己做的那些。
- 命令行版的离职清理（`bin/forget-person.js`）不会把人从「待清理」里拿掉，因为它不碰管理库；在后台清理的会。
- 桌面端的网站列表还不会标出「管理员下线」和原因：现在的桌面版只把它当作已下线，发布人要重新发布时才从拒绝里看到原因。
- 定时任务页只列有任务的人，按 open_id 排，不能按失败次数排序：失败最多的人要翻页找；部门管理员的范围大时，一页可能不满 50 人（按负责人逐页取、再按范围筛，每次最多看 20 页）。
- 正在流式输出的一次回答不会被下线打断，最多再持续到这一轮结束（模型网关每次请求开始时才检查）。
- PostgreSQL 上（`node scripts/smoke-admin-console.js --people 100000 --postgres`，管理库在 PostgreSQL、用量账本仍在 SQLite）：缓存热了以后每个查询 100 毫秒以内——成员第一页 10 毫秒、一个中心（两万人）68 毫秒、一个人的详情 42 毫秒、审计按人查 30 天 40 毫秒（要过 31 个按天的分区）、部门管理员的页面 24–75 毫秒；第一次打开冷读 0.1–0.5 秒。用量账本放 PostgreSQL 时的计时还没跑。

## 12. 怎么验证

- 每个存储的行为测试同时跑在 SQLite 和 PostgreSQL（`test/helpers/postgres.js`）上。
- 查询计划测试：十万人目录、百万条审计的典型查询都要走索引（SQLite `EXPLAIN QUERY PLAN`、PostgreSQL `EXPLAIN`）。
- 停用、下线在每个入口都要被挡住：登录、恢复、续期、模型网关、飞书代理、定时任务、网站访问，各一条测试；撤掉检查，这些测试必须失败。
- 浏览器验收：用真实的服务端和合成的十万人数据启动，Playwright 走一遍每个页面和主要对话框，截图看；也以部门管理员的身份走一遍。每个画面都查有没有残留的 null、undefined、NaN 和横向溢出（`scripts/smoke-admin-console.js`，`--postgres` 换成 PostgreSQL）。
- 部门管理员：逐条接口各发一个请求，新加的接口没说明对限定范围的管理员怎么做，测试就失败（`test/admin-server.test.js`）。
- 改名前建的数据库：所有管理库存储和拼出来的查询都落在 `mydoubao_admin_*`，一张 `idou_*` 表都不许出现（`test/admin-legacy-names.test.js`；服务器的库就是这种）。
- 审计里能写出的每种动作都要有中文名字，测试从源码里读出动作逐一核对（`test/admin-action-labels.test.js`）。

## 13. 服务状态

「服务状态」页给管理整个组织的管理员看服务现在好不好、哪里不好、从什么时候开始、要不要加机器：每个进程（协调副本、模型副本、执行节点）的心跳、版本、负载和内存；各模型近 1 小时和 24 小时的请求、出错率和开始回答用时；被拒的请求按原因；每项自检最近 24 小时的色条和近 7 天的故障时间线；最近一次备份；告警发给谁、最近发过什么，以及给自己发一条「测试告警」。设计和部署见 [service-status.md](service-status.md)。
