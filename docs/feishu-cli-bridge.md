# Feishu CLI single-login bridge

The SaaS adapter reuses a confirmed application login for lark-cli OpenAPI operations. Reads are the default. Seven reviewed write actions can additionally be enabled per deployment: the single-span document replacement, document creation, an append to a document, the general `cli.write` route, a new message, a reply, and a single-shot Drive upload. Each is separately configured and separately gated. The Drive action has a documented blocker described below and cannot complete end to end yet. This is an opt-in server capability, not token import and not a copy of the user's system CLI profile.

## Request path and custody

The bundled lark-cli is built from the pinned upstream commit with the upstream `authsidecar` build tag. On account activation the Electron main process creates an isolated CLI config directory and a loopback-only sidecar with a random process-lifetime HMAC key. The renderer receives neither value. Codex and native provider subprocesses receive only the sidecar address, HMAC key, public App ID, Feishu brand and user-only policy.

The upstream CLI substitutes a sentinel for the user token, signs the request and sends it to the loopback sidecar. The native sidecar verifies protocol version, timestamp, body digest, HMAC, user identity, auth-header and exact Feishu target. It then authenticates the transit request with the current application session. The control plane resolves the server-held OAuth user token, injects it only on the final HTTPS hop to `open.feishu.cn`, streams the response back and stores neither request nor response bytes.

The application secret, OAuth access token, refresh material and parent application session never enter the CLI, Codex shell environment or renderer. The HMAC key is intentionally available to the task runtime: it authorizes the same bounded CLI **read** calls the Agent is allowed to make, but cannot be exchanged for a Feishu token and cannot carry a write.

## Reading a spreadsheet is a POST

The pinned CLI reads a spreadsheet through `POST /open-apis/sheet_ai/v2/spreadsheets/<token>/tools/invoke_read` (`tool_name` `get_workbook_structure` or `get_cell_ranges`, arguments as a JSON string), not through a REST resource — so the proxy's "every GET plus named POSTs" rule refused it, and every live spreadsheet read came back as Feishu's error mangled by the SDK ("SDK returned an invalid JSON response"). That covered the app's own 飞书表格 view as well as the knowledge copy; it was found by reading a real spreadsheet, not by a test, because the sheet smokes drive a fake CLI.

Both read tools are now named reads (`src/providers/feishu/cli-read-contract.js`) with a closed body shape: exactly `{tool_name, input}`, a `tool_name` from the recorded pair, and an `input` that parses to a bounded object whose `excel_id`/`sheet_id` are tokens and whose `ranges` are at most eight A1 ranges. `invoke_write` on the same endpoint is untouched and remains a confirmed write.

Reading Base records by id is another named read: the pinned CLI's `base +record-get` sends `POST /open-apis/base/v3/bases/<token>/tables/<tblId>/records/batch_get` with exactly `{record_id_list, select_fields?}` — 1–100 unique record ids and at most 50 field names — and nothing else is admitted at that path. Reviewed Base edits read the records they change through it, before the write and after (see [the Base workspace](feishu-base.md)).

## Read-only knowledge operations

`kb-search` and `kb-read` are the only operations on the Agent bridge that change nothing and therefore raise no confirmation card (`src/application/agent-knowledge-actions.js`). They reach exactly what the attached excerpts already came from: this login's own local knowledge copy, where every passage is re-read from Feishu and permission-checked before any of its text comes back. There is no route from them to an arbitrary Feishu URL, a task narrowed to selected documents cannot see past that selection, and a task with no knowledge scope cannot use them at all.

| Operation | Arguments | What it returns |
| --- | --- | --- |
| `kb-search` | `--query <≤200 chars>` | up to 8 passages (≤6,000 characters total) with title, `sourceUrl`, section label and a 12-character document id |
| `kb-read` | `--doc <id prefix>` `[--around <offset>]` | a 4,000-character window of one document around that offset, with `to` for paging |

They exist because a single search made with the person's own words carries every sentence an answer needs about 68% of the time on the evaluation corpus (`test/knowledge-eval.test.js`); the rest is usually one wording away. The knowledge-scope instruction tells the Agent to search again in the documents' own words before concluding that something is not there.

## Confirmed writes

A write never travels on the reusable read key. After the existing native confirmation, the main process asks the control plane for a short-lived, single-use grant bound to the session family, user, tenant, semantic action, the exact target, a fresh operation identifier and SHA-256 digests of the confirmed payload. A document grant additionally pins the expected base revision; a message grant additionally pins the recipient or source message, the placement, and the idempotency key the CLI will send as `uuid`. The confirmed text itself is never sent to the grant service. The sidecar then mints a fresh per-invocation HMAC key for that one CLI process; the process-lifetime read key is untouched.

The pinned CLI resolves its own user identity before every command, so a write-scoped key admits at most three `GET /open-apis/authen/v1/user_info` reads. Those preflights are forwarded under the ordinary read policy and do not spend the grant. The next request must be exactly the granted write; any other shape retires the key without reaching Feishu.

The control plane consumes the grant atomically **before** validating and dispatching, rechecks the live session and that it still holds the same server-held OAuth credential, then matches method, path and body against the grant. A mismatch, a replay, a reused operation identifier, a revoked session or a lost upstream response therefore all fail closed, and none can reissue the grant. A dispatched write whose outcome was never observed stays unknown; the existing local intent/receipt behaviour is unchanged and nothing retries automatically.

The audit sink receives the action, hashed session, tenant, user, resource and operation identifiers, the decision and the upstream status class. It never receives the UAT, the parent bearer, the request body, document text or the response body.

## Identity checks

Every read confirms the Feishu user it ran as, and the knowledge copy did that before and after each source it re-read: nineteen `GET /open-apis/authen/v1/user_info` requests, each its own CLI process, for one question over eight sources, counted in the running application. Under this bridge the user is the application session's, and the control plane binds a session to one Feishu user — renewal replaces the token, never the user — so `SaasFeishuCliProvider.documentIdentity` shares a check with the reads that follow it while two things hold. The session the next request would travel under must be the one the check was made under, which the sidecar reports as a digest (`FeishuCliSidecar.sessionFingerprint`: SHA-256 over application, server, token and expiry; the token itself never leaves the sidecar). And the check must be less than 30 seconds old. A new login or a renewal changes the digest and is checked again, and a check during which the session changed is not kept. Writes never share a check: document edits, message sends and replies, and Drive uploads ask for `fresh: true`, and the control plane rechecks the session before dispatching any write in any case.

## Server configuration

This first slice requires source access because it reuses the same server-owned OAuth grant:

```text
FEISHU_SOURCE_ACCESS_ENABLED=1
FEISHU_CLI_BRIDGE_ENABLED=1
FEISHU_CLI_SCOPES=<explicit comma-separated OAuth scopes approved by the administrator>
FEISHU_CLI_WRITE_ACTIONS=document.inline-replace,document.create,document.append,cli.write,message.send,message.reply,drive.upload   # optional; omit to stay read-only
```

`FEISHU_CLI_WRITE_ACTIONS` is empty by default and accepts `document.inline-replace`, `document.create`, `document.append`, `cli.write`, `message.send`, `message.reply` and `drive.upload`. `cli.write` is the general Agent route: the application asks the pinned CLI with `--dry-run` what a command would send, shows that request to the person, and binds the grant to exactly that method, path and canonical body digest, restricted to an allow-list of write families (create/block-edit a document, write a spreadsheet, create or update Base records). Deletion, permission and sharing changes, owner transfer and raw `api` endpoints are outside it. It requires the bridge, and the corresponding write scopes must be listed in `FEISHU_CLI_SCOPES`. A login advertises `cliDocumentWrites` for the document action, `cliMessageWrites` for either message action and `cliDriveWrites` for the Drive action, and only when that action is configured; online renewal must carry the identical capabilities or the session fails closed. Enabling one action never enables another: `message.reply` alone leaves `message.send` refused at the grant service even though both share a capability flag, and the desktop refuses the message paths outright when only the document action is enabled. The Drive action carries a strict multipart reader that accepts no nesting, no unknown header, no duplicate or extra field and no unterminated part; it was checked against a body captured from the pinned binary and refuses a single flipped byte.

`FEISHU_CLI_SCOPES` has no implicit defaults. Startup rejects a missing, duplicate or malformed list. These scopes are included in the OAuth consent request and the returned grant must contain every configured scope. Validate them against the customer's Feishu edition and the exact read operations being enabled.

Reads are unchanged: `GET /open-apis/...` plus the CLI's exact semantic-read `POST /open-apis/docs_ai/v1/documents/<token>/fetch`, only to `https://open.feishu.cn`, with a 30-second upstream deadline. Each enabled write action contributes exactly one endpoint:

| Action | Request | Body bound by the grant |
| --- | --- | --- |
| `document.inline-replace` | `PUT /open-apis/docs_ai/v1/documents/<document_id>` | `command=str_replace`, `format=xml`, granted `pattern`, `content`, `revision_id` |
| `document.create` | `POST /open-apis/docs_ai/v1/documents` | exactly `content`, `format=markdown`, with `content` matching the granted digest |
| `document.append` | `PUT /open-apis/docs_ai/v1/documents/<document_id>` | `command=block_insert_after`, `block_id=-1`, `format=markdown`, granted `content` digest and `revision_id` |
| `cli.write` | whatever the pinned CLI's own `--dry-run` declared, restricted to the allowed write families | the canonical digest of that exact body; the method is the one the dry run named, not one fixed by the action. A request the shared rule classifies as destructive is refused under this action even when its digest matches |
| `cli.delete` | the same route for destructive requests: `DELETE` of an event on the user's primary calendar or of a task, `POST …/records/batch_delete`, and the sheet and document requests that delete, clear, revert or overwrite | the canonical digest of the exact body, or of no body for a `DELETE`, which must arrive with none. It is the only grant a destructive request can travel under; the desktop requests it only after a red deletion card is answered -- or, from a task on 完全访问, on that task's standing authorization (`approveDeletionForFullAccess`) -- and adds the CLI's own `--yes` only then |
| `message.send` | `POST /open-apis/im/v1/messages?receive_id_type=open_id` or `chat_id` | granted `receive_id`, `msg_type`, `content`, `uuid` |
| `message.reply` | `POST /open-apis/im/v1/messages/<message_id>/reply` | granted `content`, `uuid`, and `reply_in_thread` present only for a confirmed thread reply |
| `drive.upload` | `POST /open-apis/drive/v1/files/upload_all` | multipart with exactly `file_name`, `parent_type=explorer`, `parent_node`, `size`, `file`, matching the granted name, folder, length and byte digest |
| `drive.replace` | `POST /open-apis/drive/v1/files/upload_all` | overwrite in place of one scheduled task's oldest kept report, chosen by the control plane from that task's own receipts (never by a run): multipart with exactly `file_name`, `parent_type=explorer`, `parent_node`, `size`, `file_token`, `file`, where `file_token` is the granted file and the name is an `idou-<uuid>.schedule.md` report (`mydoubao-<uuid>.schedule.md` for one written before the rename); single-shot only. The file keeps its token and takes the new name. No upload grant can carry `file_token`. Before any grant is asked for, the file must still be that report: listed in the folder under its name (metadata and `drive +inspect` still show a file in the recycle bin; the folder listing does not) and downloaded with the length and SHA-256 its receipt recorded |
| `drive.upload-chunked` | `POST /open-apis/drive/v1/files/upload_prepare`, then `POST …/upload_part` once per block, then `POST …/upload_finish` | one grant for the whole sequence: prepare with exactly the granted name, folder and size; each part multipart with exactly `seq`, `size`, `file`, `upload_id`, in order and sized to the block Feishu answered; finish with that `upload_id` and block count, forwarded only when the running SHA-256 of every part equals the granted byte digest |

A request no configured action could target is refused with 405 before any grant is looked up, so a disabled deployment never reaches the grant path. Every other POST, every PATCH/DELETE outside an enabled family, a grant offered on a read, arbitrary origins, redirects and paths outside `/open-apis/` fail closed. Widening a method never enables a write.

Every shape above was recorded against the pinned binary rather than inferred, including that `im +messages-reply` omits `reply_in_thread` entirely for a main-chat reply, so its presence is part of the confirmed placement.

## Drive: single-shot bound, and metadata-free lookup

Measured against the pinned binary, `drive +upload` sends one `upload_all` at or below 20 MiB (20971520 bytes) and switches above it to a server-structured `upload_prepare` / `upload_part` / `upload_finish` sequence whose part count and size come from the upstream response. A single-use grant cannot describe a sequence the server shapes mid-flight, so a file above that bound travels under its own action, `drive.upload-chunked`: one grant admitting exactly the recorded sequence, checked step by step by the sidecar and again by the control plane (`src/providers/feishu/cli-write-sequence.js`). The prepare request must name the granted folder, file name and size. Feishu's answer to it is read whole, and the rest of the sequence is bound to its `upload_id` and block size. Every part must carry the next `seq` and exactly that block size (the last one the remainder), and its bytes feed a running SHA-256. `upload_finish` — the only step that makes a file exist — is forwarded only once every block has gone and that digest equals the granted one, and it spends the grant. A refused step, a part Feishu does not accept, or a step that fails in flight ends the sequence for good; each accepted step extends the grant by 60 seconds, never past 15 minutes. Bytes other than the confirmed ones can therefore reach an unfinished upload at most, never a file. The application uploads at most 100 MiB, in blocks Feishu may size between 256 KiB and 16 MiB.

Recorded against the bundled binary through the real sidecar and a local stand-in for the control plane: the part's multipart fields arrive in a different order on every request, and the block size follows whatever `upload_prepare` answered — 4 MiB gave six parts for a 22 MiB file, 8 MiB gave three. Writing the contract turned up an older fault as well: the file-name pattern both upload actions share allowed only letters after the dot, so an `.mp4` — a type the adapter accepts, and the one large enough to need chunks — could not be granted even as a single upload.

The Drive read path used to call the CLI's raw API resources `drive metas batch_query` and `drive files list`. Raw resources exist only when the CLI may fetch its API metadata, and that fetch goes straight to `open.feishu.cn` **around the sidecar**: with an ambient HTTPS proxy configured and `LARKSUITE_CLI_REMOTE_META` unset, the CLI issues `CONNECT open.feishu.cn:443` that the sidecar never sees. The bridge sets `LARKSUITE_CLI_REMOTE_META=off` precisely to stop that, so those commands report `unknown subcommand`. Re-enabling remote metadata would let the CLI reach Feishu outside the control plane and must not be the fix.

Folder resolution now uses the metadata-free `drive +inspect` shortcut, which reaches Feishu through `POST /open-apis/drive/v1/metas/batch_query`, the companion read this action enables. That shortcut behaves the same with or without the bridge, so both modes share one path. It has one trap worth stating: an unresolvable or unreadable target does **not** produce an error. `+inspect` exits zero and echoes the requested token back with an empty `title`. The token and type in its response therefore prove nothing; a non-empty title is the only server-derived evidence, and the adapter treats an empty one as a failure.

Post-upload verification is where the two modes differ. An independent CLI keeps the original folder listing, which proves the file is in the expected folder. Under the bridge that listing is unavailable, and it is also no longer the strongest check: the destination folder, file name, byte length and byte digest were bound by the grant and enforced by the control plane before a single byte was dispatched. Verification there shrinks to confirming, through `+inspect`, that the file exists under the confirmed name. The folder guarantee moves from a post-hoc read to a pre-dispatch binding rather than disappearing.

One consequence to keep in mind: `+inspect` rewrites a file's link to `https://www.feishu.cn/file/<token>`, which is not the `/drive/file/<token>` form the adapter parses. The receipt link is therefore built from the confirmed folder's own origin, so records and confirmations keep the tenant domain the user supplied.
