# Server-owned Wiki package-key custody

Implemented as server-owned modules with explicitly configured [publisher](wiki-publisher-key-api.md) and [recipient](wiki-recipient-key-api.md) network operations; recipient delivery is denied unless separately configured:

- `WikiKeyVault` persists wrapped, independently generated 32-byte package keys in a separate SQLite database. It accepts an explicitly provided server wrapping key; it never generates a deployment root automatically, imports client keys or stores documents/bundle bytes.
- `WikiKeyCustody` connects a verified parent Feishu session, the current coordinator lease/declaration, an explicit trusted processing-policy callback, fresh source permission checks, the vault and the actual Drive/original payload verifier.
- Publisher and recipient integrations have native HTTP implementations. `bin/server.js --feishu` instantiates the service only through an explicit key configuration. Recipient and synthesis-publisher trust lists are separate from publisher membership; desktop automatic sync and SSO-to-CLI identity binding remain unimplemented.

## Storage and lifecycle

Use `await WikiKeyVault.open({ databaseFile, wrappingKey })` in a trusted server composition, or `WikiKeyVault.fromFiles({ databaseFile, wrappingKeyFile })`. The root file must contain **exactly 32 raw bytes**, not a model key, password or base64 text. Paths are explicit absolute canonical paths; the database requires a private non-symlink parent. Database/sidecars and root files must be regular single-link files; POSIX ownership and private permissions are checked. Windows deployments need separately enforced equivalent ACLs; these tests do not establish Windows security. No production root file was created during development.

The vault uses [Node's authenticated AES-GCM primitives](https://nodejs.org/docs/latest-v22.x/api/crypto.html#class-cipheriv), a fresh 12-byte nonce per wrap and a 16-byte authentication tag. Authentication binds the vault instance, key ID, complete canonical package context and, once bound, the immutable package metadata. A root-check record rejects an incorrect root on reopening. Authenticated decryption completes before a callback sees a key. Database substitution of a package/context/key ID cannot be accepted merely because its ciphertext still exists.

The context binds hashed application/tenant identity, shard, generation, fencing number, publisher node, provider, Drive tenant/folder and source digest/count. A unique tenant/shard/fence slot is idempotent while unbound. After package binding, another prepare call fails rather than exposing the key for a different encryption attempt. Binding checks package format, source/destination/key identity and exact metadata; a second identical bind is harmless, a conflicting bind fails. Recovery verifies the existing binding without returning a plaintext key. The Drive file token is resolved separately from the coordinator's current publication; it is not part of the pre-upload binding.

SQLite WAL plus FULL synchronous mode and immediate transactions preserve key creation/binding across process restart. Maximum capacity is 100,000 retained slots, including revoked records; there is no automatic destructive purge. Revocation removes the wrapped key from the current row and is checked after asynchronous callbacks. Same-instance active callback buffers are cleared on revocation/close; caller-owned root buffers are not mutated. Copies in another process, already delivered keys, old backups, WAL history, host swap and crash dumps are **not** cryptographically recalled. Root-key rotation, external KMS/HSM integration, consistent backup/restore, database rollback protection, multi-host replication and operational garbage collection are still required for production deployment. Losing the root loses access to its wrapped keys; silently creating a replacement is forbidden.

## Authorization is separate from encryption

The vault is not an authorization API: its context/key callbacks are trusted server calls and must never be mapped directly from request JSON. The custody composition requires `authorizeProcessing` with no permissive default. It must return the boolean `true` for the current subject, shard, operation and policy. Source view permission alone does not imply enterprise approval to process or synchronize the data.

Preparation resolves the publisher's own active lease and already-registered source declaration, compares the requested source digest, and checks original permissions through the session-bound OAuth authority. The optional native source URL is not fetched or persisted by custody. Context/policy/session are rechecked around awaits. Publisher grants are bounded by the parent session and a 60-second lifetime; release, logout, cancellation, expiry checks and custody shutdown clear their owned key buffer and listeners. This grants a temporary operation, **not an expiring cryptographic key**. A consumer that copies a key can retain it, so future reads still need current source authorization.

`verifyPublication(parentToken, shardKey)` resolves the recipient's current publication, reads the registered Drive artifact, unwraps the exact bound key internally and independently compares all originals. It returns only the verifier's metadata report; the artifact buffer is cleared after verification. It never returns the recipient a key. `keyReleaseAuthorized` stays false and publisher-authored synthesis is not proven by matching its cited originals. `acquire` performs this verification afresh, then requires a separate explicit `authorizeDelivery` decision with no permissive default. The configured network service implements recipient membership and publisher-node synthesis trust policy; no client report is reusable authorization. See the recipient protocol for exact lifetime, ACL and trust limitations.

## Evidence and limits

Eight vault tests cover encrypted-at-rest storage, same-slot idempotency, immutable binding, wrong root, context/record/ciphertext tampering, persistent revocation, owned-buffer cleanup and unsafe paths. A separate Node process opens the same bound database from a private root file and verifies a digest of the synthetic package key; no key crosses stdout. Four publisher/custody tests add real codec/coordinator/budget/HTTP coordination and synthetic Feishu transport: publication, second-user verification after custody restart, lost-report recovery without another upload/key issue, processing/source denials, revoked keys and grant lifecycle checks.

An isolated loader mutation removed the stored-context equality check; the context-substitution test failed with a missing expected rejection. The production file was unchanged by the experiment; normal tests passed afterward. Initially the vault fixture used macOS's `/var` temporary alias and was correctly rejected by canonical-path enforcement; the fixture was corrected to use its real path without relaxing production validation. A recovery test's nonexistent status accessor was also corrected to inspect the existing journal. Empty failed-fixture directories were removed.

Native HTTP recipient import tests are part of the suite. Tests use disposable roots and synthetic Feishu identities/content; they do not establish live OAuth/CLI linkage, actual cloud writes, cross-machine propagation or an independent security audit. No existing MiniMax key or supplied read-only document was accessed or modified in this increment.
