# Desktop automatic Wiki publication

The enterprise desktop now owns one `DesktopWikiPublication` per account. A confirmed Feishu application login attempts startup when the server advertises either the single-login read bridge or fallback CLI identity checks. The bridge is not token provisioning: its native provider sends sentinel credentials through a loopback proxy and the OAuth token stays server-side. Fallback mode still checks its independently logged-in CLI user against the current application subject. Both paths retain original-resource access checks.

## Server-selected destination

`POST /v1/wiki/scopes/target` accepts exactly `{}` with the existing parent session. It requires enabled CLI identity checks on both the parent and source-access service, coordinator membership, Drive budget policy, publisher processing authorization, a configured original-document origin, and `automaticPublishingApproved: true`. Defaults stay off. It returns only a stable per-application/tenant/user shard hash, canonical enterprise folder reference, original origin, policy digest, parent expiry and session binding. It issues no key, lease, resource permission or publication grant. The client verifies the exact response, session binding, canonical destination and expiry; a renderer cannot supply a destination or source list.

Use the existing [account matching configuration](feishu-account-matching.md), [publisher key service](wiki-publisher-key-api.md), coordinator and Drive budget configuration. Nothing in this increment changes a deployed enterprise policy, expands OAuth scopes automatically, creates a folder, or configures an existing user's account.

## Desktop lifecycle

The native composition installs the server-approved canonical text reader, derives retained-read candidates, and uses the existing scope/key/source-registry/coordinator/budget/publisher implementations. Initial empty selection waits. Later complete document reads, including accepted message-discovery document reads, become eligible on the two-minute worker cadence. It uploads new encrypted packages, checks downloaded bytes, and records publication metadata. It does not overwrite originals, grant sharing permissions, perform root-directory sync, or delete expired packages.

The knowledge page shows local discovery and cloud publication separately, with current run counts, destination/expiry, stop and configuration-recheck controls. Native events update the view; old status responses cannot overwrite newer events. Navigation/reload disposes view listeners but does not stop the main-process publisher. Stop cancels and drains work; account switch/exit closes publication before disposing its Wiki. A separate parent-expiry timer also stops runs with no sources. Already-dispatched uploads may finish and retain a receipt; stopping is not rollback. Unknown results remain paused and cannot be replayed by stop/restart.

Desktop account verification serializes its own requests with a minimum 600 ms admission interval. Each admitted request freshly reads CLI identity and the server's current identity; no match is cached. This was required by actual desktop testing: without backpressure one fast synthetic publication exceeded the unchanged 120/minute server identity limit after uploading, before manifest commit. Cancellation prevents queued requests from reading the CLI. This is local backpressure, not fleet-wide rate allocation; concurrent clients can still be refused by the server. Long queues/timeouts fail closed. The additional latency is real and not hidden by the UI.

### Online session checkpoint

When the separately configured [online login renewal](feishu-login.md#optional-bounded-online-renewal) runs, it enters the same native FIFO work queue as publication/reception and then the local Wiki queue. This fixed cloud-then-local lock order matches publication, which may select local reads while holding the cloud lane. Current cloud work and the current local operation—including an opted-in model call and its durable result/reservation—finish before the OAuth identity check and atomic credential replacement. The next operation does not start until the checkpoint completes. Waiting does not extend the old login: if it expires before its turn, renewal fails closed. Long uploads/queues can still require explicit login.

Only an already-running publisher is refreshed. It reads the server target again under the successor session and requires the same shard, canonical origin/folder and policy digest. Changed or unavailable configuration stops publishing; a valid model login does not imply Wiki authorization. A successful checkpoint updates the parent-expiry timer, preserves the original eight-hour local-run ceiling and counters, and invalidates the inner cached scope. The next cycle disposes the predecessor scope (remote release remains best-effort; original expiry still applies) and obtains a fresh scope before planning or uploading. No old grant is extended, and source/key/budget checks remain unchanged. Stale predecessor expiry callbacks cannot stop the refreshed run.

Paused, ambiguous, user-stopped or closed work is never restarted by renewal. The encrypted publication journal remains authoritative: an unchanged package is not uploaded again, and an unknown upload receipt still requires reconciliation. An already-enabled, unexpired local synthesis consent may be rebound only after fresh same-tenant/user and same-gateway checks, with a different session binding and strictly later expiry. Its six-call startup budget is not reset; explicit disable, expiry, mismatch and failed/reserved revisions remain closed and are never replayed. This checkpoint does not renew media/MCP/runtime grants and does not certify uninterrupted model requests.

## Evidence and boundaries

`scripts/smoke-publication-desktop.js` uses actual Electron, main/preload/renderer, native account guards and canonical/Drive adapters, encrypted storage and publication code, with real loopback OAuth/scopes/keys/coordinator/registry/budget services. Only CLI/upstream identity/document/Drive endpoints and OS cipher are synthetic. The test invokes the real worker tick after the document queue to advance the normal cadence; it does not replace publisher authorization or upload logic. It verifies actual encrypted upload/download, UI publication status, stop/restart and logout. No real Feishu/model calls occur.

Node integration tests also retrieve a desktop-composed package through the existing recipient path and search the decrypted, reauthorized evidence. They cover policy/default denial, session-bound/stable targets, forbidden destination overrides, stop during a pending target, empty-run expiry and no replay after a lost upload response. Renderer tests exercise stale events/responses and disposal.

`node scripts/smoke-publication-desktop.js --renewal` exercises the additional checkpoint path using a shortened initial synthetic session. It enables synthesis, holds the real per-account cloud-work slot before the scheduled renewal window, opens a source through the actual document/Wiki path, and queues its first publication. It verifies that the first synthesis/result and encrypted publication finish before credentials rotate, then checks a preserved remaining-call count, fresh schedule expiry, one account activation, no unchanged re-upload, and a second cited synthesis/encrypted generation after changing only the fixture's original. The model endpoint is a test-only contract fixture reached through the production gateway client; no MiniMax provider call is made. It does not replace the native auth callback, publisher, journal, coordinator, quota or scope checks. Results and any failed acceptance attempts are recorded in the delivery ledger; this script definition alone is not proof of a passing run.

This is a development integration, not packaged/private-cloud or multi-device production acceptance. In particular:

- Individual parent sessions remain at most 15 minutes; optional online renewal is bounded by the original Feishu authorization and a fixed four-hour horizon. Without it, expiry still stops synchronization. The desktop [persists its own encrypted device signing identity](device-identity.md), allowing the same installation/account to reuse its existing journal ownership after a fresh login. Prior versions' already-lost ephemeral keys, deleted/corrupt device stores, changed server origins and other devices still cannot prove that ownership and require safe reconciliation. No new shard or overwritten head conceals those gaps.
- Other devices lack the original local publication proof and likewise pause. [Automatic recipient discovery/download](wiki-desktop-reception.md) is now connected to the desktop under separate enterprise approval; it does not transfer publisher ownership or constitute distributed deployment acceptance.
- Detailed recovery UI, fleet request budgeting, large-corpus incremental publication, ACL/deletion propagation, cloud package cleanup, KMS operations and quota reconciliation remain unfinished.
- A successful capability check is not a proof of source permission. A source failure pauses the whole selected set rather than silently exporting a partial set. The control plane does not persist Wiki content bytes; the smoke script's artifact routes are test-only replacements for Feishu Drive.

The supplied user document remains read-only and was not accessed or changed in this increment.
