# Immutable Wiki source declarations

The native publisher, metadata coordinator and server OAuth source-permission verifier now have a connected source-registration path. This is **an immutable publisher declaration with independent permission checks**, not an independently verified inventory of the encrypted payload. All responses retain `provenance: "publisher-declared"` and `contentVerified: false`. No route in this increment returns a content key or enables production automatic synchronization.

## Registration and publication

The publisher can receive an explicit `sourceRegistry: WikiSourceRegistryClient` dependency. After exporting current sources under its renewable node lease and before requesting a key, it derives a metadata-only list from those exact records and registers it. A failed registration prevents key preparation and upload. The default desktop has no registry/publisher activation added by this increment.

Each source contains exactly `tenantId`, `providerId`, `resourceId`, `revision`, `contentHash` and `textSha256`; bodies, titles, source URLs, credentials and arbitrary fields are rejected. Current registration requires numeric Docx revisions and SHA-256 hashes (as emitted by the SaaS document provider). The 1–200 entries are unique and sorted by the same identity digest used by the bundle codec. The independently calculated registration digest matches the codec's `sourceSetHash` and includes the text hash, not only the upstream revision.

`POST /v1/wiki/sources/register` accepts `{ shardKey, leaseId, fence, sources }` under the verified Feishu **parent** Agent token. It checks tenant membership, lease ownership/currentness and Drive policy before probing source permissions. For SaaS proof, the configured Drive tenant must equal the OAuth tenant and the provider must be `saas-cli`; this does not claim a general cross-provider identity mapping. The existing `FeishuSourceAccess` checks every source as the OAuth user, in batches of up to 20, and the registry validates each returned identity and exact batch digest.

After awaited checks, session, policy and lease are checked again. One SQLite transaction inserts the canonical declaration or returns the identical existing declaration. Reordering input is idempotent; changing a source, revision or hash under the same lease is rejected. A denial in a later batch, logout, policy change or expired/superseded lease cannot leave a partially registered list.

The existing coordinator's publication transaction now enforces that any declaration under that lease matches the manifest's source digest and count. Omitting the client registry dependency cannot bypass a declaration already present on the server. The existing budget/immutable receipt/fence checks remain. Tombstones are still allowed. Legacy publications without declarations retain their old coordinate/recovery behavior but cannot pass the new source-registration check. Registration is not a new upload, key grant, content-verification attestation or administrator data-processing consent.

The normal server entry creates these routes only when both Wiki coordination and the optional server source-permission authority are configured (`IDOU_WIKI_CONFIG_FILE`, its required Drive configuration, and `FEISHU_SOURCE_ACCESS_ENABLED=1` in Feishu mode). This code wiring is not an assertion that those settings have been enabled on a real tenant.

## Recipient check

`POST /v1/wiki/sources/check` accepts only `{ shardKey }`, not a replacement source list. It resolves the current published head and the exact lease-owned declaration from SQLite, recomputes its digest/count, requires the current configured destination, and checks **that stored set** under the recipient's OAuth identity. It rereads the head afterwards; withdrawal or replacement during a permission check cannot return old success.

The response includes generation, manifest hash, source digest/count, `declaredSourcesReadable: true`, `pointInTime: true`, and the explicit unverified provenance above. It exposes no source IDs, bodies, keys or upstream errors. A different user's permission is freshly checked, not inherited from the publisher. The native client rejects changed connections and substituted receipts and returns only the documented metadata.

The underlying source-permission service's local 100-check/minute ceiling and timeouts still apply. A large declaration or many concurrent clients may exceed that capacity; the registry then refuses registration/checking instead of accepting a partial list or automatically retrying. Supporting the full 200-source wire limit at production scale still requires deliberate scheduling/batching and authorization freshness policy. A native request timeout may leave an acknowledged-to-the-server metadata registration unknown to the client; it never authorizes a replacement upload. Registration retries require the same active lease/list and repeat source checks. Committed/expired leases are not reopened to add or alter declarations.

## Native recipient preflight

`WikiBundleReceiver` also accepts an explicit `sourceRegistry: WikiSourceRegistryClient`. Before asking its separately configured key authority for a key, it checks the server's current stored declaration as the recipient. The receipt must match the exact shard, generation, manifest hash, source hash and source count and retain `declaredSourcesReadable: true`, `pointInTime: true`, `provenance: "publisher-declared"`, `contentVerified: false`. Denial, malformed/substituted evidence or a failed registry call prevents both key acquisition and download; there is no fallback after a configured registry fails. Account, cancellation, business session and coordinator head are checked again after the awaited registry call.

This connects the existing declaration path to the existing actual-byte checks: authenticated decryption must still match the manifest and complete decoded source set, and atomic local import must still reread every original and compare its identity, resource, URL, title, revision, hash and text. The source receipt is deliberately not passed as a key-release attestation. Recipient-side checks happen too late to prove safety of giving that recipient a key; an independent production payload/source proof remains required at the key authority. Citation validation also does not prove that free-form publisher synthesis contains only source-derived information.

The dependency remains optional for existing isolated integrations; production desktop synchronization and key delivery remain disabled. It introduces no server content endpoint/storage, key issuer, OAuth scope change, schema migration, cache permission grant or UI entry. One preflight runs per receive attempt, not once per source/currentness callback; it does not add a positive permission cache.

## Storage and compatibility

The coordinator SQLite schema advances from 1 to 2, adding `wiki_source_declarations(lease_id, source_hash, sources, registered_at)`. At most one declaration can be added per existing valid lease; the existing coordinator lease bound remains. No content or key bytes are stored. The registry uses the coordinator's private database path and transaction/fencing boundary rather than another storage server. Declarations are not automatically deleted, rewritten or backfilled.

Opening a valid v1 database preserves heads and leases and creates the empty declaration table. Old publications remain explicitly without source proof. Schema-v1-only server builds must not write the upgraded database; deployment rollback needs a compatible build or a properly coordinated pre-migration database restore, not merely changing the schema number. Tests cover migration and a second database connection; this increment does not claim process-kill/power-loss or live rolling-upgrade acceptance.

## Trust boundary and next work

The source list, revisions and hashes are supplied by the publisher. Binding them to a manifest is necessary but does not prove that a malicious/incorrect publisher encrypted only those records, or that text labelled with a source actually matches it. A hash is not source provenance. Independent payload/source verification or a separately justified trusted producer is still required before this registry may be used for key release. The server permission probe checks `view`, not export/copy, model processing or enterprise synchronization policy.

The next security step must settle and implement that content-proof boundary, then bind per-package KMS keys to the verified generation, source set and recipient. CLI/OAuth identity mapping, scheduler administrative scopes, key rotation/revocation, automatic retrieval, deletion/ACL propagation and quota reconciliation remain. No enterprise-wide decrypt key or permissive placeholder has been installed.

An [independent payload/original verifier](wiki-payload-verifier.md) now implements actual ciphertext and source comparisons with explicitly injected trusted readers/key custody. An [opt-in common source reader](wiki-canonical-sources.md) supplies versioned plain text through both CLI and server OAuth. The verifier is not wired into these HTTP routes; live adapter acceptance, real artifact access/key custody and policy remain required. Its in-process reports do not authorize key release. Registry responses therefore remain unchanged and unverified at the content level.

## Verification

Eight registry tests exercise canonical digest agreement with actual bundle records; real HTTP/native clients and SQLite; immutable/reordered retries and a second connection; different-recipient permission checks; denied later batches; logout/lease expiry/policy races; foreign node/token/tenant and arbitrary field rejection; manifest mismatch; head withdrawal; v1 migration; and substituted client responses. The permission authority in these focused tests is synthetic.

Two additional publisher tests use the actual publisher/codec/Drive-provider code, HTTP coordinator/registry, SQLite budget and actual `FeishuSourceAccess` with synthetic OAuth credentials/Feishu responses. The produced artifact's manifest matches the persisted declaration; a second identity checks the stored list and a later denial is observed. When server permission denies a source that the native fixture can read, no key is requested and no file or byte charge is created.

An isolated module-loader mutation removed only the coordinator's declaration-to-manifest binding check. The mismatch test then failed because the bad publication was accepted. Production source was not altered by that experiment; the unmodified test passes. This is not real SaaS/private-cloud authorization, key delivery, multi-machine synchronization or a production security audit.

Three recipient tests cover denial/substituted receipts before any key request, cancellation/session/identity/head races during registry checks, and successful/corrupt/changed-original imports after registry agreement. The denial test first failed on the old receiver with one unexpected key request, then passed after integration. An additional publisher-to-recipient test uses real HTTP, SQLite, codec, Drive provider and local encrypted Wiki with the actual OAuth source-access implementation against synthetic Feishu responses. A second identity is denied before key/download, subsequently imports searchable evidence when allowed, and is denied again on a later attempt without cached registry permission. Its key authority remains explicitly synthetic, not production authorization evidence.
