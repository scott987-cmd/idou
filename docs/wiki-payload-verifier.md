# Independent Wiki payload verification

`src/control-plane/wiki-payload-verifier.js` implements a server-internal verifier of an actual encrypted publication against its immutable registered sources and independently read originals. This is executable verification logic, **not an enabled production service or a key-release authority**. Its trusted content readers and server key custodian must be supplied explicitly; there is no default reader, HTTP route, client credential import or source-content persistence.

## Data flow and result

1. Verify the parent Feishu Agent session. Resolve the current published manifest and immutable declaration through `WikiCoordinator.publishedSources`, including tenant membership and destination policy. The caller supplies only a shard hash, not a manifest or source list.
2. Ask the configured trusted artifact reader for that exact stored publication. Bound and snapshot the returned bytes; do not mutate the reader's buffer.
3. Within the trusted server key custodian's `withKey` callback, authenticate and decode the package with the existing AES-GCM codec. This validates the complete file hash, exact header, decoded record count and source digest. Correct encryption by a publisher does not excuse hidden or substituted records.
4. For every decoded source, ask the trusted original reader using its **registered metadata**, not the package's source URL. Require the reader's returned app/tenant/user/device subject to match the session; require exact tenant, provider, resource, revision, upstream hash, URL, title and normalized text, plus a non-partial source.
5. Recheck session, current publication/declaration and Drive policy across awaits, including after the key callback has finished. Only then return metadata hashes and verification facts. No decoded text, title, URL, credentials or keys are returned or written to disk by the verifier.

The result binds `subjectHash`, shard, generation, publication/manifest/ciphertext/source hashes and the stable full-content digest. `payloadMatchesDeclaration: true` means the decoded source inventory matches the registered digest; `originalsMatched: true` means its source fields matched the trusted reader. These are point-in-time in-process observations, not a signed or durable reusable attestation. Existing revocation/source-change races outside those individual reads remain; there is no global atomic snapshot of all Feishu documents or positive permission cache.

`synthesisProvenance` is `publisher-declared` when synthesis exists and `absent` otherwise. Valid quotations do not establish that free-form summaries are entailed by those quotations or contain no other information. `keyReleaseAuthorized` is always **false**, including for packages without synthesis: production delivery additionally needs policy, key custody, recipient binding and current authorization. Do not turn this report into a client-provided Boolean that unlocks keys.

One operation per verifier instance and a 120-second abort signal bound the intended work. The trusted readers/custodian must honour cancellation and release resources; the signal also aborts at operation completion. Late non-cooperative dependencies cannot produce accepted results, but JavaScript cannot forcibly terminate arbitrary injected code. Owned ciphertext buffers are cleared; the codec clears owned key/plaintext buffers. This is not a guarantee of erasing JS strings, transport copies, host swap or crash dumps. Deployment must disable body logging/dumps and apply its own process-level protections.

## Required production adapters and format decision

The current client reads CLI `docs +fetch --doc-format xml --detail simple`, projects that XML and hashes the XML bytes. The official [cloud-document content API](https://open.feishu.cn/document/docs/docs-v1/get.md), inspected on 2026-09-09 via the official documentation index, documents Markdown content and the `docs:document.content:read` scope. It does not establish byte equivalence with the CLI's XML output. Substituting its Markdown response and comparing hashes would reject legitimate packages; ignoring differences would defeat verification.

A subsequent increment adds an [opt-in shared plain-text representation](wiki-canonical-sources.md), using document metadata and `raw_content` on both the bundled CLI and server OAuth paths, with version bracketing and canonical configured-origin Docx URLs. It does not claim XML/Markdown equivalence. Existing XML pages refresh on authorized reads without carrying stale citations; old published bundles require coordinated regeneration. Native/server tests are synthetic; live response, link and private-provider compatibility remain to be accepted. No deployed scope or CLI account was changed.

An opt-in server-owned OAuth artifact reader is implemented below. The [wrapped per-package key vault and custody composition](wiki-key-custody.md) connects publishing and recipient payload verification with an explicit trusted processing-policy callback. The opt-in key service now composes this verifier for [recipient acquisition](wiki-recipient-key-api.md), applying separate recipient/synthesis policy before delivery. Operational KMS/root management, deployed synchronization policy, source-change/ACL propagation and actual SaaS/private acceptance remain missing. Desktop automatic Wiki synchronization remains disabled. The metadata-only registry remains unchanged and still reports `contentVerified: false`; verifier results are never accepted from a client as authorization.

## Server OAuth Drive artifact reader

`FeishuSourceAccess.readPublishedBundle(parentToken, shardKey, { coordinator, signal })` is internal-only. The trusted server coordinator resolves the current publication; request bodies cannot supply a manifest, download URL or OAuth token. It checks parent-session identity, configured tenant, SaaS provider, manifest digest and current publication/declaration/policy across awaits. Credentials stay in the existing OAuth authority, with fresh `user_info` validation before the Drive request. There is no bot fallback or content-serving HTTP route.

`FEISHU_WIKI_BUNDLE_READS_ENABLED=1` is a **new, default-off** configuration option. It requires existing source-access enablement and nonempty `FEISHU_WIKI_ORIGINAL_ORIGINS`. New OAuth authorization additionally requests `space:document:retrieve` and `drive:file:download`; existing grants are not silently extended. No deployed environment or account authorization was changed during development. The option prepares the internal reader, not an enabled synchronization/key-release service.

The official [folder-list API](https://open.feishu.cn/document/server-docs/docs/drive-v1/folder/list.md) supplies direct children, including file tokens, types and parent tokens. The reader searches only the registered folder, at most ten pages of 200 entries per membership check. It requires the exact registered file token, `file` type, parent folder and managed reservation filename; same-name replacements and shortcuts are rejected. It never recursively scans or defaults to the user's root. Missing/malformed/repeated cursors or the page bound fail closed; this is not an entire-directory inventory. A second membership read after download catches observed moves/renames, not arbitrary changes after the final check.

The official [file-download API](https://open.feishu.cn/document/server-docs/docs/drive-v1/download/download.md) returns cloud-file bytes, not online Docx/Sheet/Base content. The fixed HTTPS endpoint uses user OAuth and rejects redirects; listing URLs and Content-Disposition filenames are never followed or used as filesystem paths. Only full HTTP 200 responses without content ranges or nonidentity encoding are accepted. A supplied Content-Length must match the manifest, but actual stream length and SHA-256 are always checked independently. A single bounded buffer (maximum 10 MiB) holds ciphertext without disk writes. Abort/logout cancels stalled streams; failures cancel bodies and clear the owned buffer. On success the internal caller owns the returned buffer and must release/clear it when finished. This is not an OS swap/crash-dump or JavaScript-memory-erasure guarantee.

The authority shares its four-read concurrency cap and per-session single-flight gate with original/permission reads. List calls are limited to 20/s and downloads to 5/s within this authority instance, without automatic retries or failed-call refunds. The operation has a 30-second abort deadline. This is not distributed/global quota enforcement; production must coordinate shared application limits (including the documented daily download ceiling) and deployments must disable response/body logging.

Tests connect this reader to the real verifier/codec and SQLite coordinator using synthetic upstream streams and key custody. The canonical-source integration additionally passes native observation/export through server Drive and original readers, with synthetic CLI/HTTP responses. No live download, key delivery, real enterprise identity bridge or private-provider acceptance has occurred.

## Evidence

Sixteen tests in `test/wiki-payload-verifier.test.js` use actual SQLite coordination/budgeting, real AES-GCM bytes and separate synthetic originals. They cover complete-source reads and metadata-only reports; a correctly authenticated malicious package containing an undeclared record with a recomputed outer hash; changed/denied sources and subject substitutions; logout/expiry/cancellation/policy/head races; child tokens and missing declarations; single-flight cancellation/reuse; corrupt artifacts and failed key custody; correctly quoted but unsupported publisher synthesis; and the OAuth Drive transport's scopes, folder membership/pagination, bounds, binary errors, cancellation and rate slots.

An isolated module-loader mutation removed the original-field comparison. The changed-original test failed with “Missing expected rejection”; the production file was never modified by that experiment. The normal suite passes. No real Feishu content, live key delivery, HTTP verifier endpoint, multi-machine deployment or independent security audit is covered by these tests.

A second isolated loader mutation removed the transport SHA-256 check. The binary-error test failed because the key callback was invoked once instead of zero times for corrupted ciphertext. The on-disk source was untouched and the normal focused suite passed again. Current full-check evidence is in the development ledger.
