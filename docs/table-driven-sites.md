# 用表格做网站（私有化）：调研与设计方案

目标：在编程任务里说「用这张多维表格做个网站」，得到一个**数值和内容跟着表格走**的站点。多维表格和电子表格当轻量数据库用，人继续在表格里改数据，网站自己跟上。

**前提：这个功能是给私有化部署做的。私有化没有妙搭，方案里不出现任何 SaaS 托管。** 站点由我们自己的控制面托管。

---

## 一、先例调研（不是选型，是借判断）

### 1.1 飞书妙搭做了什么，以及为什么我们用不了

妙搭是飞书 SaaS 的 AI 应用搭建工具。**私有化没有它，`lark-cli apps` 这一整套命令在私有化环境里不存在**，所以它只能当先例看。从我们内置的 lark-cli 1.0.96 的命令和技能文档里读出来的事实：

- **妙搭的数据库不是多维表格，是 PostgreSQL。** 应用有 dev/online 两套库，online 分支禁 DDL，有行级审计、DDL 变更历史、时间点恢复。
- **多维表格是靠同步进去的**：`+db-sync-create`，`source=base` → `target=postgresql`，单向、一次一张表，`mode=streaming` 会持续跟进 Base 的变化。
- **行级权限做在数据层**（平台 SQL 规范里有 RLS 和 `user_profile`），不是做在页面里。
- 可见范围是应用级的三档：specific / tenant / public。

**可以抄的三个判断**（和它的实现无关，和部署形态也无关）：

1. **页面不直接读表格，中间要有一份受控的副本。**表格是事实来源，副本是读缓存。
2. **谁能看见哪些行，是数据层的事，不是前端的事。**
3. **开发态和发布态的数据要分开**，不能让一个还在调的页面打生产表。

**不能抄的**：它的整套托管、同步任务和 PG。私有化环境里这些要么不存在，要么得我们自己造——而我们并不需要造一个 PG 来做这件事，见 2.3。

### 1.2 Codex cloud 的顺序

`learn.chatgpt.com` 上的 Codex cloud：**环境是一等公民**（仓库 + 依赖 + 变量 + 安装步骤，可命名、可共享），先把环境固定下来，再并行发任务，最后按 summary 和 diff 审、开 PR。

对我们有用的不是它的界面，是这个顺序。我们做表格网站正缺中间那层：**先把「数据长什么样」固定成一份契约，Agent 再写界面**。见 2.2。

### 1.3 平台事实（决定新鲜度能承诺到什么程度）

- 飞书平台有多维表格记录变更事件 `drive.file.bitable_record_changed_v1`，**走 Webhook 推送**，且**公式字段的值变化不触发**。
- **我们内置的 lark-cli 事件总线里没有云文档/多维表格事件**（实测 `lark-cli event list` 只有 application / approval / board / card / im / minutes / task / vc 八类，drive 域只开放了评论订阅）。
- 但**私有化和桌面不一样**：控制面是客户自己网络里的一台常驻服务器，本来就有一个对外地址（`IDOU_PUBLIC_URL`，今天用作飞书登录的回调来源）。飞书集群和控制面在同一张网里，**Webhook 回调在私有化是有可能做通的**——这是私有化相对桌面的一个真优势。
- 但别把它当已证实：`IDOU_PUBLIC_URL` 现在只证明**用户的浏览器**能访问控制面（OAuth 重定向是浏览器发起的），不证明**飞书的服务器**能回调过来。这要在具体客户环境里实测。加上「该版本有没有这个事件」也因版本而异，所以它必须是**部署能力**（provider definition 上的一个 capability），不是全局假设；**轮询永远是兜底**。

### 1.4 读表格本身的实测事实（本仓库既有结论）

- **多维表格没有可用来做条件写/条件读的版本号**：`rev` 读出来有滞后（实测约 2 秒），所以现有 `base-records.js` 用**内容摘要**当版本。
- **电子表格的 revision 一次写恰好 +1**，可以当可靠的变化探针。
- 多维表格 `+data-query` 支持服务端聚合，仪表盘类页面不必拉全表。
- 频控：SaaS 上多维表格接口普遍 20 次/秒、超限 429。私有化的上限由客户自己的集群定，但**一个切片一个探针**的纪律不变——绝不能按访客数去打客户的飞书。
- 浏览器**不能**直接调飞书接口：没有凭据、跨域、而且用户令牌绝不能进页面。必须有服务端来读。

### 1.5 我们手上已经有的

- **控制面**：飞书登录、租户/成员/角色、会话、审计、定时任务、SQLite 存储、`IDOU_PUBLIC_URL`。
- **不可变版本包**：清单 + 每文件 SHA-256 + 包哈希，客户端取回时再校验（`app-candidates.md`）。
- **隔离静态运行节点**：固定镜像、无挂载、无外网、只读非 root、网关只交出清单内且哈希一致的字节（`isolated-app-runtime.md`）。注意它是**验收用的一次性节点**（最长 5 分钟），不是托管。
- **无人值守凭据**：`IDOU_SCHEDULE_UNATTENDED` 那一套，正好是「没人登录时也要刷新」需要的东西。
- **部署适配层**：`base`/`sheets` 是 provider definition 上的能力（`baseRecords`/`baseEdits`/`sheets`/`sheetEdits`），部署不支持时由 `FeishuCapabilityUnavailable` 明说。

## 二、设计

### 2.0 它住在哪：「文档网站」是一级分区

**不放在编程任务里。**做一个能给别人打开的网站，和写代码是两件事：想把季度看板发给同事的人，未必是会开编程任务的人。所以：

- **文档网站**（一级导航）拥有「这个网站是什么」：名字、它自己的目录、接不接表格、接哪一片、谁能打开、什么时候发布。
- **编程任务**拥有「这个网站怎么做出来」：页面代码在这里写，发布也从这里走。列表里每个网站都有「用编程任务修改」，直接在它自己的目录上开任务。

**两类网站，一个列表**：

| 类型 | 有没有切片 | 会不会读飞书 | 典型 |
| --- | --- | --- | --- |
| 接表格的 | 有 | 按刷新间隔读 | 季度看板、名单、台账 |
| 只有文件的 | 没有 | 从不 | 自己写的静态小游戏、单页工具 |

切片**可选**是这个分区不裂成两个分区的关键：一个小游戏除了没有数据源，其他地方和看板完全一样——都是一个目录、一个名字、一份要发布给别人的东西。下面 2.1–2.7 讲的是「接表格的」那一半；只有文件的那一半直接从 2.4 的发布形态开始。

（此前 `enterprise-app-platform.md` 写的是「不新增一级导航，入口放在编程任务」。那句话现在只对「写代码」成立；「做一个给别人用的东西」需要自己的入口。）

### 2.1 一句话

**表格是事实来源，不是运行时。**站点由三样东西组成，控制面只做三件事，生成的代码只在访客浏览器里跑。

**站点 = 版本包 + 数据切片 + 权限模式**

| 组成 | 是什么 | 谁产生 |
| --- | --- | --- |
| 版本包 | 不可变静态前端，清单 + 每文件哈希（沿用现有版本候选） | Agent 写，人验收 |
| 数据切片 | 只读契约：哪张表、哪个视图、哪些字段、多少行、多久刷新 | 人在确认卡片上选定 |
| 权限模式 | 跟随表格·表级 / 跟随表格·行级 / 公示（见 2.6） | 人在发布卡片上选定 |

**控制面只做三件事**：

1. 按清单交出**已校验的静态字节**（和现有归档预览同一套校验）。
2. 按切片交出**它自己取来的 JSON**。
3. 按权限模式**问飞书这个访客能不能看**，放行或拒绝。

**它不执行生成的代码**——这条是现有文档里「服务端不是一个混合执行进程」的立场，这个方案不打破它：控制面交出的字节是静态的，交出的 JSON 是我们自己的代码产生的，生成的 JS 只在访客浏览器里执行。

### 2.2 数据契约：三个文件，每次都一样

编程任务的工作目录里放两份产品生成的文件和一个运行时，Agent 只读不改：

```
data/schema.json     切片定义：源、字段和类型、行数上限、刷新间隔
data/snapshot.json   当前数据，形状永远一致
data/table.js        页面运行时：loadData() / onChange(cb)
```

- `schema.json` 的字段类型是**查出来的**（走 definition 的 `baseRecords` 取字段表，或电子表格表头），不是模型猜的。妙搭把类型固化在建表 DDL 里，我们固化在 schema 里，目的一样。
- `table.js` 只有两个函数。**三种运行形态下实现不同，页面代码一个字不用改**（见 2.4）。

这就是从 Codex cloud 借的那层：先固定环境，Agent 再干活。好处是生成结果可复现、可审、可换形态。

### 2.2.5 契约要带的是「含义」，不是一串字符串

第一版契约把每个格子压成 `{text, value}`，`text` 用一个只认标量的函数生成。结果是：**人员、链接、附件全变成空白，日期变成 `1789862400000`，复选框变成 `true`，金额没有千分位**。模版再好也救不回来，它拿到的就是空的。这不是样式问题，是数据在契约这一层就丢了。

现在每个格子带三样东西：

```json
{ "text": "张三、李四", "kind": "people", "items": ["张三", "李四"] }
{ "text": "进行中",     "kind": "option", "value": "进行中" }
{ "text": "查看合同",   "kind": "link",   "href": "https://…" }
{ "text": "2026/9/20", "kind": "date",   "value": 1789862400000 }
{ "text": "128.5",     "kind": "number", "value": 128.5, "style": "currency" }
```

两条规矩：

- **`text` 由部署自己生成**（`renderCell`）。只有它知道这个部署里的人员、附件、公式结果长什么样；没有它就只能渲染标量，而那正是原来那些空列的由来。
- **`kind` 是归一化的含义，不是飞书的原始类型名**。飞书有二十多种字段类型，页面只需要分辨七八种；页面按 `kind` 分支，别人新增一种字段类型时不会碎掉。

呈现放在运行时里一次做对：`Table.paint(节点, 格子)` 按含义画——单选和人员画成标签、链接画成 `<a>`（校验过协议）、日期按本地格式、金额带千分位——而且**永远只用文本节点和它自己建的元素**，因为内容来自别人的表格。Agent 自己写的页面也该调它，而不是各写各的转义。

### 2.2.8 先看见，再决定谁能看

第一版的顺序是错的：建完一个网站，**下一个问题是「谁可以打开」**——一个关于没人见过的页面的权限决定。Kimi 网页和 ChatGPT Sites 都不是这样，它们先把页面摆在你面前，发布是后面单独的一步。

所以建站（非空模版）之后**直接把它打开**，列表每一行也有「预览」。预览用的就是编程任务「成果预览」那套加固：本地回环服务器 + 一次性路径、和发布页**同一份 CSP**、自己的分区、出不了这个 origin、开不了新窗口、下不了东西。

两个刻意的选择：

- **是一个窗口，不是列表上盖一层原生视图**。一来网站本来就是整页的东西；二来**只有窗口是测试读得回来的**——原生视图连截图都证明不了它画了什么。
- **标题由我们写，不由页面写**（`page-title-updated` 挡掉）。窗口上必须说清「本地预览（还没有发布）」，页面自己的 `<title>` 一盖上去，看起来就和已经发出去的一模一样了。

空网站没有 `index.html`，这时不开窗口，而是直说「先用编程任务做出页面再预览」。

### 2.3 为什么不建数据库

妙搭要 PG，是因为它要承载任意应用的任意后端。我们这里的需求窄得多：**一张表的一个切片**。所以副本就是**控制面存的一份 JSON 投影 + 一个内容摘要**，放在控制面已有的 SQLite 里，不引入任何新组件。

只有当切片大到页面拉不动、或者页面需要服务端过滤/聚合时，才把切片**物化成 SQLite 里的一张表**，并开放受限的查询端点（字段和过滤条件都限定在 schema 内，**不接受前端传 SQL**）。这是 R4，不是起手式。

### 2.4 三种运行形态，同一份页面代码

| 形态 | 数据怎么到页面 | 新鲜度 | 能给谁看 | 用什么实现 |
| --- | --- | --- | --- | --- |
| **快照** | 构建时写进 `snapshot.json`，站点纯静态 | 重新发布时 | 拿到包的人 | 现有版本候选 / 单文件发布 |
| **本机预览** | 桌面起一个只读数据端口，页面自己刷新 | 探针间隔 | 只有本人（127.0.0.1） | 复用隔离节点网关那套：随机端口 + 随机 capability 路径 + Host/Origin 校验 + 只接受 GET |
| **控制面托管** | 控制面按切片取数、缓存、按权限模式交给页面 | 见 2.5 | 飞书说能看这张表的人 | **新建**：站点注册 + 只读数据端点 + SSE |

托管这一档是这次真正要造的东西，也是私有化唯一的分享路径。

### 2.5 「跟着表格变」的新鲜度阶梯

**飞书 → 控制面**（取数方向）：

1. **推送（可选）**：部署声明了 `tableEvents` 能力时，用 `IDOU_PUBLIC_URL` 注册 Webhook 回调，收到记录变更就取数。秒级。
2. **轮询（永远可用）**：一个切片一个探针，在控制面跑，不在页面跑。
   - 电子表格：读 revision（写一次 +1，可靠）。
   - 多维表格：`rev` 不可信，用**切片投影的内容摘要**比对；要更省时用 `+data-query` 的聚合当摘要，代价是只能发现聚合会变的改动——**这一点要在界面上说清楚**。
   - 节奏：默认 60 秒，可在切片里调；没人打开这个站点时自动降到 10 分钟；429/错误指数退避。

**控制面 → 浏览器**（送达方向）：这一段完全在我们手里，用 **SSE**。所以即使上游是轮询，**探针一发现变化，已打开的页面立刻更新**，不需要页面自己去轮询控制面。

**没人登录时怎么刷新**：直接复用无人值守凭据（`IDOU_SCHEDULE_UNATTENDED` 那套）。站点的刷新和定时任务是同一个问题——控制面要以某个人的身份持续读飞书——不要再造一套。

**能承诺什么**：有推送时秒级；只有轮询时是探针间隔，界面上写「上次更新：xx:xx」，**任何地方都不写「实时」**。

### 2.5.5 那个时钟在哪里（以及它什么时候不转）

这一节是整个功能的招牌，所以把它单独说清楚。

链条是：**表变了 → 有人发现 → 推给服务端 → 服务端告诉页面 → 页面重取**。后面三段一开始就建好也测过了（摘要比对、`/v1/sites/data`、SSE `changed`、`Table.refresh()`）。**第一段一度不存在**：`refreshSeconds` 存在切片上、印在列表里，没有任何一行代码读它。也就是说「数值会跟着表格走」只在有人手动点「重新读取」之后才成立——这是一句假话，而且它印在界面上。

现在的实现：

- **时钟在桌面端**，每 15 秒扫一遍（15 秒也是切片允许的最短间隔），只挑**已发布且在线**、且自己的间隔已经到点的站去读。没发布的站没人看，读它只是白花飞书配额。
- **用的是本人的飞书身份**，那份身份在这个进程里。所以它**只在应用开着的时候转**——列表上就这么写：「每 N 分钟 自动读取（应用开着时）」、未发布时写「（发布后开始自动读取）」。要做到关掉应用也跟着走，得把这件事搬到控制面并给它一份长期凭据，那是「无人值守定时任务」那条链的事，不在这里偷偷做。
- **一个站读失败不影响别的站**：某张表被收回权限，不该让其他站停止跟随。
- **没变就不惊动任何人**：`putData` 比对摘要，只有真变了才 `notify`。按时钟重读，绝大多数次写进来的都是同一批数字；为这个让每个打开的页面重取一遍整包，纯属浪费。

验证在 `scripts/smoke-sites-desktop.js` 第 12 段：真实应用里发布一个「每 15 秒」的站，然后在表里加一行，**之后不碰任何东西**，等服务端的数据自己变成 3 行。把那个 `setInterval` 注释掉再跑，它会报「表里多了一行，等了 100 秒线上还是旧数据 —— 自动读取没有发生」。

### 2.6 权限：不重写一套，继承飞书那一套

**结论：能，而且不该自己造。**站点的权限直接以飞书为准——谁能读这张表，谁就能打开这个站点；飞书里改权限，站点立刻跟着变。我们自己的设置只能**收窄**，不能放宽。

#### 飞书那一套到底有什么（实测命令面）

| 层 | 粒度 | 对应命令 |
| --- | --- | --- |
| 协作者 | `view` / `edit` / `full_access`；对象可以是人、群、部门、用户组、应用 | `drive +member-add/list/remove` |
| 公开范围 | 组织内可读/可编辑、互联网可读/可编辑、关闭（`link_share_entity`） | `drive permission.public patch` |
| 其他开关 | 谁能管理协作者、谁能复制下载打印、谁能评论、对外分享总开关 | `drive +permission-get-setting` |
| 密级 | 密级标签可以直接拦掉分享（`91009`–`91012`） | `drive +secure-label-*` |
| **多维表格高级权限** | 角色 → **表级**（`read_only`/`edit`）→ **视图级** → **字段级** → **记录级（带筛选条件，就是行级权限）** | `base +advperm-enable`、`base +role-create/update` |

最后一行是关键：**飞书自己就有行级和字段级权限**，条件式的（「负责人 = 我」这种）。妙搭用 RLS 在数据库里实现的东西，多维表格原生就有。只要我们以访客身份去读，这些规则**原样生效，一行代码都不用写**。

#### 三种权限模式，建站时选一种

| 模式 | 谁能打开 | 看到多少 | 能不能写 | 代价 |
| --- | --- | --- | --- | --- |
| **跟随表格·表级**（默认） | 飞书说能读这张表的人 | 和所有者一样（一份共享快照） | 否 | 几乎没有新机制 |
| **跟随表格·行级** | 同上 | 飞书高级权限算出来的那部分 | 可以，写也以访客身份，由飞书判 | 每访客一份缓存、调用量上去 |
| **公示** | 站点自己的名单 | 所有者能看到的 | **永远否** | 多了一份会漂移的权限事实 |

**为什么「表级」这一档几乎不用造新东西**：控制面已经有 [源访问权限探针](feishu-source-access.md)——服务端 OAuth 拿到访客自己的凭据、绑在他的会话上、用**他的**凭据去问飞书「这份文档你有没有权限」，而且只要 `docs:permission.member:auth` 这一个窄 scope，不读任何正文。所以：**用探针判断访客能不能读这张表 → 能就把所有者取来的那份快照给他，不能就拒绝。**授权跟随飞书，缓存只有一份，不需要给每个访客要内容 scope。

**「行级」这一档**才需要以访客身份真正取数（每个访客要授权内容读取 scope）。它换来的是完全的保真：行级、字段级、视图级规则全部继承。

**「公示」这一档**是给「网站要展示的东西，访客在表里本来看不到」的场景（比如只有财务能打开的表，做一个全员可见的汇总看板）。它本质是**把一部分数据重新发布给没有表权限的人**，所以：必须单独一次确认卡片、必须只读、卡片上要写明「以下人员将看到他们在飞书里看不到的数据」。

#### 「读写范围」怎么设

站点自己声明一个**上限**，最终权限 = 飞书的答案 ∩ 站点声明：

- 读：站点只能读切片里声明的字段和行——即使访客在飞书里能看到更多。
- 写：站点默认只读；要可写就在切片里声明**哪几个字段可写**，并且写入一律以访客身份发出，由飞书判他有没有 `edit`。站点声明能把可写字段缩小到一个，但**不能让一个只读访客写成功**。

一句话：**我们的开关只会让权限更小。**任何「更大」的诉求，都要去飞书的权限设置里改。

#### 权限管理界面放在哪

**v1 不做第二个权限编辑器。**站点的权限页只做两件事：把飞书当前的设置**读出来显示**（`+permission-get-setting` / `base +role-list`），和给一个直接跳到这张表权限设置的链接。

理由：权限只能有一个事实来源；而且飞书那套有密级、对外分享、租户策略的联动（`91009`–`91012` 这些错误码就是它们），我们复刻一份就一定会在某个边角上说谎。

以后要在产品里直接改，走**透传**而不是平行实现：确认卡片 → `drive +member-add` 写进飞书自己的权限体系。不新建我们自己的名单。（唯一例外是「公示」模式的名单，它本来就不是飞书的权限。）

#### 几个必须处理的后果

- **字段可能缺**：以访客身份取数时，飞书的字段权限会让某些字段不返回。`schema.json` 是所有者的形状，所以页面必须容忍缺字段——渲染成「无权查看」，而不是报错或空白。这一条要写进编程说明。
- **汇总数会因人而异**：行级权限下，「总营收」这类数字对不同访客本来就不同。这是正确行为，但界面上要说清楚，否则会被当成 bug。
- **公式和引用字段可能泄露**：公式的结果可能由访客看不到的行算出来。这是飞书的模型决定的，不是我们能修的，但选切片时要提示。
- **密级标签**：带密级的表可能根本不允许这样分享，要把 `91009`–`91012` 的原文和下一步照实显示。
- **所有者失权**：探针失败时**停在最后一次成功的数据并标记为过期**，同时通知所有者；不静默继续，也不立刻删页面。

### 2.7 安全边界

1. **单元格内容是数据，不是指令，也不是标记。**
   - 交给 Agent 的表格内容标注为不可信输入（和知识库、文档内容一个待遇）。
   - 生成的页面渲染单元格一律用文本节点，**禁止 `innerHTML`**；来自单元格的链接必须校验协议才能变成 `<a>`；图片只允许白名单主机。写进编程说明，并在发布前对产物静态检查一遍。
2. **凭据不进页面**，也不进版本包。页面只跟控制面的数据端点说话。
3. **取数必须走 provider definition 的 `baseRecords` / `sheets` 部件，禁止直接调 lark-cli。** 直接调就等于把功能钉死在 SaaS 上，私有化跑不起来；部署不支持时要由 `FeishuCapabilityUnavailable` 明说，而不是空白页面。
4. **发布和改权限模式是对外动作**，必须用户在确认卡片上亲手点。卡片写明：源、字段清单、行数、权限模式、多久刷新、用谁的身份读。
5. **「公示」模式要额外一次确认**，卡片上必须出现这句话：以下人员将看到他们在飞书里看不到的数据。
6. **快照是副本**：已经发出去的快照包不会因为后来撤了权限而消失。卡片上要说。
7. **开发态不打生产表**：预览默认走本机形态，托管站点的切片单独确认一次。
8. **写入一律以访客身份发出**，由飞书判他有没有 `edit`；绝不以所有者身份代访客写——那是冒名。沿用现有「提案 → 确认卡片 → 写入 → 读回核对 → 可撤销一次」链路。「公示」模式永远不能写。

### 2.8.5 部署时必须做的一件事：注册访客登录的回调

开启「文档网站」后，访客登录会把飞书的授权码回调到 `<IDOU_SITES_URL>/_auth/callback`。**这个地址必须加进飞书开放平台该应用的「重定向 URL」**，否则访客点开链接会停在飞书自己的错误页上（错误码 **20029**），而且那个页面不会提到我们。

本机实测（2026-09-20）：同一个 client_id，已注册的 `:3041/auth/feishu/callback` 正常进登录页；未注册的 `:3042/_auth/callback` 直接返回 20029 错误页。

控制面启动时会把要注册的那个地址原样打一遍——管理员刚开完开关就能看到，而不是等同事来问为什么打不开。

### 2.9 诚实的边界

- **没有推送时不是实时**，新鲜度 = 探针间隔；界面写「上次更新」。
- **公式字段**：即使用上了平台事件，公式字段变化也不触发，仍要靠轮询。
- **多维表格写后约 2 秒内读回可能还是旧值**（实测）。「改完立刻看到」的演示要考虑这 2 秒。
- **是否支持多维表格/电子表格，取决于该私有化部署**；provider definition 说了算，不支持就明说，不要降级成空白。
- **控制面托管 = 控制面要一直在线**，站点的可用性就是控制面的可用性。这在私有化是客户自己的运维，但要在文档里写明。
- **要的如果只是「把这张表做成能分享的看板」**，先确认该私有化版本自带的多维表格仪表盘分享/应用模式够不够用——可能一行代码都不用写。这个判断放在选切片之前的第一步。
