# 企业技能的管理：审核、版本、可见范围、使用情况

企业技能是技能管理员发布给全公司的技能（签名目录、桌面端核验与任务使用见 [enterprise-skills.md](enterprise-skills.md)）。这份文档讲后台怎么管它：谁能上架、上架前谁审、出了问题怎么回到上一版、谁能看见、有多少人在用，以及每一步留下的记录。

代码：`src/control-plane/skill-governance.js`（管理库里的审核、版本、可见范围、上架人、使用情况）、`skill-catalog.js`（桌面端的上架、读取、上报，从这里经过）、`admin-api.js` 的 `skills` 路由、`admin-ui/pages-skills.js`（后台「企业技能」）。

## 0. 以前缺什么

- 上架直接替换线上版本，不留历史，不能回退。
- 上架没有任何审核：上架人点了就对全公司生效。
- 谁能上架只能写在服务器的环境变量 `IDOU_SKILL_ADMINS` 里，后台改不了。
- 一个技能要么全公司都能看见，要么都看不见。
- 服务端不知道谁在用哪个技能；桌面端的上架、下架不写审计。
- 后台说「每台电脑几分钟读一次目录」，其实没有定时读取（桌面端在打开技能中心、以及每次任务开始一轮时读）。

## 1. 放在哪里（回退安全）

线上技能目录（`IDOU_SKILL_REGISTRY_FILE` 或共享库里的那一条记录）**格式不变**：它的读取是严格校验的，多一个字段，`.270` 及以前的服务端就起不来。新的东西都放在管理库的新表里，旧版本不读它们：

| 表 | 存什么 |
| --- | --- |
| `idou_admin_skill_settings` | 每个企业：上架前是否需要审核 |
| `idou_admin_skill_publishers` | 每个企业：后台加的上架人（和环境变量里的合在一起生效） |
| `idou_admin_skill_versions` | 每个技能上架过的版本（完整内容、谁上架、谁批准、什么时候），每个技能保留最近 5 个 |
| `idou_admin_skill_submissions` | 提交审核的版本：待审核、已通过、已驳回、被更新的提交替代 |
| `idou_admin_skill_visibility` | 每个技能对谁可见：全员，或指定部门 |
| `idou_admin_skill_usage` | 谁在哪天用过哪个技能（只记一次一天，人用不可逆的摘要） |

回退到 `.270`：线上目录照旧；审核中的提交、可见范围、历史都不生效（旧版本不读这些表），技能对全员可见，桌面端上架直接生效。再升级回来，这些设置都还在。

## 2. 上架与审核

- **谁能上架**：环境变量 `IDOU_SKILL_ADMINS` 里的人，加上后台「企业技能 → 谁能上架」里加的人。后台只有管理整个企业的管理员能改名单；环境变量里的人在后台显示为「服务器配置」，后台删不掉。
- **要不要审核**：每个企业一个开关「上架前需要管理员审核」，**默认开**。
  - 开着：桌面端「上架到企业」提交的是**待审核**的版本，线上不变；桌面端提示「已提交，等管理员审核」。
  - 关着：和以前一样直接上线，但仍然留下版本历史和审计记录。
- **审核**：后台「待审核」列出每个提交：技能、版本、提交人、时间、所需工具。打开看：每个文件的全文（只当文字显示，不执行），和线上版本逐文件比较（新增 / 删除 / 修改），所需工具逐项说明它能做什么。
  - **通过**：先把这个提交占下（同一时刻的「不通过」要么在前、这次通过被拒，要么被拒），再上线；上线失败，提交回到待审核。原来的线上版本进历史；同一技能更早的待审核提交标为「被替代」。同一个技能的通过和回退一个接一个做，不会交错。
  - 通过时可以同时定「上线后谁能看见」：默认沿用这个技能现在的设置，新技能可以一开始就只给几个部门（§4）。
  - **驳回**：要写原因；线上不变；提交人在桌面端技能中心看到原因。
  - 审核人不能审自己提交的版本，只要还有别的管理整个企业的管理员——配置里的超级管理员、管理员群的成员、后台授予的管理员，停用的不算；只有一位管理员的企业，自己可以审，审计里写明。
  - **上限**：一个上架人同时最多 10 个版本等审核，一个企业最多 100 个；处理过的提交保留 180 天。
- **下架**：后台或上架人在桌面端下架；下架前线上的那一版先记进历史。后台「企业技能」页有「已下架」一栏，点进去是它的技能页，可以从版本历史重新上线（重新上线前可以先改可见范围）。

## 3. 版本与回退

- 每次上线（直接上架、审核通过、回退）都记一个版本，每个技能保留最近 5 个。被替换或下架前线上的那一版，如果还不在历史里（这个功能上线前就在线上的），先记一笔「版本记录开始前就在线上」，所以升级后第一次换版本也能回到原来那一版。
- 「回到这个版本」：把历史里的那一版重新放到线上（目录的修订号照常加一，桌面端照常核验签名）。回退本身也是一次上线，记审计。
- 已经在跑的任务绑定的是「编号 + 版本 + 摘要」：线上换版本后，旧任务下一轮读不到原来那一版就会停下，要用新版本得新建任务（和以前一样，不会悄悄换版本）。

## 4. 可见范围

- 每个技能：**全员**（默认），或**指定部门**（含下级部门，最多 50 个）。
- 桌面端读目录时，服务端按这个人当前所在的部门（组织架构同步的结果，见 [admin-console.md](admin-console.md) §8）过滤后再签名；看不到的技能，任务也用不了（每一轮都会重新读）。
- 组织架构没同步到的人，只能看到「全员」的技能。后台在设置部门范围时提示组织架构同步的状态。
- 桌面端技能中心里的「货架」（上架人管理用的列表）也按这个过滤，而且只有名称、版本这些，没有文件：文件只在签过名的目录里，按人过滤后才发。上架人看得到整个货架。
- 飞书里已经没有的部门仍留在设置里（没有人在它下面），后台标成「已不在通讯录里」，去掉才会变；不会因此变成全员。

## 5. 使用情况

- 新版桌面端（`.271` 起）用企业技能新建任务时，向服务端报告一次（技能、版本）。服务端只记这个人现在看得见、正在线上的技能，版本取线上的那一版；按「企业、技能、日期（UTC）、人」记一条，人用加了服务端密钥的摘要，不存 open_id；一个人一天一个技能最多计 100 次；保留 400 天。
- 后台显示每个技能近 30 天的使用人数、使用次数和每天的趋势；旧版桌面端不报告，所以 `.271` 之前的数据是空的。

## 6. 记录

审计日志（管理库，见 [admin-console.md](admin-console.md) §6）：

| 动作 | 什么时候 |
| --- | --- |
| `skill.submit` | 桌面端提交审核 |
| `skill.publish` | 桌面端直接上线（不需要审核时） |
| `skill.unpublish` | 上架人在桌面端下架 |
| `admin.skill.approve` / `admin.skill.reject` | 后台审核 |
| `admin.skill.rollback` | 后台回到历史版本 |
| `admin.skill.withdraw` | 后台下架 |
| `admin.skill.visibility` | 改可见范围 |
| `admin.skill.publishers` | 改上架人名单 |
| `admin.skill.settings` | 改「上架前需要审核」 |

## 7. 权限

- 看（列表、详情、文件、历史、使用情况）：后台有 `view` 权限的人，且管理整个企业（部门管理员看不到，和以前一样）。
- 审核、回退、下架、可见范围：`content.manage`。
- 上架人名单、审核开关：`content.manage`，且管理整个企业。

## 8. 还不是什么

- 不审技能的内容是否有害：审核是人看；签名只证明内容没被改过。
- 不按部门分批推送新版本（灰度）：要先给一部分人用，用「可见范围」把新技能只开给试点部门。
- 不能限制已经下载到某台电脑上的内容被人记住或截图。
