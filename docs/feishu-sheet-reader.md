# Feishu spreadsheet workspace: bounded read and Agent context

In a work task, open **文件与协作 → 打开飞书内容**, select **电子表格**, and enter a SaaS `sheets`/`spreadsheets` URL. The application shows an inert grid next to the existing task conversation. Select a worksheet from the returned list, enter an explicit A1 rectangle and choose **读取范围**. Sending with the reference checkbox checked freshly rereads that range before constructing the Agent context.

Select **生成逐格修改建议 · 核对确认后才写入** to request a structured proposal for up to 20 ordinary cells in the currently read range. The conversation shows exact addresses, typed original/proposed values and the baseline revision. Under a valid proposal, **核对并写入飞书表格** writes those values into the original sheet after a confirmation card, and a verified write can be undone once with **撤销这次写入** — see [Writing reviewed cells back](#writing-reviewed-cells-back). Formulas, formatting, merged or complex cells, Base records and Wiki-wrapped sheets are not edited this way.

## Proposal-only boundary

Explicit proposal requests use the existing server-session Responses client with the chat model the server enforces (MiniMax-M3 by default, or GLM-5.3 through a loopback LiteLLM proxy), `tools: []`, `tool_choice: none` and `store: false`; they do not start Codex, enterprise skills or MCP. The source is freshly checked before generation and again before accepting the answer. Task cancellation also aborts the second source read. Model output is parsed as inert JSON and validated against native addressed cells, not renderer-provided originals or model-provided before-values. Unknown keys, duplicate/out-of-range addresses, unchanged values, unsafe integers, oversized responses, formulas and unsupported originals fail visibly. Text, numeric and boolean types are preserved in the preview; formula-like strings cannot be disguised as value edits. No calculations are executed or verified by this draft path, and it must not be reused as a write authorization.

The same pinned CLI's [cells-set implementation](https://github.com/larksuite/cli/blob/03de81c5f3986c2af98a3296328df9c98afabd39/shortcuts/sheets/lark_sheet_write_cells.go) builds range/cells/sheet/overwrite/copy inputs without an expected-revision parameter; local `+cells-set --help` agrees. This does **not** establish that every upstream API lacks concurrency support, but it does rule out copying the Docx revision-conditional adapter onto this shortcut. The write contract below therefore does not pretend the write is conditional: it narrows the window with a fresh read immediately before dispatch, detects a concurrent writer from the revision the receipt reports, and proves the outcome by reading the cells back.

## Writing reviewed cells back

`SheetEdits` (`src/application/sheet-edit.js`) and `SaasSheetEdits` (`src/providers/feishu/sheet-edits.js`) turn a validated proposal into one write. The pinned `+cells-set` cannot make that write conditional, so the contract rests on two behaviours measured against a live tenant: every `+cells-set` call moves the sheet's revision by exactly one however many cells it sets, and its receipt carries the new revision; a `{}` cell inside the written range is left as it was, and a cell written as `""` reads back empty.

1. **Plan.** The changes become the smallest rectangle holding all of them, with `{}` for every cell in between — at most 200 rows and 2,000 cells, so it is one bounded read. The bundled CLI plans `sheets +cells-set --url … --sheet-id … --range … --cells …` with `--dry-run`, and the plan is refused unless it is the `sheet.write` family, not destructive, with a body of exactly `{input, tool_name: "set_cell_range"}` whose input names that spreadsheet, worksheet, range and cells matrix and nothing else (no `copy_to_range`, no sheet name).
2. **Confirm.** The card 「确认写入飞书表格」 names the sheet, worksheet, link, range and the proposal's revision, and lists every cell as `B2  文本 "00123"  →  文本 "00456"`, with the type on both sides: text that looks like a number is a different value. The draft is usable once, and the sheet must still be the open snapshot the proposal was made from.
3. **Check just before dispatch.** A fresh identity check, then a read of the rectangle: its revision R and every cell. Each changed cell must still hold the value on the card, compared with its type, and must not have become merge-related or complex; otherwise nothing is written.
4. **Dispatch.** The intent — range, base revision, and the typed before and after of every cell — is saved in the task as `dispatching` before the CLI runs, the on-screen snapshot is dropped, and the write travels under a one-shot `cli.write` grant bound to the dry run's method, path and body digest. One write per task and per worksheet at a time; nothing is retried.
5. **Verify.** The receipt's revision must be exactly R+1, or the outcome is `conflict`: someone else wrote in between. The rectangle is then read back: changed cells must hold exactly the confirmed values, compared with their types, and every other cell what it held before. A difference is a `mismatch`, listed cell by cell with the confirmed and the stored value — unless the read-back's revision has already moved past the receipt, when nobody can tell whose value it is and the outcome is `conflict` again. Only both checks passing is `verified`. A failure after dispatch is `unknown` — including a receipt whose read-back could not complete, which keeps the receipt's revision — and the message says to check the sheet in Feishu. Measured live: `+cells-set` stores a value by the cell's format, so a number written into a text-formatted cell comes back as text (`数字 5.6` was read back as `文本 "5.6"`); the card therefore warns whenever a change alters a cell's type.
6. **Undo.** A write can be undone once, through its own card 「确认撤销表格写入」, by the same steps in reverse, when what Feishu holds is fully known: a `verified` write, or a `mismatch` Feishu made of that write alone (revision exactly +1, no later revision at the read-back, and only the written cells differ). Undo expects the values the read-back found — the stored ones, for a mismatch — and stops before writing if any cell no longer holds them, so nobody's later edit is overwritten. A cell that was empty is written back as `""` and must read back empty.

`conflict`, `mismatch` and `unknown` are reported and never repaired automatically; a `conflict`, an `unknown`, and a mismatch in a cell the write did not touch cannot be undone from the application. The write is gated like other document writes: under the login bridge it needs `cliDocumentWrites` and the `cli.write` action enabled on the control plane. Pinned by `test/sheet-edit.test.js`; the desktop smoke opens and cancels the card.

## Native adapter and source contract

`SaasSheetReader` is owned by the replaceable SaaS provider, not by the renderer. It invokes bundled CLI `sheets +workbook-info`, `+cells-get`, `+revision-get`, and a fixed `api GET /open-apis/sheets/v3/spreadsheets/:token/sheets/:sheet_id` for layout metadata, always as the current user, with bounded process output/time and cancellation. The native layout endpoint has no registered typed GET command in the pinned CLI; unlike the AI `+sheet-info` tool's opaque response, its public response schema documents merge coordinates. It preserves existing application-to-CLI identity checks at dispatch; it does not provision a CLI login or introduce client-held model/application secrets.

The implementation reads the version-aligned embedded `lark-sheets` and `lark-shared` instructions. Contract details were additionally checked against the official CLI tag **v1.0.78**, commit `03de81c5f3986c2af98a3296328df9c98afabd39`:

- [Range-read implementation](https://github.com/larksuite/cli/blob/03de81c5f3986c2af98a3296328df9c98afabd39/shortcuts/sheets/lark_sheet_read_data.go): `value,formula` requests formula rendering; these values must not be described as independently calculated results.
- [Revision projection](https://github.com/larksuite/cli/blob/03de81c5f3986c2af98a3296328df9c98afabd39/shortcuts/sheets/lark_sheet_revision_get.go): backend read responses carry a revision; a missing revision is an incompatibility, not a safe default.

Workbook metadata is read first. Its revision, the range response revision and a final revision read must match, and the final CLI principal/tenant must still match the initial identity. This is a point-in-time consistency check, not a transactional lock against subsequent edits or permission changes. Sources are read again before sending a referenced question.

Coordinates come from `row_indices` and `col_indices`, not matrix offsets or an ID column. The adapter validates strictly increasing bounded coordinates, rectangular matrix shape, returned `actual_range`, selected sheet and request bounds. Missing rows/columns or explicit truncation make the preview incomplete and block context submission until the range is narrowed and reread. An initial preview spans every column and at most ten physical rows; it is never a claim to have read the complete used region.

`+cells-get` also returns `warning_message`, at the top level and on each range. The pinned CLI's embedded `lark-sheets` skill describes it as something a caller must read before the other fields — where cells really are and how to continue a cut-off read — and live reads carry that advice even when nothing was cut. It is validated (a string of at most 4,000 characters) and kept as the snapshot's `diagnostics`, never as a warning: the checks above already apply it, and it says nothing about the sheet. Earlier builds put it in `warnings`, so the preview's meta line, the 已加入 note and every knowledge search hit showed instructions meant for a program as if something were wrong with the person's sheet. Person-facing warnings now come only from the adapter's own checks — the snapshot note, merge-related cells, complex cells, and truncation read from `has_more`, `truncated` or missing coordinates — so a range Feishu did cut short still says so, in the adapter's words. `diagnostics` is left out of the content hash (the same cells at the same revision are the same content whatever advice came with them) and out of the Agent context. A `warning_message` on `+workbook-info`, which reports sheet IDs that no longer resolve, still fails the read.

Primitive strings, numbers, booleans and empty cells are rendered using `textContent`. Formula strings are displayed without execution. Complex cell values and integers beyond JavaScript's safe precision are visibly marked unsupported; no rich object becomes blank or executable HTML. Style/comment/chart information is not reconstructed. Raw unsupported objects are not forwarded to the renderer or model.

### Merge-related cells and editing eligibility

The [public sheet GET specification](https://open.feishu.cn/document/server-docs/docs/sheets-v3/spreadsheet-sheet/get.md), reached through the official `llms.txt` → cloud-docs module index, defines `data.sheet` and zero-based `merges` coordinates; omitted `merges` explicitly means no merges. The provider validates sheet ID/title/type/hidden state/dimensions against the workbook it just read. Malformed, duplicate, oversized, warning-bearing or mismatched layout responses fail closed. Permission failures do not fall back to the old cell-only path. Layout is read between the same revision/identity checks as cell data; cancellation is propagated to the CLI process.

The public specification does not explicitly say whether end indexes are inclusive. Until a real authorized fixture or explicit upstream contract proves the convention, the provider conservatively marks the union of both interpretations as `mergeRelated`. This may exclude an extra edge row/column; it never expands write permission. Anchors outside the read window still protect related cells inside it. The UI marks these cells **合并关联**, preserves the received value, and does not fabricate `rowspan`/`colspan` or describe a blank placeholder as an independent empty cell. Native proposal validation rejects these addresses, while ordinary cells outside the exclusion remain usable. This is merge-awareness for safe proposals, **not full-fidelity merged rendering or confirmed merge editing**. No source bytes or credentials are added to the server.

## Context and lifecycle

The native service stores a ten-minute, task-bound handle and transient snapshot. Renderer text, ranges or identities cannot replace that snapshot at send time. Current source version/content/identity must still match before producing exact addressed cells and the source link. Closing, navigating away, opening a different document/range, task cancellation or account disposal invalidates/aborts pending work. Late results cannot resurrect a closed handle. Failed source checks clear the current preview rather than using cached authorization.

The conversation receives a bounded `feishu-sheet` context containing worksheet/range/revision, addressed cells, warnings and native identity evidence. Ordinary analysis directs the Agent to analyze only that range, cite addresses/source URL and not write from this read reference. That prompt is not a sandbox: the general task runtime retains its existing tool approvals. The explicitly selected proposal mode is instead the tool-free branch described above. Writes happen only through the confirmed path above, never from the Agent's read reference.

Once the user sends the reference, it is retained in the existing account-local task message store, just like document references; this is not a claim that task messages use encrypted Wiki storage. Opening a sheet does not automatically put it into the Docx-based Wiki or synchronize its contents to Drive. Enterprise retention/encryption controls for all task content, spreadsheet Wiki canonicalization and authorization propagation remain separate requirements.

## Development limits and verification

- SaaS HTTPS `sheets`/`spreadsheets` links only; an optional `?sheet=` selects an ID that must exist in the returned list. Wiki-wrapped spreadsheets and private-provider URLs await their own provider support.
- Up to 200 worksheets, physical grids up to 50,000 rows/200 columns, and at most 200 rows/2,000 cells per explicit preview. Context is capped at 24,000 serialized characters. Larger, malformed or unsupported responses fail visibly rather than silently claiming completeness.
- The knowledge copy is the one caller that goes past a single preview. `readTable` takes a worksheet page by page, each page within the same 200 rows/2,000 cells, checks every page against the revision reported before the first, reads the revision again at the end, and stops at the bounds its caller sets (the knowledge source asks for 5,000 rows, 100,000 cells or 450,000 characters, see [the local Wiki](local-wiki.md)). `revision` is one `+revision-get` as the user, used to re-verify a stored sheet without reading its cells. The preview reaches neither, and neither writes.
- Fixtures exercise actual Electron/native/provider/service/renderer code with synthetic CLI, cipher and model boundaries, and `test/sheet-edit.test.js` pins the write contract. Neither is live SaaS/private-cloud, SSO or chat-model acceptance. See also `scripts/smoke-sheet-desktop.js`.
- A single synthetic-URL CLI `--dry-run` probe unexpectedly reached the existing unavailable Keychain and failed. It was not retried; no reset, downgrade, credential extraction or configuration change was performed. The supplied real document was not accessed or modified.
