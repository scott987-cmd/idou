# Feishu document reader: implementation and limits

The entry lives inside work tasks, not a new primary navigation item. A user can start a task from a document without first making a model request. The reader shares the existing Agent conversation and supports selected-text references.

## Provider boundary

- The SaaS adapter accepts HTTPS docx/wiki links under Feishu, Lark and Doubao domains; it preserves anchors and removes unrelated share query parameters. It never uses the browser cookie jar or requests arbitrary input URLs itself.
- Actual invocation: pinned, hash-checked `lark-cli docs +fetch --doc <url> --as user --doc-format xml --detail simple --format json`. Scope remains the user's supplied URL/anchor. User identity is checked before and after the read.
- Under the [single-login bridge](feishu-cli-bridge.md), identity is resolved through the same server-held OAuth grant with `GET /authen/v1/user_info`; the CLI receives only a sentinel. The fallback profile requires `auth status --json --verify`, `verified: true`, a nonempty user `openId` and `tokenStatus: valid`. Unknown status fails closed. Live SaaS compatibility is not yet demonstrated.
- The private provider should implement `readDocument(reference)` and `documentConnection()` with equivalent semantics; command syntax and authentication storage remain adapter-specific. Do not introduce private/SaaS domain checks in the task controller.
- The returned document includes provider/resource identity, canonical source URL, source revision, content hash, readable text, partial-content flag, embedded-resource limitations and a principal fingerprint. A missing tenant key remains `null`; a principal fingerprint is not enterprise tenant enrollment or SSO proof.

## Reading and referencing

An opened snapshot has a task-bound opaque handle and a ten-minute reference lifetime. It stays in main-process memory, not a server content database. Before a reference is sent, the source is fetched again as the current CLI user. Revision, content, resource target and principal must still match. Permission failures or identity/version changes invalidate the handle and clear the active reader; the client does not return its old snapshot as a successful read.

Accepted complete reads also feed the [automatic local knowledge node](local-wiki.md). When a verified tenant identity and OS encryption are available, that node retains an encrypted, principal-scoped source-evidence page. The document handle itself is still memory-only. Collection does not imply shared Drive publication; model synthesis happens only if the user separately enables the temporary automatic-synthesis setting.

Selected excerpts are reconstructed in the main process from normalized display text, with an 8000-character limit. A whole-text reference is limited to 24000 characters; longer documents require an explicit selection rather than silent truncation. Accepted references, including excerpts, are persisted in the local task history and sent through the configured model gateway when the user sends a prompt. Opening a document makes no model request by default; the optional automatic knowledge-synthesis setting changes that behavior as described above.

The text projection uses pinned [@xmldom/xmldom](https://github.com/xmldom/xmldom) with strict parser errors; DTD/entity declarations are rejected. Source markup is never inserted as executable HTML. Images, attachments, sheets, Base and other embedded resources are labeled as not loaded, not presented as complete content. Styles and reference maps are not preserved for replay because this is a reading projection, not a document rewrite format.

## Reviewed inline editing

Inside **文件与协作**, open a complete document, select an inline phrase, click **引用选中内容**, enable **生成选区修改建议**, and describe the replacement in the task conversation. The initial scope is a unique 1–2000-character phrase in one eligible XML text node, with a different plain-text replacement of at most 2000 characters (empty means deletion). Anchored/partial reads, multiline selections, duplicate matches, titles, links, citations, resource nodes and selections crossing style nodes are rejected rather than rewritten as plain text.

This opt-in proposal path calls the existing server's Responses gateway with the chat model the server enforces (MiniMax-M3 by default, or GLM-5.3 through a loopback LiteLLM proxy when the server sets `IDOU_MODEL_PROVIDER=litellm`), `tools: []`, `tool_choice: "none"`, `store: false`, one non-streaming request and no automatic retry. The output budget is that model's (`sideCalls` in `src/providers/codex/chat-models.js`): at most 3000 output tokens with a 90-second client timeout on MiniMax-M3, 8192 tokens and 180 seconds on GLM-5.3. GLM reasons before every answer and that reasoning counts against the cap, so a MiniMax-sized cap can end its answer `incomplete`, which this path refuses after the call has been billed; the gateway accepts any budget up to its own cap (32768 tokens on GLM) and refuses one above it. A gateway enforcing a different model refuses the request before any upstream call, and the proposal says to reconnect instead of retrying. It does not start Codex, execute a task skill, connect MCP or run shell commands. Only a completed, validated text proposal is accepted; source authorization/handle freshness is checked again before saving the answer. The suggestion is displayed in the same product task conversation. It is not a new turn in an existing Codex runtime thread; ordinary coding/analysis conversations continue using Codex as before. Prior task conversation/skills are not silently sent as extra context on this specialized rewrite path.

**核对并应用到飞书文档** resolves the selected assistant message from native task history, not renderer-supplied target/body data. The original user message must contain the explicit edit intent and native-reconstructed selection. An open, unexpired reader must still match the original resource, revision, content hash, principal and tenant. The SaaS adapter then fetches current `simple` content plus `full` XML and validates unique safe matching without reconstructing or overwriting the whole document.

The native confirmation shows the exact source URL, base revision, before/after and the fact that the original document—not a copy—will be modified as the CLI user. Cancelling makes no write. Confirming repeats source/identity/full-structure checks, persists a `dispatching` marker on that assistant message, invalidates the old reader, and invokes exactly one:

`docs +update --doc <resolved-document-id> --command str_replace --pattern <selected-text> --content @replacement.xml --revision-id <captured-revision> --doc-format xml --as user --format json`

Replacement content is XML-escaped plain text in a private temporary file, never interpreted as user-supplied tags or a path. The pattern is an argv value (no shell), so it can be visible to same-OS-user process inspection; no model/provider key is passed in argv. Temporary files are removed after the CLI finishes. There is no `--yes`, overwrite, permission change, implicit login or retry. A same-task/same-resource in-process lock prevents overlapping confirmed writes; new model sends for that task wait until write verification ends.

Only a user-identity, no-warning `success` acknowledgment carrying a later revision, followed by a fresh read at that revision whose whole projected text equals the confirmed text with only the selected span replaced, is recorded as `verified`. The acknowledgment must name the confirmed document if it names one and report one changed block if it reports a count; the pinned CLI's receipts carry no count, so scope rests on the whole-text read-back, which is the stricter check. Partial success, missing/invalid acknowledgment, timeout or changed post-read state remains `unknown`; no rollback or retry is performed. Intent/result metadata persists in task history. Restored `dispatching` and `unknown` attempts remain blocked for that same suggestion; a new suggestion requires a newly read source and explicit confirmation. This is **local per-suggestion protection, not cross-device/global exactly-once execution**. Failure to save the intent prevents dispatch; a failed result save leaves the durable intent conservative.

The private CLI adapter must provide the equivalent `documentEdits.prepare(expectedDocument, pattern, replacement)` / `apply(prepared, beforeDispatch)` contract. Application/UI logic has no SaaS domain rules. The adapter must call and await `beforeDispatch` before the external write and must never execute an opaque prepared object as a shell command.

### Remaining edit limits

The base `--revision-id` is **not** a concurrency guard. Measured on the real tenant: a `str_replace` and an append sent with revision 3 to a document already at revision 5 were both accepted, each taking it to 6, with no conflict reported. Inside the product the captured revision is pinned by the one-shot write grant; Feishu does not check it. What keeps a confirmed edit off a changed document is the application's re-read and full-structure hash comparison immediately before dispatch, the unique-match requirement and the read-back afterwards. None of these makes the remote operation atomic, and an unknown result may already have changed the document. Rich-format preservation is **not yet validated against live Feishu**. The reader projection is not a full formatting/resource diff. Cross-block/rich edits, sheet/Base operations, granular undo, write audit administration and cross-device reconciliation remain open. New complete reads after verified edits can refresh local Wiki evidence; existing knowledge queries still reauthorize source reads.

The enterprise-login-to-CLI gate opens only for a server-advertised read bridge or the separately configured identity-matching fallback. Bridge writes remain closed. Tests do not bypass this gate in production and do not modify the user's read-only test document.

## Important unfinished boundaries

- Reviewed inline text writeback is implemented as above. Rich Feishu editing, sheet/Base reading/editing, media expansion, undo and live write acceptance are still missing.
- Ordinary document analysis still gives Codex a read-only instruction; that ordinary path is **not** a general shell/CLI write-denial mechanism. Only the explicitly selected proposal flow avoids the tool runtime entirely. General external-tool authorization enforcement remains unfinished.
- The bridge now binds read-only CLI transit to the product login, but live Feishu SSO acceptance, write-scoped policy, persistent sessions and historical-conversation access policy remain unfinished. Invalidation of the active reader does not redact previously authorized excerpts or answers from task/Codex history.
- This read receipt is not permission to publish a document into shared LLM Wiki. Local ingestion now requires tenant/principal metadata and revalidates before search output; shared knowledge publication still requires the complete enterprise audience/ACL/revision policy.
