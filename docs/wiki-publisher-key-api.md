# Publisher key transport

The native `WikiPublisherKeyClient` connects `WikiBundlePublisher` to the server's `WikiPublisherKeyService` and persistent `WikiKeyCustody`. The operations documented here authorize publishing only. The historical service class also supports [separately configured recipient delivery](wiki-recipient-key-api.md); publisher membership alone does not authorize receipt. Neither interface enables the desktop synchronization scheduler. No model/provider/root key is returned to a client.

## Protocol

All routes below are POSTs under `/v1/wiki/keys/`. They require the same current parent Feishu Agent bearer session throughout an operation, JSON, no browser Origin and no nonidentity content encoding. Child model/skill/coordinator tokens and another parent session—even for the same user on a different device—cannot reuse a grant. Current Agent sessions are bearer credentials redeemed through device-key login, **not per-request hardware/device attestation**.

| Action | Input | Result |
| --- | --- | --- |
| `prepare` | `shardKey`, `leaseId`, `fence` | Current lease/source/destination receipt, random grant ID, expiry and a package key |
| `bind` | `grantId`, pre-upload package metadata | The same receipt, `bound: true`; no key |
| `current` | `grantId` | Revalidated grant receipt; no key |
| `resume` | Lease reference and the previously recorded full manifest | Bound recovery grant; no key |
| `release` | `grantId` | Idempotent release of that session's grant |

The server resolves the source declaration from the publisher's current registered lease. `prepare` does not accept source bodies, caller-supplied keys or an arbitrary source list. Custody checks current server processing policy and OAuth source permissions before initially preparing a key. The 60-second grant remains bound to the original parent session, publisher node, generation/fence, sources and Drive destination. The receipt includes a domain-separated parent-token digest for client-side response binding; it is not an independent authorization or signature.

A repeated, still-live unbound preparation returns the **same grant, key and expiry**, not a new key or renewed lifetime. Once bound, preparation no longer returns that key. Repeated identical binding is supported, conflicting binding fails. Current/bind operations recheck the original custody grant. Resume validates the persisted immutable binding and provides no encryption key; it enables recovery of a known uploaded package, not another upload. Publisher/native transport never retries automatically. A lost preparation/binding response stays an interrupted operation; only an already recorded upload follows the existing recovery path.

Grant storage is in memory, capped at 100 live entries; preparation/recovery is single-flight per parent. Requests are limited to 120 per parent per minute (with a bounded parent-bucket map), 4 KiB of metadata and a 30-second processing deadline. Logout, release, expiry pruning and shutdown dispose owned server grants. These are per-process bounds, not a distributed rate limiter. Generic failures reveal no upstream response or key material.

The native adapter validates the receipt against its session, lease, source digest and destination tenant, checks subsequent responses against that exact receipt and rejects unknown fields. It limits responses to 8 KiB, rejects redirects, applies a 15-second request deadline and performs current-session/business-access checks around awaits. Owned response-byte buffers are cleared; package-key buffers are cleared after binding, release, abort, local expiry or close. Its lifetime never exceeds 60 seconds from request start; up to five seconds of future timestamp skew is tolerated only while validating the server receipt, not as an extension of local lifetime. JavaScript strings, transport copies, OS dumps and keys copied by other code are not guaranteed erased.

Only the native process should instantiate this client. Grant IDs and key buffers must not enter the renderer, Agent tool output, journals, logs or environment. The adapter does not claim that a CLI principal and an OAuth open_id are the same identity; the existing business-access gate and the unfinished SSO/CLI bridge remain separate prerequisites for desktop use.

## Explicit server configuration

`bin/server.js --feishu` loads this service only when `IDOU_WIKI_KEY_CONFIG_FILE` names a trusted configuration file. Existing Feishu login/source-access, allowed canonical source origins and Wiki/Drive coordination must already be configured. Each publisher tenant must match the server Feishu app and a configured original origin. There is no default publisher membership or generated root.

Example structure (illustrative paths only; no files are generated by this example):

```json
{
  "schemaVersion": 1,
  "databaseFile": "/srv/idou/private/wiki-keys.sqlite",
  "wrappingKeyFile": "/srv/idou/secrets/wiki-root.key",
  "tenants": [{
    "appId": "cli_enterprise_app",
    "tenantId": "enterprise_tenant",
    "publishers": ["authorized_user_open_id"],
    "processingApproved": true
  }]
}
```

The root file must meet the [vault's private-file requirements](wiki-key-custody.md). `processingApproved` is an administrator's explicit decision to permit processing/publishing, not a user request field or a claim that source view permissions alone grant synchronization rights. The coordinator still independently enforces its current membership and destination policy. The initial configuration authorizes publishing only, not the custody verifier's `verify` operation or recipient key delivery. Configuration is loaded at startup; changes require a restart, which invalidates in-memory grants but preserves wrapped keys. Invalid or missing configuration fails without creating a replacement root.

The optional tenant boolean `automaticPublishingApproved` separately enables [native scheduler scope grants](wiki-scheduler.md#service-backed-scope-authorization). It defaults off and does not waive per-publication source, key, lease or budget checks. Scope routes share live-grant and per-parent request bounds, but their handles cannot be used on key routes. This option does not enable the desktop or link CLI identities.

The gateway listens only on loopback. Remote deployments require TLS termination, disabled request/response-body and Authorization logging, and restricted secret/database access. Native URLs must be HTTPS except for literal loopback HTTP used in local development tests. No deployment setting, real root key or Feishu authorization was changed in this increment.

## Verification and remaining scope

Eight tests were added to the publisher suite: actual local HTTP preparation/binding/publication and another synthetic user's server verification; persistent recovery without another upload; lost key responses; cross-session/child-token/browser rejection; key-free current/resume receipts; response substitution; native grant lifecycle; cancellation during server source checks; and explicit startup configuration (several scenarios share one test). They use the real vault/codec/coordinator/budget and native adapters, with synthetic Feishu transport and disposable roots. They do not represent live enterprise Feishu or desktop/CLI SSO acceptance.

A loader-only mutation removed the grant's parent-session check. A different session then received HTTP 200 instead of 403 and the regression failed. The production file stayed unchanged, and the full normal suite passed. Recipient transport and explicit synthesis trust policy are now documented separately. Desktop IPC/scheduler wiring, real multi-client propagation, KMS operations and live/private deployment acceptance remain open.
