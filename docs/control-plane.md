# Control plane

This document describes the target architecture. Implemented today: a model gateway, an in-memory SaaS Feishu OAuth server, a desktop flow with explicit identity confirmation, short-lived connection activation and account-scoped task storage, an opt-in read-only [CLI bridge](feishu-cli-bridge.md), plus signed skill catalog/preview and confirmed task use with local files or explicitly bound MCP tools. Live SSO acceptance, long-lived device sessions, write policy and complete publishing services remain incomplete. See [implemented login protocol and deployment boundaries](feishu-login.md).

## Feishu-based Agent login

The desktop client starts Feishu OAuth with Authorization Code + PKCE. The callback terminates at the control plane because the Feishu application secret must never ship in the client. After tenant and user validation, the server binds the session to the device public key and returns a revocable session handle for the OS credential store.

The client exchanges that handle for short-lived tokens with explicit audiences such as `codex-model-gateway`, `skill-center`, `knowledge-coordinator`, or `media-gateway`. Tokens carry tenant, user, device, scopes, policy version, and a short expiry. A token for one audience is invalid at every other service.

During SaaS development, the preferred path is the opt-in read-only CLI bridge: the pinned 1.0.78 CLI uses its upstream `authsidecar` protocol while the control plane retains and injects the OAuth user token. There is no token import, browser-cookie copy or client App Secret. Deployments without it may use the older point-in-time matcher with a separately authenticated CLI. A future private CLI may replace the authentication adapter without changing the Agent identity contract.

## Codex model authentication

Use a custom Codex model provider whose `base_url` points to the server's Responses-compatible gateway. Configure command-backed authentication to run `idou-auth-token --audience codex-model-gateway`. The helper reads the device session from the OS credential store and prints a short-lived token. No foundation-model key is present on the client.

The server maps an allowed logical model name to the real provider/model, injects its server-held key, meters usage, and strips secrets from logs. Tenant policy controls model allowlists, regional routing, and retention.

Implemented today: Codex's command-backed auth runs `bin/agent-token.js <session file> <server URL>`, which prints the token from the account scope's owner-only (mode 0600) session file, not from an OS credential store. The gateway maps the one slug it enforces, injects its key and keeps provider errors, keys and prompts out of responses and logs. It does **not** meter usage (its audit hook receives only a request id, session id and status, and `bin/server.js` installs none), and there is no tenant model policy: one server enforces one model for every tenant.

### Chat model provider

Implemented today: one control plane enforces exactly one chat model, chosen by server-only settings. Nothing changes on the desktop's side of the configuration; it learns the enforced slug from `GET /healthz` and accepts only a slug the product ships (`src/providers/codex/chat-models.js`).

| `IDOU_MODEL_PROVIDER` | Client slug | Upstream | Key | Output cap / timeout |
| --- | --- | --- | --- | --- |
| unset or `minimax` (default) | `MiniMax-M3` | `https://api.minimaxi.com/v1/responses`, model `MiniMax-M3` | `MINIMAX_API_KEY` or `MINIMAX_CONFIG_FILE` | 16384 tokens / 180 s |
| `litellm` | `GLM-5.3` | a LiteLLM proxy on the control plane's own machine, `IDOU_LITELLM_BASE_URL` (default `http://127.0.0.1:4000`), model group `IDOU_LITELLM_MODEL` (default `volc-coding`, served by Volcengine Ark) | `IDOU_LITELLM_API_KEY`, or `IDOU_LITELLM_KEY_FILE` | 32768 tokens / 600 s |

With none of these set, requests are forwarded exactly as before and no response normalisation runs (the larger MCP frame bound noted below applies to both routes). The deployment measured on 2026-09-11/12 sets `IDOU_LITELLM_MODEL=volc-agent`, because `volc-coding` was out of monthly quota until 2026-09-17; the desktop sees `GLM-5.3` either way. For `litellm`:

- The base URL must be a literal loopback origin: `http:`, host `127.0.0.1` or `[::1]` (not `localhost` or any other name, which a resolver could re-point), an explicit port, no user info, no path beyond `/`, no query or fragment. The gateway checks the same rule again when it is constructed, before any key can be sent.
- The key file is an absolute path opened without following a symlink, a regular file of at most 64 KB. It holds either just the key on one line, or `KEY=VALUE` lines (comments, blank lines, `export` and quotes allowed) from which `IDOU_LITELLM_API_KEY` or else `LITELLM_MASTER_KEY` is taken, so the proxy's own `.env` can be pointed at without copying the key. An inline `IDOU_LITELLM_API_KEY` wins over the file. The key is read only by the server; it never reaches the desktop, the Codex environment, the bundled CLI, a log or a preflight report, and every configuration error names the setting, never its value.
- Clients still must send `model: "GLM-5.3"` (anything else is `403 model_not_allowed`); the request forwarded to the proxy carries the model group name instead and omits `service_tier`, which is MiniMax's tier vocabulary. The client-facing tier check is unchanged. The field allowlist, output cap (a `max_output_tokens` above it is refused with `400 output_limit_exceeded`; a request without one gets the cap), tenant-hashed `prompt_cache_key`, removal of `client_metadata`, `redirect: "error"`, error redaction, strict response content type and rate/size limits all apply as on the MiniMax route.
- Responses are put back in the client's terms by `response-normalize.js`: a string `model` at the top level and `response.model` become `GLM-5.3` in JSON bodies (buffered up to 8 MiB) and in every SSE frame, and a `response.output_item.added` item missing a field Codex requires is given an empty one (`content: []` for a message, `summary: []` for reasoning, `arguments: ""` for a function call), because Codex drops an added event it cannot parse and then has nowhere to put the deltas that follow. A frame that needs no change passes through byte for byte. The stream order is function-call repair, then normalisation, then MCP name restoration. The MiniMax route has no normalisation step.
- What the real proxy does, as measured against LiteLLM v1.96.0 on 2026-09-11/12, and where each is handled: its SSE frames carry only `data:` lines, with no `event:` line, and the gateway's stream stages read only the `data:` JSON (the function-call repair and the normaliser take the event type from its `type` field, as Codex does), so such frames are handled like any other; a top-level `model` naming the model group rides on every event, not only inside `response`, so that field is rewritten in every frame rather than just in the `response.*` envelopes; `output_item.added` items arrive without the fields above, and with the defaults in place a real desktop reply streamed incrementally (45 → 142 → 275 → 385 → 478 characters) while the same task's 8 tool calls all carried complete arguments; and a `namespace` tool is dropped rather than forwarded, so the MCP flattening below is what lets GLM see an MCP tool at all.
- Found in review rather than measured: the proxy echoes the request's tools into `response.created`, so with a large MCP tool set the first frame of every GLM turn outgrew the 1 MiB frame bound MCP name restoration used to have. That stage now uses the gateway's 8 MiB request bound on both routes, as the repair and the normaliser do.
- `GET /healthz` returns `{ "status": "ok", "provider": "litellm-loopback", "model": "GLM-5.3" }` (`"minimax-cn"` / `"MiniMax-M3"` on the default route) and never the upstream origin, the model group or a key.

The desktop's tool-free side calls (document and spreadsheet proposals, Wiki synthesis) are one non-streaming request each, never retried, with a budget per model in `CHAT_MODELS`: MiniMax-M3 keeps 3000 output tokens for proposals, 2400 for synthesis and a 90-second client timeout; GLM-5.3 gets 8192 for both and 180 seconds. GLM reasons before every answer and the reasoning counts against `max_output_tokens`; a response that runs out ends `incomplete`, which those clients refuse after the call has been billed. The numbers are chosen to fit, not reconciled at run time: each budget is below its route's output cap (16384 on MiniMax, 32768 on GLM), and a budget above it would be refused with `400 output_limit_exceeded`, not trimmed, which the unit tests check by sending both models' budgets through the real gateway each route builds; each client timeout is shorter than its route's upstream timeout (180 s and 600 s), so the client gives up first. An explicit `timeoutMs` passed to either client overrides the model's. The 8192-token budgets have not yet been run live.

Image and speech generation stay on MiniMax on either route, with MiniMax's own key. Video goes to Qwen HappyHorse when `QWEN_TOKEN_PLAN_KEY_FILE` names a Token Plan key, and to MiniMax with the images otherwise; the startup line says which. On the LiteLLM route a configured MiniMax key is still loaded (a broken one stops startup, naming the setting). With `IDOU_MEDIA_ENABLED=1` and no MiniMax key the server still starts, logs that media is unavailable, and answers the media routes with `503 media_provider_not_configured` instead of a 404 that reads as "not enabled".

`npm run preflight` loads the chat configuration exactly as the server will, warns when the key file is group- or world-readable, and asks the proxy's unauthenticated `GET /health/liveliness` (2 s timeout, no key) whether it is up; a proxy that is down is reported but does not block startup. `node scripts/smoke-start-app.js` boots the real launcher on the LiteLLM route against a fake proxy on `127.0.0.1` with a synthetic key file; no real LiteLLM or paid model call is made by any automated test. The paid `--live` smokes and the desktop run against the real proxy are run by hand.

## Skill center

Implemented so far: a server-configured tenant catalog with domain-separated Ed25519 signatures, a separate short-lived skill-read audience, pinned-key verification, explicit desktop content preview and confirmed task use with per-turn release revalidation. Skills can declare local files and specific tools from one explicitly selected account-local MCP connection, including an imported enterprise-broker descriptor; undeclared extra tools on that connection are filtered from the skill task. Publishing, persistent installation and delegated user/resource-policy services remain target architecture. See [current skill-center protocol and limits](enterprise-skills.md).

Skills are immutable, signed bundles. Catalog entries declare version, publisher, digest, compatible Codex/Feishu provider ranges, required tools/scopes, and tenant rollout policy. Clients verify the digest and signature before activation.

Feishu SaaS skills embedded in `lark-cli` are referenced as provider-owned skills rather than copied into the catalog. Customer-authored skills may be stored in the skill center because they are executable configuration, not enterprise document content.

## MCP integration

Manual account-local MCP task connections and explicit signed-skill bindings are implemented in the desktop. The gateway translates Codex MCP namespaces to flat function names on both routes before the upstream sees the request, and restores JSON/SSE function-call envelopes without persisting payloads. On the LiteLLM route this is required, not cosmetic, because LiteLLM drops `namespace` tools. Both routes are verified live: MiniMax-M3 earlier, GLM-5.3 on 2026-09-11/12 with one call to the smoke's local MCP server and one approved call to DeepWiki's public MCP server. Separately, the implemented [enterprise MCP broker](enterprise-mcp-broker.md) uses server-held service credentials, administrator-configured tenant/App-ID/user/tool grants and short-lived connection/tool-scoped client tokens. It terminates independent protocol sessions and closes them on lease/parent revocation. This is not delegated user OAuth or document/row ACL enforcement. Persistent/distributed administration, resource-level policies and production deployment remain unfinished; local confirmation is not a substitute for them.

## Content prohibition

The server now also supports [persistent managed-upload budgets](drive-budget.md): administrator-configured tenant targets/byte limits, a separate Drive lease audience, atomic SQLite reservations and one-shot upload permits. It does not enforce total Feishu storage or independently verify a client's reported file; remote reconciliation, release and quota administration UI remain open.

The control plane may persist identities, policies, skill bundles, opaque resource hashes, Drive tokens, shard sizes, leases, approval/audit records, model usage, and media job state. It must not persist source document text, retrieval chunks, embeddings, prompts containing document text, or generated media bytes. The CLI bridge may stream OpenAPI bytes through memory but has no durable content path. Diagnostic payload capture is off by default.
