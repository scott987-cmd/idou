# Native automatic Wiki publication — development implementation

`WikiPublicationScheduler` connects a bounded authorized source set to the native `WikiBundlePublisher`. It has a service-backed scope adapter and source-authorized key transport, tested together through real local HTTP/SQLite/crypto. A [reading-driven orchestrator](wiki-reading-publication.md) now selects retained local reads and obtains a new scope when the set changes. These are **not enabled in the production desktop**: SSO-to-CLI binding and desktop composition remain missing. Synthetic integration coverage is not live enterprise acceptance.

## Service-backed scope authorization

The existing `IDOU_WIKI_KEY_CONFIG_FILE` tenant row can opt into `automaticPublishingApproved: true`. Omitted/false denies automatic scopes even for a configured publisher; nonboolean values are rejected. This is an administrator's explicit approval for configured publishers to automate processing/publication of their readable originals into the current configured Drive destination. It is not approval inferred from a source ACL or a client `confirmed` flag. Existing deployments remain unchanged. As with the other key-service policies, configuration is loaded at startup; restarting invalidates in-memory grants.

`WikiPublicationScopeClient.authorize(scope, { signal })` supplies the scheduler's `authorizeScope` dependency. The service exposes POST `/v1/wiki/scopes/acquire`, `/current` and `/release`. Acquire accepts exactly the shared normalized `{ shardKey, sourceIds, folderReference }` contract: one shard, 1–200 unique retained-document ID hashes, and the exact canonical folder URL derived from the tenant's configured original origin and current Drive policy. IDs are sorted before hashing. Requests are bounded to 20,000 bytes to accommodate 200 hashes; responses remain bounded to 8 KiB. Unknown fields, another origin/folder, unapproved publisher, browser Origin, child token or invalid parent session fail. No original content, title, model secret or encryption key enters this scope protocol.

The server checks the configured automatic approval plus current publisher processing eligibility, coordinator membership and destination. Its in-memory grant binds parent session, node, scope digest and Drive policy digest for at most 15 minutes and never beyond the parent session expiry. Only one automatic scope can be live per parent; a second acquisition does not silently replace or renew it. Scope and key grants share the service's 100-entry cap and 120 requests/parent/minute bound; namespace and parent checks prevent cross-use of handles. Scope requests have a 30-second server deadline and 15-second native deadline. The client also checks session/business access, exact receipts, expiry and cancellation. There is no automatic retry or renewal; a lost acquire reply can leave an inaccessible grant until logout/expiry/restart.

Each scheduler checkpoint rechecks the grant through the service. Current checks reevaluate automatic approval, publisher membership and policy digest; normal byte usage changes alone do not revoke it. A changed destination or quota policy, logout, scope release or server restart invalidates it. The scheduler's frozen source set prevents newly read documents from silently expanding an ongoing run; changing the set requires stopping/re-authorizing. This still needs discovery-driven scope selection and desktop integration for the intended automatic product workflow.

**Scope approval is not source authorization, source provenance, CLI/OAuth association, a key grant or a server-side restriction of every manual publisher API to these IDs.** It authorizes this cooperating native scheduler's repeated attempts. Every actual publication still uses existing current native source reads, server source registration/permission checks, key custody, leases and budget authorization. Server policy already separately permits the configured publisher to publish manually. Native business gating remains mandatory; unlinked enterprise desktop accounts are not enabled by this change.

## Execution and ownership

`start({ shardKey, sourceIds, folderReference })` validates and snapshots an exact scope, sorts its unique source IDs, and asks an injected native `authorizeScope(scope, { signal })` for authorization. At most 200 retained sources are accepted. New messages/reading activity must not silently expand this approved set; the reading-driven orchestrator releases the old grant and obtains fresh authorization before using a changed set.

The authority returns `{ scopeDigest, expiresAt, assertCurrent, release }`. The digest must be `wikiHash` of the canonical scope; expiry must be a future integer timestamp no more than eight hours away. The authority, not a renderer-provided flag or digest, must independently bind the current enterprise user/device, CLI identity, source permission and destination policy. It must remain able to deny `assertCurrent()` after revocation. Shorter upstream token/key lifetimes still apply. No long-lived session or raw key is stored by the scheduler.

The first check runs immediately after authorization; subsequent checks start two minutes after the previous cycle finishes. The interval is injectable for testing. One worker has at most one cycle in flight, including authorization. The publisher's native journal lock additionally prevents overlapping journal writes from other publisher instances in the same process.

- `ready`: allocate an operation UUID, recheck the grant and call the native publisher. The scope grant is the basis for `confirmed: true`, not arbitrary Agent consent. Publisher lease/key/budget/source checks still apply.
- `unchanged`: schedule another check without an upload or reservation. The status explicitly preserves `remoteBytesVerified: false`; content equality does not prove that the remote file or its key remains available.
- `review-required` or `remote-head`: pause and release the grant. Do not overwrite a remote head, resurrect a tombstone, generate a replacement for an uncertain upload, or automatically call recovery.
- Any failed authorization or operation: pause without an automatic retry. Preserve the active operation UUID when one was allocated; durable publisher metadata remains the recovery authority.

`status()` / `changed` report lifecycle, busy flag, next/expiry timestamps, counters, last outcome/generation and an optional validated operation UUID. They do not expose source bodies/IDs, folder URLs, upstream error text or grant contents. `start`/`tick`/`stop` return status snapshots; callers should still render the current `status()` after concurrent lifecycle changes.

## Stop, expiry and in-flight side effects

`stop()` aborts the scope signal, removes future timers, drains pending authorization/work, releases the grant once and then reports stopped. A late authorization result is released rather than enabling work. `close()` also permanently prevents another start on that worker. A new worker starts idle; this increment does not persist consent or restart schedules automatically. Old timer callbacks are checked against their original run before they can affect a newly started run.

The scheduler passes both an abort signal and a live asynchronous authorization guard into `plan` and `publish`. The publisher checks that guard around source/context checks and after durable intent storage before acquiring a lease. Scope revocation is independent of content-key revocation and native business access. Guard failures remain generic to callers.

Cancellation is not rollback. An already dispatched CLI operation cannot necessarily be interrupted. Its acknowledged file token must still be durably saved; a stop/revocation then prevents subsequent manifest publication at the next authorization check. Charged bytes and uncertain intents remain for reconciliation, not automatic refund or reupload. A stop during initial journal storage can leave an intent with no lease; this too is conservatively retained. These are checkpoint checks, not an atomic transaction with Feishu ACL changes or already dispatched server commits.

## Verification

`node --test test/publication-scheduler.test.js test/wiki-publisher.test.js` covers nine deterministic lifecycle tests and 25 publisher/integration tests. The lifecycle tests reproduce a stale expiry callback stopping a new run and malformed operation metadata entering status before the fixes, then pass unchanged assertions after correction. They also test immutable scope/status snapshots, missing/invalid/expired grants, late grant cleanup, no overlapping work, expiry and cancellation while a read is pending, revocation, unknown/remote heads and restart refusal after close.

The integration tests use real timers, native publisher/coordinator/budget clients, HTTP services, SQLite, encrypted journals, codec and provider file upload/download code with synthetic Feishu transport and key/scope authority. They verify two actual encrypted artifacts and exactly their combined byte charge after a content change; unchanged cycles make no extra artifact. Revocation during upload retains its file token and charge but no manifest, and restarting pauses on the same unresolved UUID rather than uploading again. Stop during intent storage produces zero leases/charges/uploads, and stop during source preflight produces neither journal nor lease/upload.

An isolated test process removed only the publisher's operation-scope guard while retaining business-access and abort checks. The revocation test failed because the coordinator had a published manifest where it required none. This demonstrates that scheduler-only post-call checks are insufficient; the publisher must enforce the live scope during its workflow. No production source was changed by that mutation.

Seven additional integration tests now exercise the configured automatic scope service/native adapter with the real scheduler, publisher, key custody and encrypted artifacts. They cover changed-version publication and unchanged deduplication, default-off policy, exact targets/input, native business denial, revocation during upload, parent/namespace isolation, 200-ID metadata bounds, non-renewal, forged receipts, lifecycle invalidation, lost responses and source denial despite a valid automatic grant. The version test advances a mock Date clock through the production two-minute cadence; it is not a wall-clock throughput benchmark. An initial rapid-tick run correctly exhausted the 120/minute quota; no quota was raised or bypassed to make the test pass. An isolated loader mutation removed only explicit automatic approval, and the default-off denial test failed with a missing expected rejection; production source was unchanged.

This is not live Feishu, process-crash, multi-machine or UI acceptance of automatic publishing. Full-product remaining work includes identity binding, deployed administrator controls, discovery-driven authorized source selection, desktop automatic publishing/recipient retrieval, cross-device version proof, revocation/deletion propagation, quota reconciliation/GC and packaged SaaS/private-cloud acceptance. See [publisher](wiki-publisher.md) and [bundle security boundary](wiki-bundles.md).
