# 服务状态：每个进程、容量、模型、自检历史、备份与告警

后台「服务状态」页给管理整个企业的管理员看：服务现在好不好、哪里不好、从什么时候开始、要不要加机器。以前这一页只有协调副本自己内存里的最近一次自检和「模型能不能答」，看不到两个模型副本和执行节点，重启就清空，也没有任何历史。

代码：`src/control-plane/process-status.js`（每个进程的心跳与流量、自检和告警的记录、页面读取）、`health-monitor.js`（自检，新增「备份」「服务进程」两项）、`model-gateway.js`（每个请求怎么结束、多久开始回答）、`run-queue.js`（执行节点的心跳表）、`bin/backup.js`（`status.json`）、`admin-api.js` 的 `GET system` 和 `POST system/alerts/test`、`admin-ui/pages-system.js`。

## 1. 每个进程的心跳

协调副本、每个模型副本（`--role api`）、每个执行节点（`--role worker`）每 20 秒写一行心跳到共享库：

| 字段 | 内容 |
| --- | --- |
| 进程 | 角色、主机名、名字（`IDOU_PROCESS_NAME`，没有就用角色 + 端口）、进程号、启动时间、版本 |
| 资源 | 常驻内存、堆、事件循环延迟（p99） |
| 负载 | 这个进程持有的会话数、正在答的模型请求和上限、飞书命令代理、定时任务运行和上限（有执行池时运行由执行节点报，协调副本不重复算） |
| 模型 | 这台进程看来哪个模型答不了、原因、什么时候再试 |

流量另写一张表（§2）。会话数不跨进程相加：同一个会话会出现在几个副本上。

- 协调副本和模型副本写管理库的 `idou_admin_processes`；执行节点的数据库账号只能碰定时任务队列，写的是单独一张 `idou_run_worker_beats`（部署时执行一次 `deploy/server/worker-role.sql` 授权，见 §7）。
- 判断：1 分钟内有心跳 = 在线；超过 1 分钟 = 可能卡住；超过 3 分钟 = 掉线。正常停止的进程把自己标成「已停止」（不删）。同一台机器上同名同角色、在它最后一次心跳**之后**启动的进程，算它的接替者——哪怕它看起来还在线（崩溃后一分钟内是这样）：被接替的不再列出，没有正常停止的计为「意外退出后重启」。比它早启动的同名进程不算接替者。协调副本同时只有一个，另一台机器上接手的协调副本也算接替者（它从拿到租约那一刻算启动）。一天没有心跳的行不再读出，一天后由协调副本删掉。各进程版本不一致时提示（升级到一半时正常，长时间不一致就是没重启完）。
- 新增自检「服务进程」：有进程掉线 = 严重；停止后 3 分钟没有接替者（新版本起不来，或有人停掉了）、可能卡住、或同一台机器上有两个在线进程同名 = 告警。和别的自检一样连续两次才告警。有意停掉的进程一天后不再提示。
- `IDOU_PROCESS_NAME` 只写在各进程自己的配置里（例如 `api-1.env`），别写在所有进程共用的配置里：同名的进程一个掉线时看不出来。不设时是角色加端口，各不相同。
- 一天没心跳的进程行自动清掉。

## 2. 流量与模型

- 模型网关记下每个通过登录检查的请求怎么结束——成功、用户停止（客户端先断开）、客户端错误（4xx）、被这个服务端限制（每分钟次数、同时在答、个人并发、额度）、上游出错（上游的 5xx、上游的 429、超时）——以及从收到请求到上游模型开始返回用了多久（分档：0.5、1、2、3、5、10、20、30、60 秒和更久），按「5 分钟 × 进程 × 模型」累加，写进 `idou_admin_traffic`，保留 30 天。每行只由写它的那个进程改，写的是这一档的当前总数，不是增量。
- 页面显示：近 1 小时和 24 小时，每个模型的请求数、出错率、开始响应用时（中位数和 95%，取所在档的上限，超过 60 秒的写「1 分钟以上」）；24 小时每小时的请求柱状图；被拒的请求按原因（每分钟上限、服务器满、个人并发、额度）。用户停止不算出错。
- 「模型能不能答」汇总所有副本：任何一台标记它答不了，就显示哪台、什么原因、什么时候再试。

## 3. 自检历史与故障时间线

- 每 5 分钟的自检结果存进 `idou_admin_health`（每项一行），保留 30 天。
- 每一项显示最近 24 小时的状态条（每格 30 分钟，取那段时间最差的结果）。
- 「故障时间线」：近 7 天每次某项变成告警或严重、什么时候恢复、持续多久。
- 告警发出的消息也记一行（发给几个人、成功与否），页面上能看到最近发过什么。

## 4. 备份

- `bin/backup.js` 每次运行在备份目录写 `status.json`（开始与结束时间、成功与否、文件数、大小、是否封存、是否送到飞书、错误原因）；它不含任何数据，对服务账号可读。
- 服务端配置 `IDOU_BACKUP_DIR` 后，新增自检「备份」：最近一次成功的备份超过 36 小时 = 告警，超过 72 小时或最近一次失败 = 严重。
- 页面显示最近一次备份的时间、结果、大小、是否封存、是否送出。

## 5. 告警

- 页面显示告警开没开（`IDOU_ADMIN_ALERTS`）、发给谁（配置里的超级管理员 `IDOU_ADMIN_USERS` 和管理员群 `IDOU_ADMIN_CHAT` 的成员；后台授予的管理员收不到）、最近发过的告警（送到几个人，一个都没送到的标红）。
- 「发送测试告警」：给当前登录的这位管理员自己私聊一条测试消息（不发给别人），确认机器人和权限都通；消息里写明真正的告警发给谁、开没开。每人每分钟最多一次；需要管理员或超级管理员（审计员只能看），写审计 `admin.alerts.test`（发出或没发出都写）。没有飞书应用时这个按钮不出现。

## 6. 容量与建议

把所有进程的心跳加起来：在线会话、正在答的模型请求 / 总上限、定时任务运行 / 上限、队列里等着的运行、近 1 小时因容量被拒的请求。被拒的请求多、或正在答的长时间接近上限时，页面直接说「建议加一个模型副本」或「建议加一个执行节点」。

## 7. 部署

- 新表都由协调副本建（管理库，名字随库：改名前建的库是 `mydoubao_*`）。
- 执行节点的心跳表要授权：新版协调副本启动（建表）之后，在服务器上再执行一次 `deploy/server/worker-role.sql`（可以重复执行；改名前建的服务器上有 `mydoubao_worker` 角色时，脚本授给它，不另建 `idou_worker`）。授予的是心跳表的插入、改时间和状态，以及只读 `worker` 一列：执行节点读不到别的节点的状态，也删不了行（停下时标成已停止，一天后由协调副本清掉）。执行节点共用一个数据库角色，所以一个被攻破的节点能改别的节点那一行；页面只取符合执行节点名字格式的行，状态只取运行数和内存。没执行时，执行节点照常工作，日志说一次「写不了心跳表」，页面显示「执行节点没有上报心跳」；授权后不用重启，下一次心跳就写进去。
- 备份检查要配置 `IDOU_BACKUP_DIR`（服务器上是备份的 `--to` 目录）；没配置时这一项不出现。配置后先手动跑一次备份（`systemctl start <备份单元>`），否则到下一次定时备份之前，这一项会提示「还没有备份记录」。备份程序把数据库地址里的密码（用户部分或 `password=` 参数）放在 `pg_dump` 的环境变量里，不在它的命令行上；地址的其余部分原样交给它（libpq 认的写法都行）。备份程序自己的命令行上也别放密码：用 `--postgres-env IDOU_DATABASE_URL` 从环境变量读地址。失败原因里的数据库地址，写记录和读记录时都去掉。
- 回退：旧版本不读新表；执行节点授权多一张表无害。

## 8. 还不是什么

- 不是完整的监控系统：没有任意指标查询、没有自定义告警规则；要那些就用 `/metrics`（Prometheus 格式）接企业自己的监控。
- 进程、流量、备份是整个服务端的：一台服务端服务几个企业时，每个企业管理整个企业的管理员看到的是同一份。
- 心跳表在共享库里：共享库本身挂了，这一页也看不到别的进程（自检里的「共享数据库」会是严重）。
