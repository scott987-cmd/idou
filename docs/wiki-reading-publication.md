# Reading-driven publication orchestration

`WikiReadingPublication` connects actual retained local document reads to the existing service-backed scope client, publication scheduler and encrypted publisher. The caller supplies only a shard and destination folder, not a hand-picked source ID list. The [desktop composition](wiki-desktop-publication.md) now retrieves that target from approved server policy and owns the worker per account; it is not enabled for unconfigured or unlinked enterprise accounts.

## Source selection

Successful `LocalWiki.observe` commits record an additive `localReadAt` timestamp in the encrypted local page. This includes the existing accepted document-read event path and the message-discovery worker's successfully read originals. It does not import chat message bodies. Partial, failed, out-of-order or unretained observations cannot establish a new eligible source.

`LocalWiki.publicationCandidates({ signal, expectedIdentity })` serializes with local writes and returns only a fresh identity snapshot, sorted source ID hashes, `selectionKind: "retained-local-reads"` and `permissionsChecked: false`. It filters for the current principal/tenant, valid local-read timestamps and the existing retention/count bounds (normally 30 days / 200 pages). Identity is checked before and after storage access. It does not fetch original bodies, call a model, upload or turn previous ACL evidence into current permission. Actual source reauthorization remains inside export/registration/key/publisher paths.

Search, export and encrypted restart preserve a legitimate local-read timestamp without refreshing it. Imported-only pages have none and remain excluded even after knowledge search or restart. Importing an already locally read source may preserve its old timestamp, but does not make that reading recent again. Opening/reading the authoritative source afresh can establish eligibility. This prevents automatic client-to-client re-publication loops caused solely by importing a package. The optional field stays within the existing local snapshot version; old records lacking it remain usable for search, but conservatively require a new local read before automatic publishing. Old app versions may drop this new field on rewrite; no migration invents a prior local read. Package format and server metadata schemas are unchanged.

## Worker lifecycle

Construct the worker with `wiki`, the actual `publisher`, `authorizeScope` (normally `WikiPublicationScopeClient.authorize`), and a mandatory native `businessAccess` check. `start({ shardKey, folderReference })` snapshots the target and current local identity. One outer timer drives the two-minute cadence; the inner `WikiPublicationScheduler` has no independent timer. Manual calls to `tick` share one in-flight promise, so reading selection and publication cannot overlap within this worker.

Each cycle derives candidates again. Empty selection waits without key acquisition or upload and releases any previous scope. A changed set releases/drains the old scope and obtains a new server authorization before publishing. An unchanged set retains its still-current grant and uses the publisher's existing version preflight/deduplication. Reads accepted during a dispatched upload do not change that frozen package; they join a later reauthorized cycle. Counts and last operation status are metadata-only copies, not references to mutable source or grant objects.

Waiting has the existing eight-hour local ceiling; once a server grant is obtained, the worker's deadline is reduced to that grant's expiry (currently at most the 15-minute parent session), never extended by later selection changes. A separately verified desktop online-login checkpoint can replace this deadline within the original local ceiling and force a fresh scope for the next cycle, only while no inner publication is in flight. It preserves counters and does not restart paused/stopped work. The worker itself does not renew login. Identity changes, business denial, unavailable storage, source/key/permission failure, expired grants, unknown uploads and remote-head conflicts pause the run. Stop/close cancel selection, stop the inner scheduler, drain ongoing work and clear timers; an abort-ignoring late selection cannot obtain a new grant. Old expiry callbacks are bound to their own run and deadline and cannot stop a restarted or refreshed run.

An empty/expired local reading set does **not** delete originals, remove cloud package bytes or publish a tombstone. A failed source read pauses instead of silently publishing a partial set. An already dispatched upload may leave a charged artifact and durable receipt; existing recovery rules still forbid automatic replay. Cross-device ACL/deletion propagation, automated reconciliation, safe garbage collection and richer partial-unavailability policy remain unfinished.

## Evidence and limits

- Local Wiki tests cover encrypted restart/search preservation, legacy/expired/other-account exclusion, cancellation, identity races, closed storage and the fact that candidates do not grant export permission.
- Worker tests cover empty-to-active selection, fresh authorization on expansion, immutable scope, account/business rejection, no restart on ambiguity, single flight, stop during selection and publication, expiry and stale callbacks.
- Actual document-service read events feed real LocalWiki, HTTP scopes, keys/coordinator/budget, codec and publisher in integration tests. They produce two encrypted versions after a new reading, make no duplicate unchanged upload, exclude import-only evidence after actual recipient import/restart, and stop or release on source denial/account/retention changes. Feishu transport and identities are synthetic; cadence is tested using a mock Date clock, not a performance benchmark.
- An isolated loader mutation removed the local-read eligibility condition. The import-only regression returned a source ID instead of the required empty list and failed. Production source was unchanged.
- The existing Electron document/knowledge regression still verifies normal reads, encrypted restart, reauthorization and cited synthesis with synthetic CLI/model/cipher inputs and no live writes or paid calls. It does not exercise a production desktop automatic-upload entry.

Remaining product work includes safe shard re-enrollment across device changes, shared CLI login, persistent/offline authorization, live message-to-cloud acceptance, fleet-scale receiver scheduling, ontology/semantic retrieval, distributed authorization propagation and SaaS/private packaging. Bounded online renewal and approved desktop receiver discovery are implemented separately, not production acceptance. Enterprise business gating remains; no deployed user's synchronization has been configured by this development work.
