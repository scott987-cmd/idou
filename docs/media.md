# Cowork media generation

Image and video requests share a job state machine:

```text
queued -> running -> awaiting_acceptance -> uploading -> available
                    \-> failed
queued/running -> canceled
```

The request includes tenant/user identity, kind (`image` or `video`), prompt, optional source asset references, model policy class, and idempotency key. Server policy decides the concrete model and provider. Long-running video jobs are polled or streamed by job ID and survive a client reconnect.

Provider output is short-lived. After client-side MIME, size, and safety validation, accepted output is uploaded with the Feishu Drive provider and the final response contains the durable Drive token/link. Rejected or expired output is discarded. Prompts and thumbnails are not retained by the control plane unless a tenant explicitly enables a bounded audit policy.

## Implemented server increment (2026-09-09)

The state machine above is the product target, **not a claim that enterprise Drive delivery is complete**. The server implements text-to-image and text-to-video submission, status retrieval and local cancellation. The desktop has work-task media controls, native cost confirmation, resumable records, isolated temporary preview and a confirmed new-file Drive upload path gated by a persistent server-managed budget. Enterprise login-to-CLI binding, trusted remote quota reconciliation, live upload acceptance, Agent media invocation and reference-image support remain unfinished. No media bytes are downloaded or stored by the control plane.

Enable explicitly with `IDOU_MEDIA_ENABLED=1` when launching `node bin/server.js --feishu` (or `--dev` for loopback development). When omitted the media routes do not exist. It uses the existing server-only domestic MiniMax key loader. Images keep that MiniMax key, and MiniMax as their provider, whatever chat model the server is configured for: choosing GLM-5.3 for chat (`IDOU_MODEL_PROVIDER=litellm`) does not move image generation, so enabling media still needs `MINIMAX_API_KEY` or `MINIMAX_CONFIG_FILE` alongside the LiteLLM key; without one the image routes answer `media_provider_not_configured` and chat is unaffected.

Video is made by Qwen HappyHorse on Alibaba Cloud Model Studio's Token Plan when `QWEN_TOKEN_PLAN_KEY_FILE` names a file holding one `sk-sp-` Token Plan key (the standard since 2026-09-23); without it video stays on MiniMax. The file must be a regular file, not a symlink, and not readable by other users. The Token Plan is for interactive use only, which this service keeps to: every video is submitted after a person confirmed it on a card, and at most four run at once. Do not put a provider key in a client connection file. In enterprise mode, this flag enables the capped beta for **all verified Feishu identities accepted by the existing login policy**; separate per-tenant model/budget administration is still required before general release. Development identities are rejected unless the service is explicitly started in development mode.

The fixed server policy is one `image-01` image with a supported aspect ratio, and one video: `happyhorse-1.1-t2v` at 1080P / six seconds / 16:9 on Qwen, or `MiniMax-Hailuo-2.3` at 768P / six seconds on MiniMax. Clients cannot supply the model, upstream endpoint, callback URL, output count, duration or resolution. Images request the provider's watermark; videos do not ask for a visible one. This is not a certification of video watermarking, content safety or regulatory compliance. Prompt optimization is disabled for predictable input; prompts exist only while the provider request runs and are not put in the job map, logs or disk.

### Native API contract

All routes are `POST`, JSON only, bounded to 16 KiB, reject browser Origin headers, and return `Cache-Control: no-store`. These are native-client APIs; `confirmed:true` is a declaration. The desktop implements a native dialog before submission, but other API clients must implement their own trusted confirmation; the server cannot attest that a human clicked it.

| Route | Authorization | Body / result |
| --- | --- | --- |
| `/auth/media-token` | Valid model-gateway parent token | `{kind:"image"}` or `{kind:"video"}` → five-minute, parent-bounded `media-service` token, kind, `instanceId`, verified owner metadata and `offer` — the provider (`minimax` or `qwen`), model and, for video, seconds, resolution and aspect ratio that a job would use |
| `/v1/media/jobs` | Matching-kind media token | `{kind,prompt,idempotencyKey,instanceId,confirmed:true,aspectRatio?,model?}` → 202 job snapshot; same retained key/input returns the same job with 200. `model` is the offer's model the person confirmed; a different one, or none while the server would not use the model older clients name (`image-01`, `MiniMax-Hailuo-2.3`), is refused with 409 `media_model_changed` before anything is sent upstream |
| `/v1/media/job` | Matching-kind media token, same owner | `{id}` → current snapshot; may start a bounded video status check |
| `/v1/media/cancel` | Matching-kind media token, same owner | `{id}` → locally canceled snapshot; no claim that the provider stopped or refunded |
| `/v1/media/lookup` | Matching-kind media token, same owner | `{idempotencyKey,instanceId}` → original snapshot without submitting generation; for a lost initial response |

Use a new UUID v4 for each explicitly approved generation. Retain that UUID **and its original `instanceId`** before sending. A retry must keep both and the exact same input; changed input returns 409. A different server instance rejects a stale submission with `media_server_restarted_review_required`, not an automatic new paid POST. Do not substitute the latest instance ID to get around this result. After a lost response, reuse the same request only within the stated retention window; after expiry, ask the user to review provider completion/cost rather than silently regenerate.

The media token cannot call the text model, skill catalog or MCP, and a model token cannot submit a media job directly. Parent revocation also invalidates its media leases. One kind's lease refresh does not revoke the other kind or skill/MCP leases. Jobs are owned by verified provider/tenant/app/user identity, not caller-supplied identity or provider task IDs. A newly authenticated device for the same owner can retrieve an existing job by ID; a different owner receives 404. Token expiry/logout removes access, but does not promise to cancel already submitted provider work.

Snapshots expose `running`, `awaiting_acceptance`, `failed`, `submission_unknown`, `canceled` or `expired`; **never `available`** in this increment. Every snapshot says `persisted:false`. A temporary result contains a HTTPS URL, optional provider-reported byte count and conservative one-hour local expiry. This URL is an authenticated user's sensitive temporary reference, not a Drive URL. The native downloader applies separate address/size/MIME/signature checks and never attaches the provider credential.

## Desktop work-task workflow

Use **工作任务 → 创作图片或视频**, or an existing work task's **图片与视频** tab. This does not add a top-level sidebar section. The right-hand Agent conversation can discuss the creative brief; it does not yet receive the media automatically or invoke generation itself. Generation is explicitly performed in the left-hand form.

1. Choose image/aspect ratio or video, enter a prompt, and confirm in the native dialog. The dialog displays the configured server, fixed model/quality, exact prompt, cost/external-processing warning and temporary-storage boundary. Cancel dispatches no generation. The native process rechecks the session after confirmation.
2. The client synchronously reserves an account/server-bound UUID and original server instance in a mode-0600 journal **before** the generation POST. Prompts, temporary provider URLs and credentials are not written to that journal. An accepted Drive delivery adds resource identifiers, folder URL/title, CLI tenant/principal fingerprint and local-byte hash, not secrets or bytes. Metadata is atomic-renamed and flushed, including directory sync on POSIX. A failed reservation does not dispatch generation. A lost response remains `unresolved` and is recovered through read-only lookup; no automatic POST retry exists.
3. The visible media panel refreshes status every ten seconds; connection errors pause it until manual refresh. Refresh/renderer reload/client restart load the same records, and a changed server epoch becomes `server_lost`, not a new generation. The UI shows the latest twenty records per task; the account-local journal currently has a 200-record hard cap. Archival/record administration is still required for long-term production use.
4. **打开临时预览** freshly authorizes the result and downloads it in the native process. Only standard-port HTTPS with public IPv4 DNS answers is allowed; the address is pinned for the request while hostname TLS validation remains enabled. Private/reserved addresses, redirects, compressed HTTP bodies and oversized results are refused. There are no cookies, authorization headers or browser session attached. Image previews are limited to 12 MiB (PNG/JPEG/WebP MIME plus signature); video to 100 MiB (MP4 MIME plus `ftyp`). These are bounded-format checks, not full malware/content-safety scanning or a decoder sandbox certification. IPv6-only CDNs and other formats remain unsupported.
5. Validated bytes are placed in a private temporary directory and opened in a separate sandboxed Electron window with no preload, Node, Agent bridge, permissions, navigation or network access. Its network allowlist permits only its two exact local files. At most two previews/download reservations can exist. Closing a preview cleans its temporary cache; account/server switching and app shutdown close previews. A crash can leave temporary cache behind; startup orphan-cache reconciliation remains open. This is a local preview cache, **not canonical artifact storage**.
6. **停止等待 / 丢弃临时成果** requires native confirmation, invokes local server cancellation, and retains the local metadata. It does not assert provider cancellation/refund or delete a Feishu document or an already saved Drive file.
7. To save, enter an explicit Drive folder URL and click **保存到飞书云盘**. The native process resolves the folder under the verified CLI user, downloads/validates the temporary media and asks for confirmation of folder, CLI tenant/principal fingerprint, new filename, actual byte count, local SHA-256 and sharing boundary. Declining performs no upload. Enterprise mode remains blocked until its login identity is linked to the CLI; a development connection is not proof of that link.

The renderer receives only sanitized job metadata; provider keys, parent/media credentials, temporary result URLs and resolved Drive file links remain outside IPC responses. The folder URL entered by the user is visible in its form. The native account-bound journal is not protection against another process running as the same OS user. Downloads have a 60-second timeout; upload CLI invocation has a 180-second limit. Quit may wait for a running native operation. Expired/revoked sessions require reauthentication before new result access.

### Confirmed Drive delivery and recovery

The product uses a replaceable `resolveFolder / upload / verify` provider contract. SaaS-specific URL parsing and CLI arguments stay in `SaasDriveFiles`; a private CLI can implement the same contract. The pinned, bundled CLI is used with its existing profile and **user** identity, an explicit folder and relative temporary filename. It never defaults to root, overwrites a file, switches to bot, grants permissions or supplies `--yes`. Readable folder metadata is not evidence of write permission; the actual upload enforces that permission.

The native journal progresses `prepared → uploading → verification_pending → available`, separately from the server generation state. New saves require [server budget configuration](drive-budget.md): atomic byte reservation plus a once-only dispatch grant before the CLI call, and an idempotent receipt report after native verification. The journal records an acknowledged `file_token`, then the client lists the exact folder and requires matching file token/type/name/location before reporting `persisted:true`. The saved SHA-256 describes local uploaded bytes; **remote bytes are not downloaded or hash-verified**. Server media snapshots still say `persisted:false`: a budget receipt is client-reported metadata, not independent server verification of an artifact.

If upload acknowledgment is lost, the journal stays `upload_unknown` (or `uploading` after a crash). The UI offers **核查原文件夹** and never automatically uploads again or adopts an arbitrary filename match. If a token was acknowledged but verification failed, **核验并打开文件** retries only reads. These receipts survive a client restart. **打开云盘文件** rechecks the CLI identity and exact folder listing before opening the provider's validated HTTPS URL externally. Deletion, moves and permission changes prevent that open; historical saved status is not an authorization grant. Same-user local journal tampering and concurrent multi-device uploads are outside this increment's protections.

Persistent tenant-wide managed-upload reservation is connected; it does not enforce total Feishu capacity or uploads by a modified client. Trusted remote reconciliation/release, remote-byte verification, unknown-upload automatic reconciliation, orphan temporary-upload cleanup after a crash, installer packaging and real private-provider acceptance remain open. The native confirmation shows administrator-configured budget and remaining bytes and explains this managed-upload boundary.

### Cost, failure and retention limits

- Maximum four submissions per owner per rolling hour, twenty for the process per rolling hour, one running job per owner, four globally and four in-flight provider operations. Failed/canceled/uncertain submissions still consume the hourly allowance. New tokens/devices do not reset an owner's allowance within a running server.
- Video reads occur no more often than ten seconds per job. Transient query failure preserves the original provider task ID and permits later read-only retry; it never resubmits generation. No fabricated percentage is shown. A client disconnect does not cancel a submitted job, and a reconnect can resume polling with a valid lease and saved job ID.
- A timed-out/lost/invalid POST response becomes `submission_unknown`, since billing/execution may already have happened. No provider POST retry is performed. A structured provider rejection becomes `failed`. Provider diagnostics, headers and known raw key echoes are not returned to clients.
- Cancellation aborts local network work, hides results and retains the idempotency reservation; late completion cannot resurrect it. There is no verified MiniMax upstream cancellation API in this implementation. `providerMayContinue` is a conservative warning, not an upstream state assertion.
- Job metadata and hashed idempotency reservations are **memory-only**, at most 1,000 rows / 24 hours. Running jobs expire after one hour; result references expire one hour after retrieval. Periodic cleanup runs every minute and on requests/results. Prompts are represented by a process-keyed HMAC for deduplication. No bytes, prompts or thumbnails are persisted to server storage.
- Server restart loses jobs and resets budgets. The epoch guard prevents a correctly retained old submission from being silently re-created, but does not provide recovery, durable quota enforcement or multi-replica consistency. Durable **metadata-only** reservations/reconciliation are still needed; Feishu Drive remains the canonical media storage target. Do not deploy this beta as a horizontally replicated or production billing service.

### Verification and sources

`test/media-service.test.js` exercises the real local HTTP gateway/session/media routes with a synthetic MiniMax transport: request shape and key boundary, duplicate POST race, foreign-owner denial, lease audience/kind/expiry, parent revocation during a slow body, video task/file identity, read backoff, uncertain submissions, cancellation/late success, budgets across devices, expiry, server-epoch rejection, shutdown/timeout, unsafe result URLs and bounded/error responses. No live MiniMax image/video generation or actual media bytes were tested in this increment.

The desktop tests include `test/media-workspace.test.js`, `test/media-delivery.test.js` and `node scripts/smoke-media-desktop.js`. The smoke requires local `ffmpeg` to make a synthetic flat-color PNG and one-second MP4; it is not an application runtime dependency. It runs actual Electron → native journal/client → actual local HTTP gateway/media routes → synthetic MiniMax JSON. The downloader returns synthetic media and the test-only CLI invocation seam returns synthetic auth/Drive envelopes; production Drive parsing, argument construction, reservation and verification code still run. It checks canceled generation/upload sends zero writes, one image and one video generation, one new Drive upload with exact bytes, restart/read-only reopen without duplicate upload, actual decoding/playback, preview isolation/cache cleanup and foreign-owner hiding. Exact provider/parent/issued media credentials are scanned out of isolated app data; Drive resource tokens are expected metadata, not credentials. Unit tests cover real downloader streams plus upload ambiguity, permission/folder/identity changes, pagination, disk failure and read-only recovery. Real MiniMax billing/output, real CDN transfer and real Drive upload are **not** established by these fixtures.

Pinned CLI 1.0.78 `drive +upload --help`, folder metadata and listing schemas were inspected. A read-only upload dry-run failed with `keychain Get failed: keychain not initialized`; no live write occurred and credential storage was not reset or downgraded. Therefore the shortcut's assumed standard success envelope `{ok:true,identity:"user",data:{file_token}}` still needs real acceptance after local CLI recovery and authorization for a disposable target folder. The supplied test document remains read-only and untouched.

Protocol checked against MiniMax's [text-to-image](https://platform.minimaxi.com/docs/api-reference/image-generation-t2i), [text-to-video](https://platform.minimaxi.com/docs/api-reference/video-generation-t2v), [video status](https://platform.minimaxi.com/docs/api-reference/video-generation-query) and [file retrieval](https://platform.minimaxi.com/docs/api-reference/file-management-retrieve) documentation on 2026-09-09. Current examples use `api.minimax.cn`; the adapter defaults to the user's requested domestic `api.minimaxi.com` and allows only these two domestic origins. Real account/model entitlement and output CDN behavior remain unverified.

## Result download and reserved address ranges

Before fetching a temporary result the desktop resolves the provider host and refuses any answer in a private or reserved IPv4 range (loopback, RFC 1918, link-local, CGNAT, benchmarking `198.18.0.0/15`, multicast). That is the default and it stays the default.

A private deployment may legitimately answer from one of those ranges — an internal mirror, or a local proxy running in fake-IP mode that maps public hosts into `198.18.0.0/15`. Write the ranges down explicitly in `.idou.json`:

```json
{ "media": { "allowedAddressRanges": ["198.18.0.0/15"] } }
```

Only IPv4 CIDRs are accepted, at most 32, validated when the configuration loads. An entry allows exactly that range and nothing adjacent; the refusal message names the address that was refused so the right range can be added.
